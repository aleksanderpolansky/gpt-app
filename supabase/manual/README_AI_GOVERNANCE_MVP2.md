# ARCTor — AI Governance MVP 2: draft SQL recovery order

Дата фиксации: 2026-10-20.

## Что реально находится в Supabase

`public.arctor_ai_governance_draft_save_v1(text,text,text,integer,uuid,text)` использует
существующие триггеры P4A на `public.ai_processing_instruction_sets`:

- `trg_ai_processing_instruction_set_prepare_p4a` — назначает номера ревизий.
- `trg_ai_processing_instruction_revision_append_p4a` — добавляет одну запись в
  `public.ai_processing_instruction_revisions`.

Функция MVP 2 **не вставляет историю вручную**. Сохранённые черновики имеют префикс
`governance_draft__` и статус `inactive`. Никакого выполнения ИИ, записи фактов
или списания AI EUR это исправление не включает.

## Порядок восстановления

1. Исходный файл `ARCTOR_AI_GOVERNANCE_MVP2_ATOMIC_DRAFT_RPC_20261020.sql`
   сохранён как **исторический артефакт** первого релиза. НЕ следует применять его
   отдельно или после исправления: первоначальная версия пыталась вручную
   писать ревизии и была несовместима с действующими P4A-триггерами.
2. На базе, где установлены P4A-триггеры, выполнить
   `ARCTOR_AI_GOVERNANCE_MVP2_RPC_TRIGGER_COMPAT_FIX_20261020.sql`.
   Этот файл заменяет RPC, проверяет предпосылки, сохраняет роль `service_role`
   единственным вызывающим и не создаёт тестовых данных.
3. Выполнить предусмотренную в конце SQL read-only проверку прав и тела функции.
4. Провести прикладные тесты на неисполняемом черновике: создание, новая ревизия,
   восстановление предыдущего текста как новой ревизии, отказ устаревшей записи.

## Подтверждено вручную 2026-10-20

- `MVP2_REVISION_2_PASS` — ревизии 1 и 2.
- `MVP2_RESTORE_V3_PASS` — ревизия 3 восстановила содержимое v1, v2 сохранена.
- `MVP2_CONFLICT_PROTECTION_PASS` — редактор А создал v4, устаревший запрос
  редактора Б отклонён, история `[1,2,3,4]`, состояние `inactive`.

## Известное ограничение: тип операции в истории

P4A-триггер не заполняет `change_note` для `governance_draft__`.
Интерфейс показывает `save` по умолчанию, включая реальные восстановления.
Это **не доказательство** действия `save`; `restore` как отдельный тип операции
пока не сохраняется в ревизии. Корректность содержимого ревизий подтверждена,
но журнал вида операции ещё требует узкого следующего изменения, которое НЕ
должно менять общие триггеры без отдельного QA и допуска к релизу.

Документирование файлов в Git не выполняет SQL в базе.
