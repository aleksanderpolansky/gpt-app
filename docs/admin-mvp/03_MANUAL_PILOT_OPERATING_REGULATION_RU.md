# ARCTor Management OS — регламент первого практического пилота

**Версия:** 1.0 · **Дата:** 19.10.2026 · **Статус:** инструкция для ручного пилота владельцем платформы.  
**Контур:** действующая `/admin` на arctor.app; внешнее окно ChatGPT; AI runtime ARCTor остаётся выключенным.

## 1. Условия старта

- Войти под действующим платформенным owner/admin. Других людей пока не назначать на общую платформенную роль.
- Использовать **настоящую проблему без личных данных**, которую разрешено обсуждать во внешней модели. Если подходящего случая нет, начать с внутренней технической задачи/тестового обезличенного примера, явно помеченного `DEMO`; не выдавать демонстрацию за пользовательский инцидент.
- Открыть `/admin` → «ADM-2B.2 Управление делами» → «Открыть конструктор».
- Перед записью проверить, что дело с таким источником ещё не существует; при неполном списке запросить адресную проверку, не создавать дубликат.
- Ни один шаг регламента не запускает SQL и не разрешает изменение онтологии/кода. Все действия с записью в админке делает человек после проверки.

## 2. Шаги единственного первого пилота

### Шаг 1. Зарегистрировать дело

**Кнопка:** «Создать дело». **Вид:** `defect` при реально воспроизводимой ошибке или `research` при неопределённости; не называть дефектом любое отсутствие автоматического совпадения. **Приоритет:** `normal`, если нет доказанного основания повышать.

Поля из текущего конструктора:

- **Название:** `Неоднозначное сопоставление активности с системной типовой активностью` (только если проблема реально воспроизведена).
- **Описание:** `Исходный факт: [обезличенный пример / ссылка]. Наблюдение: подбор не дал однозначного кандидата. Проверить: каталог существующих типовых активностей, синонимы и условия выбора. Не создавать новые объекты до отдельной проверки и решения.`
- **Должность-получатель:** `semantic` («Главный куратор модели») — если есть среди действующих вариантов.
- **Текст поручения:** вставить текст из раздела 4 ниже, адаптировав только проверенные входные данные.
- **Требуемый результат:** `До трёх существующих кандидатов только с проверенными идентификаторами, критерии выбора, недостающие данные, вердикт MATCH|NEEDS_REVIEW|NO_MATCH, предлагаемый следующий шаг. Ни одной записи ОН/типовой активности.`

**Критический момент:** текущий интерфейс `create` атомарно создаёт дело и первое поручение. Не нажимать повторно с новой операцией при неопределённом ответе; сначала проверить реестр.

### Шаг 2. Подготовить промпт и запустить внешнюю модель вручную

- Не переносить в ИИ сырые приватные активности, email, токены, технические секреты или неразрешённые производные данные.
- Открыть «Копировать для внешнего агента» либо вручную добавить утверждённый микропротокол `TA-MATCH-001` из файла `04_MICROPROTOCOL_TA_MATCH_001_RU.md`.
- Перед вставкой проверить конкретные входные данные. Промпт без действительного списка кандидатов не должен требовать от модели угадать системный ID; ответ должен быть `NEEDS_INPUT`.
- Сохранить у себя версию протокола и точные ID использованных источников. Сам по себе внешний диалог не является частью истории ARCTor.

### Шаг 3. Зафиксировать результат

В конструкторе «Принять отчёт» выбрать дело и поручение, в `reportText` (максимум 6000 символов) включить:

```
ПРОТОКОЛ: TA-MATCH-001 v1.0
ЗАДАЧА: [идентификатор дела / поручения]
ИСТОЧНИК: [разрешённая ссылка / обезличенный текст]
ДАННЫЕ КАНДИДАТОВ: [версия, количество]
ДЕЙСТВИЯ ИИ: [кратко]
РЕЗУЛЬТАТ: MATCH | NEEDS_REVIEW | NO_MATCH | NEEDS_INPUT
ПРОВЕРЕННЫЕ ФАКТЫ: [ID и подтверждённые основания]
ГИПОТЕЗЫ: [проверить]
ОШИБКИ ИИ: [что найдено человеком]
QA: PASS | REVISE | BLOCKED; проверявший [роль/человек]
ПРЕДЛАГАЕМЫЙ ШАГ: [без автодействия]
```

Если ответ/код длиннее 6000 символов, не обрезать молча: сделать краткую запись со ссылкой на проверенное отдельное место хранения и хеш полного артефакта. Защищённое хранение вложений в UI **ещё не доказано/не принято**.

### Шаг 4. Проверить результат человеком

Минимальная проверка: (1) исходный текст разрешён; (2) каждый ID существует; (3) данные не выдуманы; (4) проверены дубликаты и синонимы; (5) объяснено, почему выбран кандидат; (6) пропуски отмечены; (7) результат не утверждает, что что-либо уже записано; (8) указано дальнейшее действие и владелец.

**Сейчас это ручное решение человека, а не отдельная утверждённая системная сущность `approval`.** При `REVISE` создать новую корректирующую работу/отчёт в рамках дела, не стирать прежнюю историю.

### Шаг 5. Передать поручение

В «Передать дальше» выбрать исходное **уже отчитанное** поручение и целевую должность (`quality` для независимой проверки, либо `semantic` для доработки). Передать короткую инструкцию, причины решения, ссылки на доказательства и версию микропротокола. Исходный статус `reported` обязателен по текущему интерфейсу.

### Шаг 6. Проверить приемлемость передачи

Новый проверяющий должен только из дела понять: что случилось, что уже было проверено, какие ошибки обнаружены, что ещё нельзя делать и какой следующий шаг. Если этого нет, вернуть отчёт на уточнение. Закрывать дело только после проверки эффекта; фактический рабочий механизм закрытия/согласования ещё нуждается в source-intake.

## 4. Текст первого поручения для существующего конструктора

> Проверить невозможность однозначного сопоставления обезличенной активности с существующей системной типовой активностью. Работать по протоколу `TA-MATCH-001 v1.0`. Исследовать только предоставленный разрешённый пример и фактически выгруженные кандидаты. Сначала проверять существующие объекты/синонимы. Не придумывать UUID, не создавать новые типовые активности, объекты наблюдения, факты или формулы. При недостатке данных вернуть `NEEDS_INPUT` либо `NEEDS_REVIEW`. Передать отчёт с доказательствами выбора, альтернативами, обнаруженными ошибками и следующим действием.

## 5. Фиксация проблем прямо во время пилота

У каждой обнаруженной трудности четыре обязательных атрибута: фактическая операция, ожидаемое поведение, наблюдаемое поведение, ссылка/доказательство. Не исправлять на месте без отдельного scoped разрешения. Каждая реальная проблема может стать новым административным делом (после triage), а не стихийной переделкой нескольких подсистем.

## 6. Критерий завершения первого пилота

PASS при наличии: действительного дела/источника → зарегистрированного поручения → конкретного промпта `TA-MATCH-001` → сохранённого отчёта → проверенного решения → передачи следующему человеку/должности, причём получатель способен понять контекст без личного чата автора. Часть «получатель — новый реальный пользователь» до внедрения персональных кабинетов остаётся демонстрационной, не считать E2E multiuser PASS.
