# ON-REVIEW-001 v1.0 — необходимость нового объекта наблюдения

**Статус:** рабочий проект микропротокола, для ручного использования; не утверждён автоматический допуск к записи ОН.  
**Ответственная должность:** `semantic`; **согласующие:** предметный куратор и, при изменениях схемы, `engineering`/`quality`.  
**Режим:** только поиск, классификация и предложение.

## 1. Когда применять

Когда в деятельности, источнике либо в профиле типовой активности нужен объект наблюдения, но существующая онтология не даёт очевидного однозначного кандидата. Ошибка сопоставления не всегда требует создания ОН: причиной может быть отсутствующий синоним, связь, параметр, профиль, типовое действие или неполная информация.

## 2. Проверки перед предложением

1. Есть ли действующий ОН с тем же смыслом под другим названием, языком или синонимом?
2. Не является ли искомое **экземпляром** существующего типа (конкретный магазин в городе), а не новым дочерним классом?
3. Не подменяется ли отношение «находится в / принадлежит сети / реализует / воздействует на» иерархией «родитель — ребёнок»?
4. Какая сущность описывается: структура/система, действие/процесс, состояние/потребность? Допускаются несколько типизированных связей-опор, если это обосновано.
5. Не хватает ли только измеряемого параметра, единицы, формулы или листового объекта внутри уже существующей ветви?
6. Кто владеет изменением, какие данные подтверждают необходимость и какие существующие формулы/типовые активности затронет новая связь?

## 3. Входные данные

- `caseCode`, `assignmentId`;
- формулировка потребности и источник;
- проверенная часть каталога существующих ОН: ID, название, тип, статус, связи (с пометкой полноты выборки);
- список синонимов и языковых вариантов;
- допустимые виды связей;
- критерии успешного использования нового ОН;
- приватность исходного примера.

Без действительного каталога: `NEEDS_INPUT`, а не выдуманная структура.

## 4. Готовый промпт

```text
Роль: аналитик структуры объектов наблюдения ARCTor. Узкая задача — оценить необходимость нового ОН; никакой записи и самостоятельной модификации онтологии.

caseCode: [КОД_ДЕЛА]
assignmentId: [ID_ПОРУЧЕНИЯ]
Потребность: [КАКОЙ_ФАКТ_ИЛИ_ПРОЦЕСС_НЕ_УДАЁТСЯ_ОПИСАТЬ]
Разрешённый первоисточник: [СВЕДЕНИЯ_БЕЗ_ПРИВАТНОГО_ТЕКСТА]
Известные ОН: [ПОДЛИННЫЙ_СПИСОК_ID_НАЗВАНИЕ_ТИП_СТАТУС_СВЯЗИ]
Допустимые отношения: [СПИСОК_ТИПОВ_СВЯЗЕЙ]

ПРОВЕРЬ ПО ПОРЯДКУ:
(1) существующие точные объекты и синонимы;
(2) нужно ли лишь новое отношение, параметр, единица, вариант экземпляра;
(3) отличие родительской классификации от типизированной связи;
(4) возможные связи с системами/структурами, действиями/процессами и состояниями/потребностями;
(5) противоречия и возможные дубликаты;
(6) влияние на существующие типовые активности, факты и формулы.

ЗАПРЕТЫ: не придумывай ID, не объявляй неполный каталог полным, не утверждай отсутствие дубля без проверки, не выполняй INSERT/UPDATE/SQL, не записывай факт.

ВЫВОД:
DECISION: REUSE_EXISTING | ADD_RELATION | ADD_ALIAS | ADD_PARAMETER | PROPOSE_NEW_ON | NEEDS_INPUT | NEEDS_REVIEW
EXISTING_IDS: [только реальные ID из входа]
PROPOSED_OBJECT_TYPE: [если необходим]
PROPOSED_NAME_AND_DEFINITION: [если необходим]
TYPED_RELATIONS: [тип отношения, target id из реестра либо 'requires_lookup']
REASON_AND_EVIDENCE: [...]
DUPLICATE_CHECK_LIMITS: [...]
UNKNOWN_AND_RISKS: [...]
CURATOR_APPROVAL_REQUIRED: true
CHANGES_PERFORMED: false
```

## 5. QA / стоп-условия

`REVISE` при неправильной иерархии, выдуманных ID, потере типизированных связей, неподтверждённом отсутствии дублей, неопределённом владельце или использовании приватного текста без разрешения. `NEEDS_INPUT` при неполном каталоге. Объект добавлять только после отдельной проверки карточки куратора и действующей процедуры записи.
