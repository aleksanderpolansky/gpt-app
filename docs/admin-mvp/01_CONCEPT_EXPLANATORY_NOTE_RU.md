# ARCTor Management OS — пояснительная записка о назначении и принципах

**Версия:** 1.0 · **Дата:** 19.10.2026 · **Статус:** предлагаемое проектное решение для утверждения владельцем.  
**Область:** административная система ARCTor, практический ручной MVP (не весь ARCTor, не автономные AI-агенты).  
**Канонический источник фактов о текущем состоянии:** репозиторий `aleksanderpolansky/gpt-app`, `main` / production SHA `e73b66be8e979e742fef8ab494bd732f7fa38797` и переданные результаты QA от 19.10.2026.

## 1. Для чего существует административная система

ARCTor Management OS предназначена для повторяемого решения проблем и выполнения задач развития платформы независимо от личности конкретного менеджера. Вся работа должна оставлять в системе проверяемый след: что произошло, на основании какого источника, кто отвечает, что поручено, какой ИИ-промпт применялся, что ответил ИИ, какие ошибки найдены, что подтвердил человек и что делать дальше.

Задача продукта — не создать «всезнающего ИИ-администратора», а дать людям устойчивые производственные процессы, в которых ИИ помогает выполнять узкие операции, но не получает права самостоятельно объявлять недоказанные факты истинными и менять систему.

### Короткое определение

**Дело** — отдельная проблема, запрос или изменение, имеющие причину, доказуемый первоисточник и итог.  
**Поручение** — ограниченная задача в рамках дела, закреплённая за функциональной должностью и позднее — за конкретным исполнителем.  
**Микропротокол** — версия инструкции для одного узкого класса задач (например, поиск типовой активности).  
**Рабочий промпт** — конкретная инструкция ИИ, сформированная из микропротокола и разрешённых фактических данных.  
**Отчёт** — результат выполнения, разделяющий факты, гипотезы, проверки, ошибки и предложенные действия.  
**Решение** — отдельное человеческое принятие, отклонение или запрос доработки. Отчёт ИИ не равен разрешению изменения БД, кода или онтологии.

## 2. Основной рабочий цикл

1. Сигнал поступает из существующей подсистемы, обращения человека или диагностического журнала; фиксируются идентификатор источника, дата и допустимость просмотра.
2. Диспетчер/администратор решает, требует ли сигнал дела. Технический статус вроде `analysis_ready` сам по себе не доказывает наличия проблемы.
3. Создаётся дело: формулировка проблемы, предметная причина, приоритет и ответственная должность.
4. Должности выдаётся поручение с ограничениями, исходными ссылками, микропротоколом и конкретным критерием готовности.
5. Менеджер копирует разрешённый рабочий промпт во внешний ИИ; автоматический встроенный запуск сейчас не нужен.
6. Менеджер проверяет ответ по контрольному списку, сохраняет существенные исходные доказательства и отчёт.
7. Отдельный уполномоченный человек принимает результат, запрашивает исправления либо передаёт следующую задачу. Пока структурированное согласование не реализовано, это только ручная процедура; не маркировать её «системно подтверждённой».
8. Дело закрывают после проверки фактического эффекта; подтверждённые правила и ошибки становятся кандидатами для организационной памяти.

## 3. Восемь функциональных направлений

| Код | Должность / направление | Основная компетенция |
|---|---|---|
| `process` | Руководитель процессов | Диспетчеризация, маршруты, сроки, эскалация |
| `product` | Руководитель продукта | Требования, цели, приоритеты и продуктовые решения |
| `semantic` | Главный куратор модели | Онтология, объекты наблюдения, типовые активности, связи |
| `ai` | Руководитель ИИ | Промпты, модели, инструкции, качество AI-ответов |
| `engineering` | Технический руководитель | Код, миграции, архитектура, техническая эксплуатация |
| `quality` | Руководитель качества | Доказательства, тесты, приёмка, регрессия |
| `commercial` | Коммерческое направление | Торговые организации, товары, сертификаты, покупки |
| `support` | Поддержка пользователей | Обращения, доступ, локализация, помощь |

Это **функциональные направления**, не восемь действующих самостоятельных аккаунтов менеджеров. Реальная привязка конкретного сотрудника к должности и минимальные персональные права — ближайшая разработка.

## 4. Почему это полезно при смене менеджеров

Вся производственная память принадлежит делу и должности, а не личной переписке исполнителя. Новый менеджер должен открыть одно место и увидеть: статус, историю, первоисточники, решения, текущую версию инструкции, неудачные попытки, открытые вопросы и следующий допустимый шаг. Передача должности не должна означать потерю знаний и пересоздание дел.

## 5. Роль ИИ: точность через узость задачи

Модель не гарантирует «ноль галлюцинаций». Минимизировать ошибки можно более надёжно через:

- один микропротокол на один проверяемый вид задачи;
- только переданные действительные кандидаты и идентификаторы, а не «всё знание ИИ»;
- запрет придумывать IDs, источники, формулы, результаты тестов;
- обязательный ответ `недостаточно данных` / `needs_review`;
- явное разделение `verified`, `inferred`, `unknown`, `contradicted`;
- детерминированные проверки идентификаторов, типов, прав и правил онтологии;
- окончательное решение человека перед записью в систему.

Примеры первых классов микрозадач: **TA-MATCH-001** — подобрать существующую типовую активность; **ON-REVIEW-001** — проверить необходимость нового объекта наблюдения.

## 6. Границы первой практической версии

**Входит:** дело, поручение, ручной промпт, внешний ИИ, ручной отчёт, человеческая проверка, передача следующей должности, сохранение следа.  
**Пока не входит:** полноценный персональный кабинет рядового менеджера, автоматические вызовы ИИ из административной системы, исполнение SQL/кода ИИ, финансовый резерв ИИ, самостоятельное изменение онтологии, автоматическое обучение и полная оркестрация.

На первом этапе реальную работу ведёт действующий платформенный owner/admin. Новых менеджеров с административными полномочиями **не приглашать до минимальной ролевой авторизации и проверки Admin Assist**.

## 7. Минимальная безопасность уже сейчас

Число пользователей не определяет наличие риска: даже одна личная запись может быть неправомерно скопирована внешней модели. Для ручного пилота использовать только учебные или специально разрешённые данные, не вставлять персональные исходные тексты, токены и секреты в промпты. Промпт перед отправкой должен проходить человеческую проверку допустимости раскрытия. Любой ответ ИИ — предложение, не разрешение на действие.

Глубокую инфраструктуру outbound/billing/runtime можно отложить до внедрения встроенных AI-исполнителей. Отдельно сохранённый риск границы Admin Assist (`KNOWN_RISK_DEFERRED`) не считать устранённым.

## 8. Метрика успеха

Пилот считается практическим успехом, если второй человек, не присутствовавший при исходной работе, способен по записи дела и инструкциям воспроизвести ход решения, выявить незакрытые вопросы, повторить проверки и корректно продолжить поручение без доступа к личной истории чатов предшественника.
