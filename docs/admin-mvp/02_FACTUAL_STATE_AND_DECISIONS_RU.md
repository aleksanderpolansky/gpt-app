# ARCTor Management OS — зафиксированное состояние и решение о смене приоритета

**Версия:** 1.0 · **Дата:** 19.10.2026 · **Статус:** фактологическая справка + предлагаемый план, без автоматического утверждения ADR.

## 1. Что фактически реализовано

| Подсистема | Установленный факт | Чего не следует утверждать |
|---|---|---|
| GitHub/Vercel | `main` на SHA `e73b66be8e979e742fef8ab494bd732f7fa38797`; Vercel production `READY`, домен `arctor.app` | Это не E2E всей платформы |
| ADM-2B.1 | API `registry` читает роли, дела, поручения и ограниченную историю событий | `viewer`-режим чтения не равен личному кабинету исполнителя |
| ADM-2B.2 | API `actions` поддерживает `create`, `assign`, `report`, `handoff` через атомарную RPC | Запись пока только платформенный `owner/admin`, не рядовой менеджер |
| UI | На `/admin` работает конструктор `ArctorAdminCaseActions` с полями дела, поручения, ожидаемого результата, ручного отчёта и копирования задания | Нет специальных полей версий промптов, проверки QA и вложений как принятой функции |
| ADM-4 | Есть коммерческие очереди, проверка некоторых первоисточников, ручная привязка к делам | Полная доказуемость производных текстов и необходимость открытия дела не закрыты |
| ADM-5A/B | Восемь функциональных ролей, контекстные manifest/snapshot, внутренний review | `reviewed_internal` не разрешает внешний вызов ИИ или передачу данных |
| ADM-5C.3B | Register-only API и RPC, append-only таблицы попыток и событий | Нет runtime, outbound, бюджета, исполнения ИИ |

### Ограничения конкретных API

- `src/app/api/admin/management/actions/route.ts`: `create/assign/report/handoff`, требует `owner/admin`; отчёт передаётся `reportText` (10–6000 символов), поручение — `assignmentText`, `requiredResult`. Нет отдельного структурированного `approve/reject/revise`.
- `src/app/admin/ArctorAdminCaseActions.tsx`: кнопка копирования задания и человеческая запись событий; не самостоятельный «рабочий кабинет менеджера».
- `src/app/api/admin/management/registry/route.ts`: реестр возвращает ограниченную выборку, есть признаки `truncated`; не использовать как доказательство полноты всей истории при больших объёмах.

**Граница подтверждения:** выводы тестов предоставлены оператором; P1 не имеет независимой полной security/E2E sign-off. Прямые мутационные атаки на append-only не выполнялись.

### Открытые проверки P1

1. Реальные пользовательские HTTP-сессии `viewer/moderator` — `BLOCKED` без подтверждённых тестовых аккаунтов.
2. Первая конкурентная регистрация нового кандидата — `BLOCKED`: SELECT вернул 0 подходящих новых кандидатов.
3. Stale/rejected snapshot, inactive role, чужое поручение; отрицательные mutating кейсы — не полностью проверены.
4. Полная история событий в UI, correlation ID, сохранение SQLSTATE и внутренней классификации ошибок — отдельный backlog.
5. ADR регистрации в источниках `proposed` и P0 independent reviewer не подписан.
6. Admin Assist effective/real identity — `KNOWN_RISK_DEFERRED`, не исправлен и не должен обходиться в новых кабинетах.

## 3. Источник P2 и почему меняем очередность

P2 source intake `ARCTOR_P2_ADM4_SOURCE_INTAKE_20261019_095917.zip`: 115 файлов, 71 административный маршрут, хеши 115/115 PASS. Анализ выявил четыре риска/долга:

1. Разрешённый PUBLIC статус `message_objects` не доказывает публичность производных `activity_events.input_text`, `rawFragment` и иных полей; при копировании внешнему ИИ нужна строгая граница.
2. Техническое `analysis_ready` не подтверждает причину открытия дела; требуется человеческий triage.
3. Выборка ограниченного числа дел/сигналов может скрыть старую связь источника с делом.
4. В некоторых диагностических API требуется нормализовать ответы ошибок.

Это проблемы качества, но они не требуют завершать всю автономную агентную программу прежде, чем выполнить **одну ручную задачу с разрешёнными данными**.

## 4. Управленческое решение — рекомендуемая смена очереди

**Было:** продолжать последовательную техническую программу P2→P14 до практической работы.  
**Становится:** начать практический человекоцентричный MVP на действующем ADM-2/ADM-4, а в процессе устранять доказанные препятствия. Исходный P0–P14 остаётся стратегической дорожной картой, а не отменяется.

| Приоритет | Рабочий результат | Gate |
|---|---|---|
| A0 — немедленно | Реальное разрешённое дело → промпт → ответ ИИ → ручной отчёт → передача | Платформенный owner/admin; без внешней передачи секретов/личных данных |
| A1 — ближайший код | Структурированная карточка дела/поручения, версия промпта, доказательства, QA, статус | Source + schema intake; scoped patch, отдельная приёмка |
| A2 | Аккаунты конкретных менеджеров, привязка к должности, ограниченные права и смена исполнителя | Персональный ACL, независимый запрет обхода через Admin Assist |
| A3 | Три независимых сквозных сценария и процедура сохранения контекста | Человек, не участвовавший раньше, продолжает дело без помощи автора |
| B | Встроенный AI runtime, outbound policy, budget, agent registry | Отдельный проект и санкция, позже |

## 5. Чего нельзя считать готовым

- Автономные агенты и вызов модели API отсутствуют в данном контуре.
- Нельзя выдавать новым менеджерам платформенные `owner/admin` только ради доступа к задачам.
- Нельзя считать текст ИИ проверенной истиной или запись в `reportText` утверждением QA.
- Нельзя запускать SQL/пушить код или создавать ОН по рекомендациям ИИ без отдельного human decision.
- Не объявлять устранёнными приватность производных коммерческих данных, администраторскую подмену личности и старые backlog P1.
