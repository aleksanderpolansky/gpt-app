# TA-MATCH-001 v1.0 — выбор существующей типовой активности

**Статус:** рабочий проект микропротокола; НЕ утверждённая системная инструкция.  
**Ответственная должность:** `semantic`; **проверяющий:** другой человек/роль `quality` по возможности.  
**Режим:** только анализ и предложение. **Запрещено:** создание/изменение объектов, запись фактов, вызовы SQL, допущение выдуманных ID.

## 1. Когда запускать

Если для конкретной активности не определена системная типовая активность либо выбрано несколько кандидатов. Наличие статуса `needs_review` не означает, что обязательно нужен новый типовой объект; сперва найти существующие.

## 2. Обязательные входы

- `caseCode` и `assignmentId` для трассировки;
- безопасный для передачи, обезличенный или разрешённый текст активности;
- дата/контекст и единицы измерения, **если доказанно нужны** для выбора;
- список реальных кандидатов из системного реестра: `id`, название, краткое назначение, доступность/статус, существенные ограничения;
- язык и терминологические синонимы, если задокументированы;
- критерии различения кандидатов, подготовленные куратором.

При отсутствии списка проверенных кандидатов: `NEEDS_INPUT` и запрос на выгрузку. Нельзя просить модель сгенерировать неизвестные системные идентификаторы.

## 3. Готовый промпт — вставить после заполнения полей

```text
Роль: помощник главного куратора модели ARCTor. Работай ТОЛЬКО по данной узкой задаче: сопоставление активности с существующей системной типовой активностью.

caseCode: [КОД_ДЕЛА]
assignmentId: [ID_ПОРУЧЕНИЯ]
Пример активности (разрешённый): [ОБЕЗЛИЧЕННЫЙ_ТЕКСТ]
Проверенные кандидаты из реестра: [СПИСОК_ID_НАЗВАНИЕ_ОПИСАНИЕ_СТАТУС]
Допустимые правила различения: [ПРАВИЛА_И_ИСТОЧНИКИ]

ПРАВИЛА:
1. Не используй сведения за пределами переданных кандидатов как доказательство существования объекта в ARCTor.
2. Не придумывай UUID, статусы, ссылки и «уже сделанные» изменения.
3. Сначала проверь соответствие действия, объекта действия, условий и измерений; затем синонимы и более общие категории.
4. Если кандидаты равнозначны или контекста мало — NEEDS_REVIEW; если кандидатов нет в данных — NEEDS_INPUT.
5. Новую типовую активность разрешено только ПРЕДЛОЖИТЬ после объяснения, почему имеющиеся не подходят. Не создавать ничего.
6. Выделяй VERIFIED (основано на входных данных), INFERRED (гипотеза), UNKNOWN (неизвестно).

ФОРМАТ ОТВЕТА:
STATUS: MATCH | NEEDS_REVIEW | NO_MATCH | NEEDS_INPUT
SELECTED_EXISTING_ID: [строго из списка / null]
CANDIDATES: [не более 3; id, почему подходит/не подходит]
EVIDENCE: [на какую строку входа опирается вывод]
UNCERTAINTY: [что неизвестно и что необходимо запросить]
HALLUCINATION_CHECK: [проверка всех ID по входному списку]
PROPOSED_NEXT_ACTION: [только рекомендация для куратора]
NO_CHANGES_PERFORMED: true
```

## 4. Контроль качества ответа

`PASS` только если выбранный ID действительно входил в проверенный список, обоснование показывает конкретные признаки, синонимы проверены, а при недостатке данных модель отказалась делать уверенный выбор. При выдуманном ID, смешении `system`/`personal` активностей, необоснованном создании нового ОН или факта — `REVISE`.

## 5. Выход и запись

Краткий отчёт → существующая операция `report` в деле, полный промпт/ответ хранить по согласованной безопасной схеме позднее. Новые записи типовых активностей создавать только отдельной процедурой куратора после human approval.
