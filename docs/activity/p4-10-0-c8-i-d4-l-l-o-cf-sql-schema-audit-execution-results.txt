Provider handling decision
public.app_users does not contain a separate provider or auth_provider field.
The future mapping corridor must accept only provider auth0 from the trusted server-side Auth0 session.
Non-auth0 provider must fail closed before DB lookup.
The lookup predicate for this corridor is auth0_sub equals trusted authSubject.

Duplicate prevention decision
public.app_users has PRIMARY KEY (id).
public.app_users has UNIQUE (auth0_sub).
public.app_users has unique index app_users_auth0_sub_key on auth0_sub.
Therefore duplicate app user mapping by auth0_sub should be prevented by schema.
Future code should still fail closed if a defensive lookup unexpectedly returns more than one row.

Active/status decision
public.app_users has no active, status, disabled, blocked, deleted_at or archived_at field.
Therefore app_user_inactive is not supported by current public.app_users schema.
The future read-only mapping response should not claim an inactive check was executed.
Recommended future response flags:
- appUserInactiveSupported: false.
- appUserInactiveCheckExecuted: false.
Adding active/status support requires a separate migration/status gate.

RLS and server-side access decision
RLS is enabled for public.app_users.
No RLS policies were returned for public.app_users in the metadata audit.
A normal client-side or user-scoped Supabase client must not be assumed to read public.app_users.

Recommended implementation path: server-only Supabase service-role/admin client, never exposed to the browser.
