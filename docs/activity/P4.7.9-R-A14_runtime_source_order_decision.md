## Current production runtime source order

## Target production runtime source order

Target source order after explicit A14 switch:

1. registry_table
2. activity_templates.default_metadata_json
3. hardcoded_fallback

## Switch principle

A14 must be rollback-friendly.

The switch must not remove the existing default_metadata_json reader.

The switch must not remove hardcoded fallback.

The resolver should prefer registry_table only when an enabled valid table row is found and parsed successfully.

If registry_table is missing, invalid, disabled, or returns a DB error, resolver must fall back to activity_templates.default_metadata_json.

If default_metadata_json is missing or invalid, resolver must fall back to hardcoded fallback.

## Proposed resolver behavior after switch

For a known template slug:

1. Attempt to read enabled registry table row by template_slug.
2. If row exists and parses cleanly, build classification/value mapping rule from registry table.
3. Mark selectedSource = registry_table.
4. Include table diagnostics in resolver diagnostics.
5. If table read fails or row is not usable, try default_metadata_json.
6. If default_metadata_json is usable, mark selectedSource = db_metadata.
7. If DB metadata is not usable, use hardcoded fallback.
8. Preserve warning trail showing which sources were attempted and why fallback happened.

## Required source labels

## Rollback strategy

Rollback must be simple:

- revert the resolver switch commit
- keep registry table and diagnostic endpoint in place
- production returns to default_metadata_json plus hardcoded fallback

No data rollback should be required because A14 switch should only change read-source priority.

A14 does not remove hardcoded fallback.
