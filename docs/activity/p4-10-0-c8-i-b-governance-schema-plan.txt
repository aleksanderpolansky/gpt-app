============================================================
3. Naming rules
============================================================
- Use snake_case table and column names.
- Use stable *_key fields for semantic keys such as state_dimension_key and rule_key.
- Use *_id only for database identifiers.
- Use source_kind for classification: direct_measurement, user_self_report, semantic_hook, inferred_state, risk_flag, forbidden_overclaim.
- Use privacy_level and sensitivity_level consistently.
- Use confidence consistently and avoid unbounded AI certainty language.
- Use evidence_summary instead of raw private text when possible.
- Use status fields for lifecycle: active, provisional, corrected, rejected, expired.
- Use valid_from, valid_to, observed_at, generated_at where time meaning differs.

============================================================
4. Ownership and subject rules
============================================================
- Every personal state row must be owned by the authenticated app user or by a private user-owned subject reference.
- Never rely on client-submitted user_id as trusted identity.
- Server-side Auth0/Supabase mapping remains the trusted identity source.
- Enterprise or organization state must be explicitly separated from personal state.
- Public directory/commercial data must not expose private personal state.
- Family, child, health, emotional, finance, exact location and workplace-conflict contexts are private or sensitive by default.
- A state fact must have a safe subject reference and must not expose raw identity unnecessarily.

============================================================
5. Privacy and sensitivity rules
============================================================

Default privacy:
- direct_measurement: private by default
- user_self_report: private by default
- semantic_hook: private by default when personal
- inferred_state: private by default
- risk_flag: private/internal
- forbidden_overclaim: internal suppression only
- similarity_edge: private unless explicitly public and non-sensitive
- relevance_edge: private unless explicitly public and non-sensitive

Sensitive domains:
- health
- emotional state
- family and child context
- finance
- exact location
- workplace conflict
- protected attributes
- legal/tax/medical conclusions

Rule:
Sensitive data must be private by default and correctable by the user.

============================================================
6. Evidence and confidence rules
============================================================
- A category candidate is not evidence by itself.
- A semantic hook is weak evidence only.
- A user self-report is evidence of user-reported state, not objective medical/legal/financial certainty.
- A direct measurement requires value, unit, source and time context.
- An inferred state requires rule, evidence summary, confidence, time window and correction lifecycle.
- A risk flag suppresses or downgrades unsafe interpretation.
- A forbidden overclaim blocks fact creation.
- Confidence must be conservative and explainable.

============================================================
7. Lifecycle rules
============================================================
- Every future state fact must be correctable.
- Every future inferred state must be provisional unless confirmed.
- Rejected inference must not continue to influence recommendations unless new evidence appears.
- Expired facts/snapshots must not silently drive NBA ranking.
- Corrections must create audit/correction rows or equivalent trace later.
- State snapshots must include input facts/deltas used and expiry policy.
- Resolver candidate links must be suppressible or correctable by user feedback.

============================================================
8. Similarity/relevance governance
============================================================
- Similarity edges and relevance edges must be separate future schema concepts.
- Similarity must not be treated as causality.
- Similarity must not create state facts.
- Relevance must not be treated as proof.
- Relevance must not override user choice in NBA v0.
- Influence requires stricter evidence than relevance.
- Risk flags can suppress relevance even when relevance score is high.
- User feedback must be able to reduce or reject automatic similarity/relevance suggestions.

============================================================
9. Next Best Action governance
============================================================
- NBA v0 starts with weakest or under-attended direction detection.
- NBA v0 must ask the user which direction to work on before suggesting actions.
- NBA may use direct measurements, self-reports, hooks, inferred states, relevance edges and risk flags conservatively.
- NBA must not claim certainty.
- NBA must not make medical, legal, financial, hormonal or social claims.
- NBA must explain why a candidate is shown.
- NBA must collect feedback/correction.
- NBA must not expose private state to other users.

============================================================
10. RLS and GRANT governance
============================================================

Future SQL migration order:
create table -> indexes -> enable row level security -> policies -> explicit GRANT.

Core rule:
GRANT does not replace RLS.

Default future access model:
- anon: only public directory/profile/offers read-only, if explicitly intended.
- authenticated: user-owned operations according to RLS.
- service_role: backend/server routes only.
- private activity/state/semantic/commercial-sensitive tables: never opened wider than necessary.
- state-related personal tables: private by default.
- semantic/resolver debug data: private or internal unless explicitly sanitized.
- No broad public read on state facts, state deltas, state snapshots or personal resolver outputs.

Supabase Data API rule:
All new SQL migrations must include explicit GRANT statements next to RLS policies.

============================================================
11. Additive migration governance
============================================================
- Future migrations must be additive first.
- Avoid destructive changes until data model is proven.
- Prefer nullable columns and backfill steps when introducing new fields.
- Use indexes only after identifying query patterns.
- Use check constraints carefully and only for stable enums/contracts.
- Avoid premature enum hard-locking if category/state vocabulary may evolve.
- No migration before C8-I-C SQL audit and C8-I-D design.
- No activity_events write enablement inside C8-I-B.

============================================================

C8-I-C SQL audit should inspect:

- existing category derivation tables or files

============================================================
14. Governance checklist for future table design
============================================================
- Does the table have clear owner/subject semantics?
- Does it avoid VO subtypes?
- Does it separate category, hook, fact, delta, snapshot and edge?
- Does it include source/evidence/confidence where needed?
- Does it include privacy/sensitivity where needed?
- Does it include correction/lifecycle where needed?
- Does it avoid raw sensitive text unless necessary?
- Does it avoid public exposure by default?
- Does it have RLS?
- Does it have explicit GRANT?
- Does it avoid broad anon access?
- Does it avoid unsupported medical/legal/financial/social claims?
