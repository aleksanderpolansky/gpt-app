- do not create a registry table yet

---

## 2. Why a table may be needed later

A dedicated table becomes useful when:

- known templates grow from 2 to dozens or hundreds
- registry rules need filtering, audit, admin UI, or versioning
- multiple rules per template become necessary
- rule activation/deactivation should not require editing JSON
- DB-level uniqueness constraints become important
- seed/migration review should be easier than nested JSON comparison

## 4. Proposed future table

Recommended future table name:

- public.activity_template_known_registry_rules

Reason:

- clearly connected to activity_templates
- expresses that this is a registry of known rules
- not limited to rubricator only forever
- still specific enough for the current resolver

## 5. Proposed columns

Identity:

- id uuid primary key default gen_random_uuid()
- activity_template_id uuid not null references public.activity_templates(id) on delete cascade
- template_slug text not null

Registry control:

- enabled boolean not null default true
- rule_key text not null
- source_type text not null default 'system_seed'
- classification_role text not null default 'primary'
- confidence numeric not null default 1
- registry_version text not null default 'v1-registry-table'
- priority integer not null default 100

Rubricator candidate:

- object_type_code text not null

- context_code text not null
- contextual_category_slug text not null

Value Object mapping:

- value_object_title text not null
- value_object_type text not null
- relation_type text not null
- metric_key text not null

## 6. Proposed constraints

Minimum v1 constraints:

- unique(rule_key)
- unique(activity_template_id, classification_role)
- check confidence between 0 and 1
- check non-empty rule_key
- check non-empty template_slug
- check non-empty object_type_code
- check non-empty action_type_code
- check non-empty context_code
- check non-empty contextual_category_slug

---

## 7. Resolver behavior after extraction

Future resolver order:

1. Try registry table.
2. If enabled matching rule exists and validates: use source = registry_table.
3. If registry table read fails: fallback to default_metadata_json.
4. If default_metadata_json missing or invalid: fallback to hardcoded rule.
5. Expose mismatches in diagnostics.

Recommended future resolver modes:

- prefer_registry_table
- prefer_default_metadata_json
- hardcoded_only

---

## 8. Compatibility rule

Do not remove knownTemplateRegistry, rubricatorCandidate, or valueObjectMapping from activity_templates.default_metadata_json during first extraction.

Transition should keep all three layers:

- registry table
- default_metadata_json
- hardcoded fallback

Reason:

- rollback remains easy
- diagnostics remain comparable
- mismatch detection remains possible

## 10. Rollback plan

Rollback must be simple:

- keep hardcoded fallback unchanged
- keep default_metadata_json unchanged
- if table resolver fails, switch back to prefer_db_metadata
- if migration causes DB issues, disable table usage without deleting table
- do not remove existing metadata blocks until a later phase
