1. Idempotency design decision

Future file
- lib/activity/controlledIntake/idempotency.ts

Future responsibilities
- Build deterministic idempotency material from validated input and authenticated server context.
- Normalize only safe user-provided fields.
- Include server-side authenticated app user id / actor id only when available from trusted backend context.
- Never trust client-provided userId, actorId, ownerId, organizationId, tenantId, workspaceId or activityEventId.
- Return a stable idempotency key suitable for preventing duplicate raw intake creation.
- Return trace metadata that can be stored later in activity_events metadata/json field if schema allows.

Recommended idempotency material v1
- schemaVersion
- helperLayer
- inputText normalized and trimmed
- title normalized and trimmed
- source
- durationMinutes if present
- startedAt if present
- endedAt if present
- occurredAt if present
- timezone if present
- trusted server actor/app user identifier when available
- optional organization/space identifier only from server-side trusted context

Do not include
- categoryCandidates
- metricCandidates
- stateHookCandidates
- valueObjects
- stateFacts
- stateDeltas
- stateSnapshots
- client-provided ownership fields
- non-deterministic generatedAt
- AI output
- raw metadata fields that can change without changing the activity meaning

Recommended idempotency key method
- Create canonical JSON from deterministic idempotency material.
- Sort object keys recursively.
- Hash canonical JSON with SHA-256.
- Prefix with controlled-intake-v1.
- Example shape: controlled-intake-v1:<sha256>

Reason
This avoids accidental duplicate activity_events while keeping semantic processing separate and later.

2. Persist design decision

Future file
- lib/activity/controlledIntake/persist.ts

Future responsibilities
- Accept only:
  1. ControlledActivityIntakePayload produced by payloadBuilder.
  2. Trusted server-side context produced by route/auth layer.
  3. Supabase/server DB client provided by route layer, not created inside validator/payloadBuilder.
- Insert only one raw row into activity_events.
- Return inserted activity_event id and safe trace data.
- Not call AI.
- Not call Category Derivation.
- Not create Value Objects.
- Not persist categoryCandidates.
- Not persist metricCandidates.
- Not persist stateHookCandidates.
- Not write value_object_state_facts.
- Not write activity_state_deltas.
- Not write snapshots.

Persist helper boundary
The persist helper may later write to activity_events only.
It must not become a semantic processor.
It must not become a router.
It must not own authentication.
It must not create Supabase client implicitly if project architecture prefers injected server client.

3. Metadata trace vs dedicated trace field decision

Decision for current stage
Use metadata/json trace first if activity_events already has a suitable metadata/details/raw_json column.
Do not add a dedicated trace column in O-H.
Do not run SQL in O-H.
A future schema audit/gate must confirm the exact target column before implementation.

Reason
The O-E gate selected existing activity_events mapping as sufficient for static helper work.
Dedicated trace fields may be useful later, but adding them now would violate additive-safe, proof-first discipline.

5. Duplicate handling strategy

Preferred future behavior
- Build idempotencyKey before insert.
- Search for an existing activity_event created by same trusted actor/context with same idempotency key if schema allows storing/querying it.
- If duplicate exists, return existing event with duplicateDetected: true.
- If no duplicate exists, insert new raw activity_event with duplicateDetected: false.

If no indexed idempotency storage exists yet
- Store idempotency key in metadata trace temporarily.
- Avoid adding SQL until a separate schema audit/gate confirms whether a dedicated index is needed.
