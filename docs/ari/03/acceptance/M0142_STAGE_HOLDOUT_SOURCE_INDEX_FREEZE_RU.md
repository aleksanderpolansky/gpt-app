# ARCTor M-0142 / ARI-03.08.04 — зафиксировать stage/holdout и полный source/index SHA

**Точное требование мастер-плана:** «Сохранить результаты stage/holdout и полный source/index SHA.»

## Что делается

1. Не меняя мастер-план, принимаем исходную точку `M-0141 / 139/615` только по приватному ledger и receipt с фиксированными SHA-256.
2. Читаем исходный, **уже созданный и принятый** отчёт `M0131_HOLDOUT_QUALITY_REPORT.json` из его фактического `evidence_receipt` в приватном журнале. Его SHA-256 фиксируется, а оригинал включается в результат.
3. Сохраняем две группы входной выборки из того же отчёта: **stage** — первые 18 утверждённых точных sanity-запросов, **semantic pilot («holdout» в историческом названии)** — следующие 18 утверждённых семантических запросов. Для каждого варианта ранжирования сохраняются исходные per-query оценки, без пересчёта неизвестных результатов.
4. Фиксируем полные SHA-256 каждого файла исходников внутри **явно перечисленных** каталогов `src/lib/ontology-research`, `src/app/api/value-objects/indexed-lookup`, `scripts/ari` и тестов `scripts/tests/ari03-*.test.cjs`; вычисляем сортированные составные SHA исходного дерева и индексных исходников.
5. Сверяем сохранённые M-0140 (4 точных сценария сна) и M-0141 (5 тем отрицательных совпадений). Проверяем отсутствие новых **офлайн-блокеров относительно ранее утверждённых ограниченных контролей**.
6. Выполняем предшествующую регрессию 2778 тестов и 50 новых структурно-отрицательных тестов. Проверяем TypeScript strict. Создаём evidence/receipt/manifest и только тогда обновляем приватный ledger до `140/615`.

## Ограничения, которые не разрешено скрывать

- Результаты M-0131 не являются независимым / blind holdout, поскольку метки утверждены владельцем. Названия stage/holdout здесь обозначают **две группы уже существующих тестов**, а не новый разделённый до эксперимента корпус.
- Полнота SHA касается **перечисленных локальных исходников и кода индексов**. Реальный физический индекс PostgreSQL/pgvector не читается; его SHA **неизвестен**, не нуль.
- Нельзя распространять 18/36 тестовых случаев на полный каталог ОН или считать проверенной приватность RLS и HTTP E2E.
- Если оригинальный M0131 report отсутствует, неверен или менялся — пакет останавливается и формирует диагностический ZIP, **без приёмки**.
- Никаких платных API, OpenAI, SQL, Supabase, commit, push или deploy. Новые ОН не создаются.

**Фактически применяемый gate:** `ACCEPTED_LIMITED_ARCHIVAL_NOT_INDEPENDENT_HOLDOUT_OR_LIVE_DB_INDEX`. Следующий шаг — M-0143: сравнение latency и стоимости с явным UNKNOWN для отсутствующих данных.

## HOTFIX: реальный порядок Gold M-0121

Первая группа содержит 18 проверенных запросов. 18-й — англоязычная вариация `walking`, `realon-variation-13`, привязанная к тому же утверждённому UUID ходьбы. Правило «все ID начинаются с `realon-exact-`» было ошибочным и вызвало диагностический STOP. Новая проверка привязана к оригинальному Gold-файлу M-0121 с неизменёнными case ID, locale и целевым UUID.
