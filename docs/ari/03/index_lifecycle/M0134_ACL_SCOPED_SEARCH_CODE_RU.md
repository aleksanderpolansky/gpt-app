# ARCTor / M-0134 / ARI-03.07.03 — ACL частных ОН в поиске

**Точное требование реестра:** «Проверить ACL: private ON другого актора не попадает ни в suggestions, ни в embeddings.» Режим микрошaга: CODE. Сначала исполняется программная проверка контракта доступа; реальные Supabase GRANT/RLS и production E2E остаются запланированными отдельными этапами.

## Реализация

Расширен `src/lib/ontology-research/indexLifecycleV1.ts` без изменения функций M-0132 и M-0133. Добавлен контракт `ARCTOR_ARI03_SEARCH_ACL_V1`:

- `prepareScopedIndexReadV1(authenticatedActorId, indexes)` — до поискового обращения выбирает только актуальные (`fresh`) индексы с типом `global_system` либо `owner_private` для **проверенного пользователя**. Не возвращает идентификаторы чужих private-индексов.
- `validateScopedSearchHitsV1(authenticatedActorId, indexes, rawHits)` — после поиска дополнительно проверяет источник каждого результата, поколение, SHA-256 и формат. Отклоняет весь ответ при попадании чужого, неизвестного либо устаревшего индекса, запрещает сырые векторы в результатах.
- Анонимный пользователь допускается только к глобальным индексам. При ошибках модели доступа, отсутствующих метаданных и некорректных хитах действует `fail-closed`.
- Сортировка ранжировщика M-0125—M-0131, схема индекса и состояния M-0132/M-0133 остаются без изменений.

**Важно:** `authenticatedActorId` должен приходить исключительно из проверенной серверной сессии Auth0/привязанного внутреннего идентификатора пользователя, НЕ из параметров клиента, заявки ИИ или локального хранилища. Поле SQL `usage_scope` не используется как самостоятельный признак глобальности; структурная идентичность глобального системного ОН определяется серверным реестром. Выполнение этой программной проверки не заменяет RLS на уровне БД.

## Ограничение результатов

Исполнение этих функций само по себе **не подключает API поиска к реальному Supabase**. До построения SQL RPC и включения live vector path необходимо обеспечить такой же контроль в запросе к БД / индексу и проверить изоляцию двумя настоящими пользовательскими сессиями. В документации шага эта часть обозначена как `databaseRlsVerified:false`, `aclEndToEndVerified:false`. Это не блокирует приёмку M-0134 по режиму CODE, поскольку фактическая проверка GRANT/RLS предусмотрена M-0137, а production E2E — позднее.

## Приёмка

Ожидается 2066 предыдущих тестов и 117 новых = **2183 PASS**, строгая компиляция TypeScript, демонстрация разделения индексов между двумя пользователями и анонимным гостем, ноль SQL/платных API/деплоя. Установщик проверяет SHA журналов и квитанции, делает резервную копию прежнего модуля, обновляет **ровно M-0134**, записывает доказательства и новый SHA. При любой ошибке возвращает прежнее состояние.
