# ARCTor — M-0135 / ARI-03.07.04: Replay pending updates после сбоя indexing job

**Оригинальная задача мастер-плана:** «Подготовить реплей pending updates при сбое indexing job».
**Режим:** CODE; интеграция с Supabase / индексирующим воркером на этом шаге не выполняется.

## Программный контракт

В `src/lib/ontology-research/indexLifecycleV1.ts` добавлена `planPendingIndexReplayV1(record, updates, options)`.

Она принимает только корректный снимок индекса в состоянии `failed` или `stale` и очередь ожидающих обновлений, привязанную к одному index_id и одному scope (глобальный системный или частный конкретного актора). Строит детерминированный, ограниченный `maxBatch` план повторной обработки. Каждый элемент содержит UUID ОН, локаль, операцию UPSERT/DELETE, sequence, хеш содержимого (не сам текст), число попыток, update_id и стабильный `replay_key` для будущей идемпотентной обработки.

### Правила восстановления

1. **Чужой владелец или другой индекс — запрет всего плана.** Смешанную очередь нельзя фильтровать «как получится».
2. **Самая новая запись для каждой пары (ОН, локаль) побеждает.** Более старые операции не воспроизводятся, даже если новейшая уже применена или является удалением.
3. **Изменившийся source_hash** не воспроизводится автоматически; нужна ручная сверка.
4. **`in_flight`** возвращается в план только при документально зафиксированном `failed`. Для состояния `stale` неизвестное выполнение не предполагается завершённым.
5. **`applied`, `dead_letter`, исчерпанные попытки** исключаются; неоднозначный одинаковый `sequence` на одной паре (ОН, локаль) блокирует весь план.
6. Функция **ничего не записывает**, не запускает задачу, не создаёт embeddings, не выполняет SQL и не предоставляет оплачиваемых разрешений. Поля `requiresExplicitJobApproval=true`, `executorMustRevalidateSourceAndGeneration=true`, `fallback=lexical_only` обязательно присутствуют в результате.
7. Идентичность будущего построения содержит желаемый `source_hash` и `proposed_generation`. На исполнителе, который будет реализован позднее, это нужно заново подтвердить по БД перед фиксацией результата.

### Проверки

105 новых локальных тестов, в том числе на семи локалях, разные статусы очереди, тайм-ауты/лимиты попыток, порядок, идемпотентность, изоляцию владельцев и отсутствие побочных действий. Приёмщик M-0135 выполняет также 2183 принятых ранее регрессионных теста (итого 2288).

### Не входит в этот микрошаг

Создание реальной очереди в Supabase, публикация индекса, запуск jobs, автозакупка API, RLS в БД, подключение API и E2E. Они не считаются завершёнными на M-0135. На M-0136 по плану — timeout/circuit-breaker/fallback на lexical read-only.
