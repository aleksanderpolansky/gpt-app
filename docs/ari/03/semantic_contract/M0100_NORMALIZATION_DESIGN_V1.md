# M-0100 · ARI-03.02.04 — Unicode, ё/е и диакритика (DESIGN ONLY)

## Назначение и неизменные границы
Закрепить консервативные правила поиска по тексту ОН без смешения идентичностей. Продолжение принятых контрактов M-0097 QueryRequest, M-0098 SearchResult, M-0099 exact UUID/suggest dispatch, и снимка M-0096. Документ и автономный эталонный валидатор не являются реализацией production-поиска. Индекс выключен; indexableApproved=0; tenant/ACL E2E не подтверждён.

## Два уровня нормализации
**Strict text key** для текстового совпадения: валидация Unicode scalar, NFC, удаление пробелов в начале/конце, сведение Unicode-пробелов внутри к одному обычному пробелу, locale-aware lower-case для заданной локали; ключ обязательно включает локаль (`ru::...`, `pl::...`). Никакого снятия диакритики, смешения `ё/е`, удаления знаков пунктуации, транслитерации, фонетического сглаживания, compatibility NFKC (может изменять смысл), замены конфузаблов, замены цифр или конверсии между языками. Это ключ сравнения текста, **не** идентификатор объекта.

**Recall-only candidates**: только для явно указанной локали из `en/pl/es/de/cs/ru` возможно получить дополнительный нормализованный ключ со снятыми Unicode combining marks (NFD→strip M→NFC), а для `ru` дополнительно `ё→е`; если не отличается, не генерировать. Такое совпадение имеет отдельную метку `soft_fold`, требует подтверждения на оригинальной форме и НЕ превращается в `exact`, UUID или approved alias. Для `uk` и `und` расслабление не применяется (консервативно); отсутствующий/неизвестный язык никогда не приписывается английскому. `ł` / `l`, `ß` / `ss`, знаки пунктуации, `C++` / `C` не объединяются.

**Коллизии и омонимы:** «лук» (овощ / оружие), «ёлка» / «елка» и «schön» / «schon» могут совпасть строго или на этапе soft-fold. Даже если strict key одинаковый, все разные ON UUID должны оставаться отдельными кандидатами. `single_candidate` не значит автоматически выбранный ОН; `ambiguous` требует candidates + clarificationQuestion, `selectedObjectId=null` до явного решения и проверки серверного доступа. Exact UUID lookup вообще НЕ выполняет текстовую нормализацию и НЕ делает fallback.

## Границы ввода и приватность
Поддерживаемые локали: en, pl, es, de, cs, uk, ru, und. Не более 512 Unicode code points, 2048 UTF-8 bytes; запрещены невалидные суррогаты, управляющие символы кроме пробельных, bidirectional override и format/zero-width control. Не склеивать разные скрипты «похожими» буквами. Не использовать клиентский `actorScope` как доказательство доступа. Применять server identity + ACL/RLS, актуальность снимка и допустимость источника перед выдачей кандидата. Ошибки внешнего API не должны раскрывать частные названия.

## Проверки и нерешённые вопросы
Эталонные позитивные примеры: NFC composed/decomposed, locale lower-case, пробелы, ru ё/е как **два strict ключа и один мягкий ключ**, es canción/cancion, de schön/schon, ru омонимы «лук», pl ł/l не объединяются, разные языки не объединяются, апострофы и пунктуация сохраняются, украинский и `und` не получают soft-fold. Негативные: неизвестная локаль, непарный суррогат, format/control, пустая строка, превышение длины, ошибочный `mode`, лишние поля, попытки ownerId, autoSelect и текстовое fallback от UUID.

Отложено в M-0101: приоритет полного выражения над отдельными токенами; в M-0102: controlled ancestor expansion. Остаются открытыми 89 алиасов с ненайденными целями, две группы возможных дублей коммерческих корней, непроверенные RLS E2E и translation identity join. Никаких SQL, production `src/`, commit/push/deploy и index activation.
