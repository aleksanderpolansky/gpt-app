# M-0123 / ARI-03.05.06 — сравнение exact и ANN/HNSW на реальных векторах (ограниченный DESIGN-пилот)

**Задача мастер-плана:** «Сравнить точность exact vs ANN/HNSW и индексные настройки на реальных данных». Режим DESIGN; это **не** внедрение `pgvector` и не разрешение на production.

## Исходные условия

- На M-0121 владелец утвердил 36 тестовых запросов для 18 глобальных системных ОН; 30 запросов RU и по одному в шести других языках.
- На M-0121 обе модели реально построили embeddings; локальные ответные векторы сохранены в приватном рабочем каталоге на Windows; в ZIP они **не включаются**.
- M-0122 зафиксировал детерминированный кеш. `pgvector` в Supabase ещё **не установлен** по read-only-инвентаризации M-0118. Поэтому невозможно честно заявить, будто производительный HNSW-индекс PostgreSQL уже создан или проверен.
- На столь малом наборе (18 элементов) точный поиск крайне дёшев. Набор недостаточен для утверждений о скорости и качестве при тысячах/миллионах ОН. Нет независимого Gold/RLS-E2E подтверждения.

## Методика

Вне Supabase, на тех же реальных локальных векторах двух моделей:

1. Проверить прежние квитанции, исходный Gold hash, SHA-256 локальных ответов, размерности 1536/3072 и эталонные метрики exact M-0121.
2. Запустить exact cosine ranking по всем 18 ОН (полный перебор) с детерминированной сортировкой и 36 запросами.
3. Построить **локальный многоуровневый HNSW-подобный граф** в JavaScript (фиксированный seed, косинусная дистанция, жадная навигация по уровням, efConstruction/efSearch, ограниченные списки соседей) и прогнать шесть конфигураций: M=4/8, efConstruction=16/32, efSearch=5/10/18.
4. Сравнить ANN/exact top-1, пересечение top-5, Gold Recall@1/@5, число вычислений расстояния, затраты на создание графа и время поиска. Не смешивать Recall against Gold с fidelity against exact. Привести отклонения каждого варианта, включая ухудшения.
5. Доказательства: агрегаты по двум моделям и по конфигурациям, исходные SHA-256, статус ограниченного DESIGN. Исходные embedding-векторы, ключ API и тексты запросов не попадут в ZIP.

## Чего мы НЕ проверяем

- Реальную производительность расширения pgvector (`CREATE INDEX ... USING hnsw`), SQL planner, фильтры по scope и RLS.
- p95/p99 на production, index size и качество при нескольких тысячах ОН.
- Независимую научную репрезентативность Gold, мультиязычную статистическую устойчивость и гипотезу «ANN быстрее exact».
- Автоматический выбор модели для production или включение indexed/vector API.

## Дальнейшая миграция / решение, но только с отдельным одобрением

Перед тестом PostgreSQL следует отдельно согласовать: расширение vector, схему отдельной таблицы embeddings, RLS, корректную размерность и ops-класс `vector_cosine_ops`, индекс `USING hnsw (embedding vector_cosine_ops) WITH (m = ..., ef_construction = ...)`, `hnsw.ef_search` в рамках транзакции и exact baseline без использования ANN-индекса. Это пока **проектный список**, а не запускаемый SQL.

Порог принятия M-0123: сравнение на **подлинных локальных** векторах, совпадение повторного exact с M-0121, не менее двух значений параметров индекса, сохранение всех провалов/расхождений и явное подтверждение ограниченной приёмки владельцем. При отсутствии файлов остановиться; ни SQL, ни сетевых запросов, ни платного пересчёта.
