# ARCTor — M-0189 / ARI-04.06.03: Temporal validity contradictions (CODE LOCAL)

**Мастер-план:** «Добавить обнаружение несогласованности временных диапазонов valid_from/valid_to».

## Граница

Этот микрошаг вводит проверку утверждений об отношениях в чистом детерминированном TypeScript-модуле `src/lib/ontology/contradictionDetectorV1.ts`. Это **локальный CODE**, не миграция SQL и не подключение API. Он изменяет один ранее принятый исходный файл M-0187 после точной проверки его контрольной суммы. Исходная принятая копия M-0187 в `0187_EVIDENCE_ATTACHMENTS/` и квитанции **не изменяются**; перед локальной заменой создаётся резервная копия.

## Контракт интервала

- Дополнительные необязательные поля утверждения: `valid_from` и `valid_to` (PostgreSQL `timestamptz`-подобный текст, ISO 8601 / RFC 3339 с обязательным `Z` или явным числовым смещением).
- Допускаются 0–6 знаков дробной части секунды; микросекундная точность сравнения реализована целыми `bigint`, без округления через JS Number.
- Интервал трактуется как **включающий обе границы** `[valid_from, valid_to]`. Это соответствует существующим ограничениям схемы `valid_to >= valid_from` для некоторых объектов ARCTor. Любое последующее решение применять полуоткрытые интервалы требует отдельного утверждения и миграционного согласования.
- `null`/отсутствие границы **не означает проверенную бессрочную истину**; означает отсутствие ограничивающей границы в доступной модели. Важное ограничение: разные БД-сущности могут иметь другой temporal contract, который нужно явно согласовать до runtime.
- `valid_from > valid_to`, некорректная календарная дата, локальный timestamp без часового пояса, недопустимое смещение, неверная доля секунды — `INVALID_TEMPORAL_RANGE` / `BLOCK`.
- Если два утверждения заведомо не сосуществуют во времени, из их противоположных полярностей не выводится текущий логический конфликт.
- Строгое противоречие для временно определённых утверждений требует одинакового ограниченного утверждения/контекста, подтверждения двух утверждений и **двух полных явно заданных пересекающихся интервалов**. Частичные временные границы — только `REVIEW`.
- Для старых записей, у которых **обеих временных границ нет**, сохраняется поведение M-0187 (совместимость с прежними тестами). Это legacy-политика, а не научное утверждение о бессрочности.
- Для датированных циклов `depends_on`/`classified_as` возвращается сигнал `REVIEW`, а не жёсткое доказательство цикла, пока не проверено общее пересечение временных интервалов **всего пути**.
- Интервалы влияют на семантическую совместимость утверждений; они **не означают** достоверность источника, freshness доказательств, автоматическую верификацию или разрешение на запись.

## Контроль сохранности

Установщик проверяет предшествующие M-0187 и M-0188, их замороженные квитанции, SHA-256 кода, Git baseline, приватные ledger/checkpoint и SEC-06. `--dry-run` не создаёт и не изменяет файлов. `--apply --owner-approve` изменяет **только** `contradictionDetectorV1.ts`, добавляет `ontologyTemporalValidityV1.test.mjs`, этот документ и создаёт приватную резервную копию старого кода. Статус M-0189 остаётся `CODE/PENDING` до отдельной формальной приёмки.

## Проверки

- 72 синтетических временных сценария, 44 независимых инварианта;
- совместимость M-0187: 72 сценария и 34 инварианта;
- неизменность M-0188: 72 сценария и 40 инвариантов;
- TypeScript `strict` / ES2020, без DB/API/network/graph writes.

## Отложено

Не выполнены production API интеграция, live schema/relation writes, динамические отрицательные тесты. `SEC-06 OPEN_BLOCKER`, релиз `BLOCKED`. Следующий шаг — M-0190 только после приёмки M-0189.
