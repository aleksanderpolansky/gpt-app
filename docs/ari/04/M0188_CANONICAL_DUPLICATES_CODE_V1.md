Это companion-модуль к принятому `contradictionDetectorV1.ts` (M-0187). Принятый файл M-0187 не переписывается; он остаётся зафиксированным в квитанции и приложениях M-0187.

## Смысл

Нормализуем `(relation_type_code, source_value_object_id, target_value_object_id)` по **проверенному реестру** типов отношений, а не по догадкам LLM:

- `same`: сохраняем порядок A→B;
- `reverse`: меняем местами A и B и используем `canonical_relation_type_code`;
- `symmetric`: упорядочиваем пару устойчиво и используем канонический тип.

Исторические примеры из действующих SQL-миграций P3:

- `prerequisite_for(A,B)` → `depends_on(B,A)`;
- `influenced_by(A,B)` → `influences(B,A)`;
- `related_to(A,B)` = `related_to(B,A)`.

**Важно:** в реальной БД реестр может отличаться от миграции. Входные метаданные всегда нужно получать из текущей авторизованной версии; никаких запросов к БД модуль не выполняет.

## Политика вывода

- Текущий идентичный канонический edge с совпадающим/отсутствующим с обеих сторон контекстом → `BLOCKED` для создания второй строки.
- Явно разные контексты или контекст указан только для одной стороны → `REVIEW_REQUIRED`.
- `rejected`/`inactive` совпадение → `REVIEW_REQUIRED`, без автоматической повторной активации.
- Разное направление **направленного** типа не является дубликатом.
- Отсутствующая/двусмысленная канонизация, неверные статусы или превышенные лимиты → fail closed.
- Дубликат не равнозначен семантическому противоречию и не доказывает истинность источника.
