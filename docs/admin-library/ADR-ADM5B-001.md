# ARCTor — ADR-ADM5B-001: серверный предпросмотр контекста по поручению ADM-4

**Дата:** 17.10.2026. **Версия:** 2026-10-17.v1. **Статус:** proposed. **Использование агентами:** false. **Режим:** только чтение, проектирование.

## Цель

Реализовать первый проверяемый шаг ADM-5B: показывать администратору точный состав будущего контекста специализированного ИИ-исполнителя **по существующему делу и конкретному поручению ADM-4**, не создавая нового реестра дел. Контекст не отправляется модели; разрешение на запуск отсутствует независимо от состояния базы и результатов проверки.

## Подтверждённая основа

Роли ADM-2B2: `process`, `product`, `semantic`, `ai`, `engineering`, `quality`, `commercial`, `support`. Поручение хранится в `arctor_admin_assignments_adm2_v1` и связано с делом по `case_id`, ролью `recipient_role_code`. Существующие человеческие поручения не затрагиваются. Каталог `taskCode` берётся только из проектного ADM-5A.2; браузер не выбирает произвольные роли.

## Серверная последовательность

1. Проверить платформенного администратора `owner`/`admin`. Не использовать пользовательскую авторизацию без проверки административной роли.
2. Валидировать `caseCode` и `assignmentId` на сервере. Получить ровно одно дело; получить поручения только этого дела, с ограничением выборки. Подтвердить, что поручение действительно относится к выбранному делу и его должности.
3. Получить действительное состояние должности из Supabase. Проверить соответствие роли разрешённому списку для `taskCode` по ADM-5A.2. Флаг `agent_execution_enabled` не изменять. Если он внезапно включён, выдать причину риска для человеческого маршрута.
4. В ADM-5B.1 допустим только публичный коммерческий первоисточник (`commercial_activity_event`). Проверить связь с `activity_events`, затем с **действующим публичным** `message_objects`. Текст активности считается доказанным для предпросмотра лишь при буквальном вхождении в разрешённое текстовое поле этой публикации. При отсутствии доказательства текст не включать, статус `SOURCE_TEXT_NOT_PROVEN`.
5. Выбрать документы, относящиеся одновременно к данной роли и задаче. Версии `proposed` или `retired`, `agentEnabled=false`, неверный SHA-256 или пустой `agentBrief` не включать. Все исключения показывать отдельно. Кандидат без подтверждения никогда не превращается в готовую инструкцию.
6. Составить поименованные секции: дело, поручение, подтверждённый фрагмент публичного сообщения, краткие утверждённые инструкции. У каждой секции есть тип и исходный ID. Зафиксировать объём символов и ориентировочный **диапазон** токенов; это не биллинговая сумма. Не молча обрезать слишком большой контекст: фиксировать блокировку.
7. Вывести понятные причины и следующие действия. При любой ошибке чтения не предполагать, что данные существуют или их нет; указать `READ_FAILED`. Не писать в БД и не вызывать модели.

## Границы безопасности

`agentContextApproved=false`, `agentExecutionPermitted=false`, `dbWritesPerformed=false`, `modelCallsPerformed=false` инвариантны. Никаких вызовов OpenAI, фонового агента, автоматического согласования, обновления статусов, SQL или публикации. Доступ к предпросмотру ограничен `owner`/`admin`; таблицы читаются серверным клиентом. Никакие поля `user_id`, `email`, приватные сигналы и прочие метаданные исходной публикации не возвращаются браузеру.

Присутствие подтверждённого публичного сообщения не означает разрешения на отправку всех полей публикации во внешнюю модель. Обработка персональных данных, длинных записей, приватных источников, сертификатов и сторонних доменных объектов не входит в ADM-5B.1. Они требуют отдельной политики и расширения списка безопасных источников.

## Работа администратора

Страница `/admin/agent-context`: выбор дела по коду, загрузка поручений из настоящей БД, выбор конкретного `assignmentId`, выбор одного из семи типов задач ADM-5A.2, чтение предпросмотра, просмотр исключённых документов, причин, проверенного источника и объёма. Отдельный read-only маршрут `/api/admin/management/agent-context` возвращает такую же машинно-структурированную диагностическую картину. Без отправки пользователем запросов на изменение данных.

Контрольный сценарий: `ADM-000001`, поручение инженерного направления, `taskCode=commercial_fact_preflight`, источник `87ee8565`. Ожидается подтверждённое публичное сообщение, **0 допущенных инструкций**, блокировка запуска и отчёт о причинах. История предыдущих событий не копируется в состав контекста целиком.

## Следующие этапы

- ADM-5B.2: контракт классификации и отбора источников, утверждение версий документов, ограничения общего объёма, точный манифест контекста и политика исходящих данных.
- ADM-5B.3/5B.4: модель, приблизительные токены, AI Billing, назначение стоимости и бюджет; сделать только после принятия договоров хранения.
- ADM-5C/D: отдельный журнал попыток, контролируемый запуск и согласование человеком, разрешение конкретных действий; устранение конфликта `agent_execution_enabled` отдельной ручной SQL-миграцией до включения любого агента.
- ADM-5E: отрицательные, конкурентные, privacy, idempotency и регрессионные тесты; отдельное согласование публикации.

**Критерий приёмки ADM-5B.1:** администратор получает доказательный предпросмотр существующего поручения с исключениями и человеческими объяснениями без каких-либо записей и вызовов ИИ. Успешный предпросмотр не означает готовности к исполнению.
