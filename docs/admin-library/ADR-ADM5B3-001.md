# ARCTor — ADR-ADM5B3-001: неизменяемые снимки контекста и внутреннее согласование

Дата: 2026-10-17. Версия: 2026-10-17.v1. Статус: **proposed**, для агентов **agentEnabled=false**.

## Цель

Не создавать вторую систему дел. Сохранить доказуемую версию контекста для конкретного поручения ADM-4 и историю ручной проверки. Ни один снимок не разрешает передачу ИИ, запуск модели, изменение фактов или существующих поручений.

## Граница ADM-5B.3

ADM-5B.1 получает текущее дело, поручение, подтверждённый публичный фрагмент и относящиеся документы. ADM-5B.2 строит детерминированный манифест SHA-256. ADM-5B.3 сохраняет его вместе с **точными текстами трёх и более исходных фрагментов**, а также проверяет актуальность при повторном чтении перед решением администратора.

Каждый снимок содержит: `case_id`, `assignment_id`, `role_code`, `task_code`, `version_num`, `manifest_digest`, `snapshot_digest`, сериализованные разделы, создателя и момент создания. Дела и поручения живут в существующих ADM-4 таблицах. Снимки не содержат ключей API и закрытых личных сырых активностей. Только проверенный публичный источник: `verified_exact_public_text`.

## Жизненный цикл

- `captured`: снимок создан и неизменяем; его наличие не означает проверку или одобрение.
- `reviewed_internal`: администратор осмотрел снимок и подтвердил его внутреннюю пригодность; **outboundAuthorized=false**.
- `rejected`: сохранена причина отклонения, оригинал не стирается.
- `stale` — **вычисляемое**, не сохраняемое состояние: текущий манифест отличается от сохранённого; предыдущий `reviewed_internal` больше не свидетельствует об актуальности, повторная проверка требует нового снимка.

К одному снимку допустимо только одно финальное решение (`reviewed_internal` или `rejected`). Попытка обновить или удалить оригинальные записи и события блокируется триггерами и правами БД. Повторный запрос с тем же `operation_id` должен быть идемпотентным; конфликтующие данные приводят к отказу.

## Проверка актуальности

Перед записью **и** ручной проверкой сервер заново загружает исходные данные из Supabase, повторно компилирует ADM-5B.1 и ADM-5B.2 и сравнивает исходный `digestSha256` с сохранённым. SHA-256 говорит о совпадении содержания при выбранной канонизации, а не о достоверности источника и не является электронной подписью. Содержимое исходных данных может измениться после проверки: поэтому при любом будущем использовании необходима свежая контрольная проверка.

`captured` и `reviewed_internal` НЕ отменяют препятствия `NO_APPROVED_INSTRUCTIONS`, `OUTBOUND_POLICY_NOT_APPROVED`, `RUNTIME_NOT_IMPLEMENTED`, а также конфликт `agent_execution_enabled` в ADM-2B.2. Здесь нет функции вида `approve_for_external_ai`.

## Безопасность

Пользовательские браузерные роли `anon` и `authenticated` не имеют `SELECT`, `INSERT`, `UPDATE` на новых таблицах или `EXECUTE` новых RPC. SQL использует `SECURITY INVOKER` и разрешает RPC только `service_role`. Действующий владелец/admin проверяется сервером и повторно в RPC по `app_user_id`.

Веб-маршрут ограничен `POST` + точный same-origin, тип JSON, малый лимит запроса, случайный `operation_id` и точные идентификаторы. Состав снимка не принимается от браузера — он собирается на сервере. Исходные тексты и аудит показываются только в защищённом административном кабинете. Браузер не получает Supabase service key.

Для подписания, подписанных политик передачи, разграничения confidential/private, retention/удаления по требованиям законодательства и OpenAI runtime нужны отдельные контракты ADM-5B.4/5C/5D. Нельзя пользоваться текущим механизмом для приватных данных пользователя.

## Ручной порядок внедрения

1. Установить локальный код и проверить ESLint, TypeScript, Next build. Автоматический запуск миграций запрещён.
2. В Supabase SQL Editor выполнить `01_PRECHECK_READ_ONLY.sql`, получить `PASS_READY_FOR_MANUAL_SQL`.
3. Отдельно изучить и вручную выполнить `02_APPLY_MANUAL.sql`; автоматически SQL не исполняется.
4. Выполнить `03_POSTCHECK_READ_ONLY.sql`, получить PASS. Только после этого разрешены локальные действия «Сохранить» и «Подтвердить внутреннюю проверку».
5. Контрольное дело `ADM-000001`, поручение `e6036022-146e-4eca-bacf-3af379858f92`, тип `commercial_fact_preflight`: проверить сохранение, повторное сохранение без дублей, решение, неизменяемую историю и stale при изменении входного контекста на тестовом стенде. Не менять реальную публикацию только ради теста.
6. При необходимости исправления ошибок — сперва анализ результатов; повторно не применять миграцию вслепую.

## Приёмочные критерии

Нельзя напрямую читать/писать в новые таблицы через браузерный Supabase клиент. Снимок сохраняется с актуальными источниками и неизменным SHA; версия является отдельным объектом и связана с настоящим делом. Одно администраторское решение фиксируется без возможности изменения. При изменении источника UI выводит «устарел» и не разрешает подтверждать старую версию. Не происходит вызовов OpenAI, выполнения ИИ-агентов, записи фактов, изменения флага `agent_execution_enabled` или автоматических commit/push.
