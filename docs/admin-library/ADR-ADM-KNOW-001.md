# ARCTor — ADR-ADM-KNOW-001: библиотека администратора и рабочий контекст ИИ

Дата: 16.10.2026. Статус: проектное решение для поэтапного внедрения.

## Цель

Документы должны быть доступны на месте выполнения работы: в административной карточке, в кабинете конкретной должности, в справочнике и, когда это отдельно разрешено, в контексте узкоспециализированного ИИ-исполнителя. Запрещены дублирующие и расходящиеся версии одного правила.

## Существующие точки интеграции

- `/project-knowledge` — защищённый обзор процессов, решений, рисков и источников. Библиотека добавляется как подраздел этого контура.
- `/admin/ai-instructions` — уже существующий реестр инструкций и правил ИИ, версия и порядок приоритета. Библиотека не заменяет его и не должна обходить встроенные ограничения.
- ADM-2B.2 — реальные дела, поручения и неизменяемая история действий.
- ADM-4 — происхождение источника, связь с делом, диагностика.
- ADM-5 — ограниченные должностные ИИ-исполнители; включение в модель только после отдельной приёмки.

## Минимальная карточка документа

Неизменяемый ID, заголовок, версия, дата, ответственная должность, тема, назначение, источники/доказательства, область применения (`taskCode` и `roleCode`), статус утверждения, допустимый доступ, краткая машинная инструкция, полное объяснение для человека, журнал пересмотра и контрольный пример. При изменении содержания увеличивать версию, не заменять бесследно прошлую.

## Приоритеты и безопасность

1. Кодовые ограничения и разрешения сервера — не переопределяются документом.
2. Детерминированные правила обработки и утверждённые системные инструкции — по действующему механизму `/admin/ai-instructions`.
3. Дополнительный рабочий документ — применяется только когда верен taskCode, роль, статус и версия; никогда не повышает привилегии.
4. Тексты активностей и сторонние документы — входные данные, а не исполняемые системные команды.

Краткое содержимое документа не должно содержать личные данные клиентов. Для личной задачи требуются отдельные разрешения владельца. Запрещено помещать секреты и API-ключи в библиотеку.

## Как уменьшать количество токенов

Сервер выбирает только актуальные для поручения документы, а для модели обычно передаёт краткие проверенные инструкции. Полный документ загружается по требованию объяснения или исследования. Для одной задачи нужно ограничить число документов и суммарный бюджет входного текста. Повторно используемый неизменный префикс может кэшироваться только при реальной поддержке провайдера. Само наличие библиотеки не снижает число токенов автоматически.

## Управляемый набор решений

В схеме задания использовать закрытые коды: `taskCode`, `attempted`, `searchMethod`, `coverage`, `resultCode`, `reasonCertainty` (`confirmed` / `probable` / `unknown`), `nextActions`, `evidenceRefs` и `instructionVersion`. Для недостаточных сведений всегда оставлять допустимый вариант `unknown / escalate`, а не вынуждать модель придумать один из имеющихся вариантов.

## Порядок внедрения

**ADM-4K1 (сейчас):** защищённая библиотека только для чтения, привязка объясняющего документа к диагностике P2.5. Хранение в контролируемых файлах приложения. ИИ не получает документы автоматически. Отдельная локальная проверка, затем ручное подтверждение публикации.

**ADM-5K2:** инвентаризация действующих инструкций и документов, назначение ответственных, статусов утверждения и правил применимости. Версионируемое долговременное хранилище при необходимости, без дублирования `ai-processing` и `/project-knowledge`.

**ADM-5K3:** серверный подбор краткого контекста по роли и задаче, защита прав, список включённых версий в журнале, оценка стоимости токенов и качества решений. Запуск только с подтверждения администратора.

**ADM-5K4:** интерфейс редактирования, согласования, архивирования и проверки конфликтов с системными правилами; обязательная регрессионная проверка эталонных кейсов.

## Критерии приёмки

Человек из контекстной карточки находит относящуюся к ней инструкцию; версия и статус видны; доступ неавторизованным закрыт; устаревший документ помечен; агент не получает неподтверждённый документ, не повышает свои полномочия и фиксирует перечень реально применённых версий. Экономию токенов проверять измерением входных/выходных токенов и стоимости, а не предположением.
