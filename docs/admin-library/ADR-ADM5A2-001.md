# ARCTor — ADR-ADM5A2-001: управление допуском и состояниями должностных ИИ-исполнителей

**Дата:** 17.10.2026. **Версия:** 2026-10-17.v1. **Статус:** proposed (не утверждён). **Использование агентами:** agentEnabled=false. **Действие:** проектирование, только чтение.

## 1. Цель

Не создавать второй реестр дел. Сохранить дела/поручения/историю ADM-2B2/ADM-4; отдельно проектировать жизненный цикл *попытки* ИИ. Организационная роль, реальный исполнитель и право запуска — три независимых измерения. Ничто в этом документе не даёт разрешения исполнять SQL, изменять объекты ARCTor, выполнять push или вызывать OpenAI API.

## 2. Проверенные исходные ограничения

В интейке ADM-5A `arctor_admin_roles_adm2_v1` хранит восемь ролей (`process`, `product`, `semantic`, `ai`, `engineering`, `quality`, `commercial`, `support`) и булев флаг `agent_execution_enabled`; для всех восьми на локальной панели показан выключенный флаг. `arctor_admin_assignments_adm2_v1` поддерживает `recipient_app_user_id` и `recipient_agent_code` как взаимоисключающие поля. Назначение поручения не есть разрешение на ИИ-вызов. `arctor_admin_case_events_adm2_v1` — существующий append-only журнал, с ограничением `details_json` по размеру; полный промпт и ответ ИИ нельзя туда бесконтрольно помещать.

**Блокирующий риск:** установленный `arctor_admin_apply_case_action_adm2b2_v1` при `create|assign|handoff` разрешает роль при `is_active AND NOT agent_execution_enabled`. Если переключить флаг, обычная человеческая маршрутизация может перестать работать. Флаг не менять до отдельного согласованного DDL/SQL и регрессии, проверяющей обычные человеческие поручения. Данный этап не содержит миграции.

## 3. Разделение прав

`inspect` — просмотр администратором; `read_approved_context` — получение строго утверждённого и минимального рабочего контекста; `prepare_report` — подготовка результатов; `request_approval` — предложение на утверждение; `execute_approved_action` — только конкретное разрешённое действие с аудитом. **В ADM-5A.2 реализован исключительно `inspect` для авторизованного администратора; все прочие права — проектные.**

Набор разрешений будущего исполнения вычисляет сервер, а не модель и не браузер. `roleCode` и `taskCode` задают применимость, но не являются достаточным основанием для запуска. Исполнитель должен быть зарегистрирован, поручение должно существовать и иметь разрешённое состояние, а решение человека — содержать область, срок действия, бюджет и идентификатор операции. Неизвестная проверка → `blocked`, не `allowed`.

## 4. Код задачи и документы

ADM-5A.2 содержит **проектный** ограниченный каталог `taskCode`, соответствующий областям документов: архитектурная проверка, сборка контекста, управление исполнителями, сопоставление листовых ОН, диагностика параметров, коммерческий preflight, управление знаниями. Это ещё не действующие поручения и не утверждение качества автоматического сопоставления.

Контекст должен отбираться по точным `roleCode` + `taskCode` + утверждённой версии/хешу и признакам `approvalStatus=approved AND agentEnabled=true`, после отдельной проверки доступа к источнику. Документ `proposed` не попадает в ИИ-вызов. Утверждение документа и разрешение агенту не дают право делать изменения.

## 5. Машина состояний будущего run (не замена статусов ADM-4)

`draft → awaiting_preflight → awaiting_human_authorization → queued → running → report_ready → awaiting_human_review → approved | rejected | needs_revision`. Возможны `cancelled`, `blocked`, `failed` по допустимым переходам проектного автомата в `src/lib/admin-execution/contractV1.ts`.

Для исправления после `needs_revision` требуется новый `runId` с ссылкой на прежнюю попытку. `assignmentId` указывает на существующее поручение ADM-4; `operationId` — ключ идемпотентности конкретного действия. Сам статус `reported` не равен согласию. Отчёт ИИ не равен разрешению внести изменение.

## 6. Форма будущей аудируемой попытки

Поля для последующих ADM-5C/D: `runId`, `caseId`, `assignmentId`, `executorId`, `roleCode`, `taskCode`, `createdByAppUserId`, `operationId`, `requestHash`, `requestedCapabilities`, `readScope`, `contextManifest`, `systemInstructionVersion`, `modelId`, `costOwner`, `estimatedTokens`, `maxTokens`, `budgetLimitEur`, `estimate/actualUsage`, `state`, `statusReasonCode`, `reasonCertainty`, `startedAt`, `finishedAt`, `reportArtifactRef`, `reportSha256`, `reviewedBy`, `reviewDecision`, `approvedActionScope`, `expiresAt`, `errorCode`, `auditEventRefs`. Хранение этих полей **не реализовано**; необходимы отдельные миграция и защищённые артефакты.

## 7. Доказательные причины остановки

Различать `not_attempted`, `awaiting_human`, `insufficient_context`, `blocked_permission`, `technical_failure`, `checked_no_match` и `unknown`. Человек видит: выполненные шаги, ещё не выполнявшиеся шаги, доказанную/вероятную/неизвестную причину, следующий шаг и ответственного. UI не должен утверждать, что ИИ искал листовые ОН, если попытка не запускалась. Использовать ADR-ADM-DIAG-001.

## 8. Проверки перед будущим пилотом

1. SQL **precheck только чтение** на живой Supabase: 8 активных должностей, 0 флагов ИИ, существование таблиц и функции ADM-2B2, исходное условие выдачи поручений, структура событий и ограничения доступа.
2. Утверждённое человеком решение о пересмотре конфликтующего условия `agent_execution_enabled`, с отдельным SQL для ручного применения, предварительной и последующей проверкой; нельзя просто выключить проверку безопасности.
3. Версионированное утверждение документов, анонимный 404/401, проверка невозможности повторных записей и утечки источников.
4. Отдельный проектный компилятор контекста ADM-5B и тесты отрицательных сценариев.
5. Хранилище попыток/артефактов ADM-5C, контроль AI Billing и возможных конкурирующих запросов.
6. Ограниченный пилот одного агента с разрешением только на подготовку отчёта и обязательным human review.

## 9. Текущее решение

Все 8 должностей остаются человеческими организационными маршрутами. Ни одного включения флага агента, регистрации попыток, OpenAI-вызова, SQL-записи, commit или push в ADM-5A.2. Пакет допускает только просмотр проектных правил и проведение человеком read-only precheck. Решение об утверждении документа и внедрении следующего подэтапа принимает администратор отдельно.
