# ARCTor — канонический technical code параметров + локализованное представление

Дата: 2026-09-03
Релиз: `ARCTOR_PARAMETER_CANONICAL_CODE_LOCALIZATION_V1`
Baseline: `2747dc75674e144c607ecb2ef8f8c4a815d963c5`

## 1. Причина

После безопасной очистки активного системного каталога параметров реальный пилот `«шёл пешком на работу 15 минут»` дошёл до ручного проектирования первого универсального параметра. Принято решение отделить предмет наблюдения от универсального контракта значения: например, `Количество шагов` должно быть листовым ОН, а универсальный параметр `Количество` должен иметь канонический technical code `count`.

Текущий admin API автоматически генерировал `parameter_code` из введённого локализованного названия. При создании параметра `Количество` в RU это могло дать транслитерированный код вроде `kolichestvo`. Такой код зависел бы от языка первичного ввода и после создания уже был бы неизменяемым. Это противоречит требованию к системным каноническим кодам.

## 2. Product lock

- При создании системного параметра куратор **явно задаёт technical code один раз**.
- Technical code является platform/system canonical identifier и не зависит от языка интерфейса.
- Формат остаётся строгим: lowercase ASCII, первая буква `a-z`, далее `a-z`, цифры и `_`, общая длина 2–80 символов.
- После создания `parameter_code` остаётся неизменяемым; существующая PUT-защита сохраняется.
- API больше не транслитерирует title для генерации кода и не выбирает суффикс автоматически.
- Дубликат уже занятого system `parameter_code` отклоняется до INSERT с `409 / PARAMETER_CODE_ALREADY_EXISTS`.
- Обычный UI показывает человеческие локализованные названия, а technical code остаётся вторым техническим уровнем.

## 3. Первый канонический параметр пилота

Следующий ручной шаг после выпуска релиза — создание параметра:

- RU title: `Количество`
- canonical technical code: `count`
- dimension: `count`
- value type: `numeric`
- canonical unit: `count`
- allowed units: `count`
- aggregation: `sum`
- default window: `event`
- negative values: false

Рекомендуемое RU-описание:

`Число дискретных единиц, действий, событий или объектов; предмет подсчёта определяется связанным листовым объектом наблюдения.`

## 4. Локализованное системное представление `count`

Для canonical code `count` presentation layer получает стабильные названия независимо от title, сохранённого при создании:

- EN: Count
- PL: Liczba
- RU: Количество
- UK: Кількість
- DE: Anzahl
- ES: Cantidad
- CS: Počet

Для `count` также фиксируется локализованное описание. Это позволяет, например, создать запись из RU admin UI, но показывать пользователю EN/PL/DE/... название по его locale.

Текущая архитектура локализации system parameters остаётся code-driven: известные canonical codes получают явное системное presentation mapping. Для новых параметров translations добавляются вместе с их канонизацией, пока не будет введён отдельный versioned translation registry.

## 5. UI редактора

- В режиме создания вместо текста `Будет создан автоматически после сохранения` появляется редактируемое поле `Технический код`.
- Поле принимает canonical code и показывает локализованную подсказку о стабильности и формате.
- При редактировании уже созданного параметра technical code остаётся read-only.
- Кнопка `Сохранить` для новой записи заблокирована, пока code не соответствует формату.
- Остальные локализованные selectors (`Размерность`, `Тип значения`, `Агрегация`, `Окно`) сохраняются без изменений.

## 6. Граница данных и безопасность релиза

Релиз:

- migrations: 0;
- DDL: 0;
- database mutations: 0;
- DELETE/UPDATE/INSERT в Supabase: 0;
- OpenAI calls: 0.

Runner выполняет только read-only DB preflight:

- подтверждает, что после предыдущей очистки активных видимых system parameters нет;
- проверяет, существует ли уже canonical code `count`, и записывает результат в REPORT без мутации.

Само создание `count` выполняется только вручную администратором после проверки релиза.

## 7. Проверки релиза

До commit runner обязан:

1. подтвердить exact `main`, local HEAD, `origin/main` и remote main;
2. подтвердить blob SHA трёх изменяемых production-файлов;
3. проверить чистое рабочее дерево и `git diff --check`;
4. выполнить read-only Supabase preflight;
5. снять full ESLint baseline и touched-file baseline;
6. применить deterministic patches;
7. проверить touched ESLint без регрессии;
8. проверить full ESLint no-regression;
9. выполнить `tsc --noEmit`;
10. выполнить Next production build;
11. выполнить final `git diff --check` и allowlist changed files;
12. commit/push и подтвердить local/origin/remote SHA.

При ошибке до commit runner восстанавливает только release-owned files. После commit используется resume state; destructive `reset --hard`, `git clean` и force push не применяются.

## 8. Точка продолжения

После PASS:

1. открыть `/activity-templates?locale=ru`;
2. нажать `+ Новый параметр`;
3. создать `Количество` с technical code `count` по контракту выше;
4. проверить карточку в RU и хотя бы одном другом locale;
5. вернуться к сигналу `«шёл пешком на работу 15 минут»` и продолжить пилот с назначением/проверкой параметров и листовых ОН.

Не создавать `Количество шагов` как отдельный parameter code; это кандидат на leaf observation object, которому назначается универсальный parameter `count`.

## 9. Recovery discipline

Этот checkpoint обязателен для восстановления. Следующий значимый этап должен обновить `docs/recovery/` фактическим commit, evidence, результатом ручного создания `count`, ошибками/уроками и следующей точкой продолжения.
