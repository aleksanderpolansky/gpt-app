# ARCTOR_SOURCE_SNAPSHOT_UNASSIGNED_STATE_V1 — 2026-09-27

## Причина

После `ARCTOR_SNAPSHOT_UI_SIMPLIFY_V1` персональный факт-срез можно сохранять как
`ОН + параметр + значение + единица + время` без обязательного глобального
`value_object_parameter_assignment`.

Но `SourceSnapshotSettings` на странице создания типовой активности продолжал
читать только assignment-based `options` из `/api/activity/facts/snapshots`.
Поэтому подтверждённый срез мог существовать в `activity_object_facts`, но его ОН
не показывался как источник.

Пример:
- ОН состояния: `Текущая масса сахара на чашку кофе`;
- параметр: `mass`;
- подтверждённый snapshot: `5 gram`;
- глобального назначения `ОН ↔ mass` нет;
- старый source selector показывал только ОН с уже существующим assignment.

## Решение

Источник типовой активности задаётся семантической парой:

`листовой ОН ветви «Состояния и потребности» + выбранный системный параметр`.

Глобальное системное назначение этой пары не обязательно.

Во время выполнения используется существующий runtime-контракт:

1. найти подтверждённый `fact_role_code = snapshot`;
2. для текущих user/actor;
3. совпадают `value_object_id` и `parameter_definition_id`;
4. `effective_at <= время активности`;
5. выбрать самый поздний действующий срез;
6. применить множитель;
7. при отсутствии среза потребовать уточнение и не подставлять ноль.

## Изменения

- `src/app/activity-templates/source-snapshot-settings.tsx`
  - источник выбирается из `stateLeaves`, а не assignment-based `options`;
  - source-side system assignment больше не требуется;
  - UI объясняет фактический runtime-поиск среза.

- `src/lib/activity/source-snapshot-resolution.server.ts`
  - `validateSnapshotBindings()` проверяет только активный системный лист
    состояния и активный числовой системный параметр;
  - проверка source-side `value_object_parameter_assignments` удалена;
  - `resolveSnapshotValue()` не меняется и читает персональные snapshots из
    `activity_object_facts`.

- `scripts/validate-source-from-snapshot-v1.cjs`
  - fixture источника не имеет системного assignment;
  - существующие поведенческие тесты выполняются на этой модели.

- добавлен `scripts/validate-source-snapshot-unassigned-state-v1.mjs`.

## Не меняется

- БД и SQL;
- destination mapping типовой активности;
- глобальные assignments для target-ОН, требуемые существующим writer;
- приоритет явно сообщённого значения над snapshot fallback;
- выбор последнего подтверждённого среза на момент активности;
- fail-closed при отсутствующем/чужом/будущем/неподтверждённом срезе.

## Контрольный сценарий

1. Существует snapshot:
   `Текущая масса сахара на чашку кофе = 5 gram`, parameter `mass`.
2. Создать типовую активность `Употребление чашки кофе с сахаром`.
3. Для параметра `Масса` выбрать target `Употребление добавленного сахара`.
4. Режим: `Прямое значение → если отсутствует, рассчитать`.
5. В source selector выбрать `Текущая масса сахара на чашку кофе`.
6. Множитель `1`.
7. Публикация должна пройти без source-side assignment.
8. Активность без явно указанной массы сахара должна получить `5 gram` из snapshot.
9. Если явно указано `7 gram`, прямое значение должно иметь приоритет.

Следующий отдельный этап: динамический множитель из другого параметра активности,
например `Количество чашек × масса сахара на чашку`.
