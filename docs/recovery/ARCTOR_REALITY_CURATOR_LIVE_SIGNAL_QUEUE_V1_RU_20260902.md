# ARCTor — рабочая очередь сигналов куратора V1

Дата: 2026-09-02

## Цель

Сделать первый полностью рабочий сквозной сценарий рабочего места куратора модели.

Пользователь в правой колонке ИИ фиксирует прошедшую или будущую активность. Событие сохраняется сразу, затем существующий фоновый базовый анализ пытается найти подходящую существующую типовую активность. Если анализ завершён и подходящая типовая активность не найдена, случай должен автоматически стать видимым куратору независимо от того, остался пользователь на исходной странице или ушёл с неё.

## Решение

Новая таблица на этом этапе не создаётся. Источником истины служит уже существующий долговечный сигнал `raw_activity_signals`.

Существующий `ARCTOR_BASIC_ACTIVITY_INTAKE_ANALYSIS_V1` сохраняет результат в:

`raw_activity_signals.normalized_preview_json.basicIntakeAnalysisV1`

Рабочая очередь куратора считает сигналом пробела случай, где одновременно выполняются условия:

- `contract = ARCTOR_BASIC_ACTIVITY_INTAKE_ANALYSIS_V1`;
- `status = completed`;
- `noSuitableTypicalActivity = true`;
- `templateCandidates` пуст.

Это означает, что попадание в очередь не зависит от открытого браузера пользователя. После завершения фонового анализа долговечная запись уже существует в БД, а страница куратора читает её напрямую.

## Новый административный API

`GET /api/admin/reality-curator/signals`

Свойства:

- доступ только активным platform admin `owner/admin` через `requirePlatformAdmin()`;
- только чтение;
- читает только `manual_chat` quick-capture сигналы;
- верхняя граница сканирования — 500 последних сигналов за один запрос;
- не вызывает OpenAI;
- не создаёт, не обновляет и не удаляет записи;
- возвращает только случаи `missing_typical_activity`.

## Новая страница

`/admin/reality-curator/signals`

Страница показывает реальные сигналы, а не демонстрационные данные:

- исходное сообщение пользователя;
- идентификатор пользователя;
- идентификатор долговечного сигнала;
- идентификатор activity event;
- язык и часовой пояс;
- временное направление;
- время завершения анализа;
- режим анализа;
- явно выявленные измеримые параметры;
- предупреждение анализатора, если оно есть.

Есть ручное обновление и локальный поиск по загруженной очереди. Автоматического polling нет.

## Навигация

Под Dashboard для администратора добавлен пункт `Куратор модели`, ведущий на `/admin/reality-curator/signals`. Активное состояние распространяется на весь `/admin/reality-curator/*`.

Локализация навигации: RU / PL / EN / ES / UK / DE / CS.

## Что сознательно не входит в V1

Очередь пока только для чтения. В этом этапе нет:

- назначения сигнала куратору;
- статусов `в работе/решено`;
- создания типовой активности прямо из карточки;
- создания/редактирования ОН прямо из карточки;
- реестра пробелов из других источников;
- отдельной таблицы `candidate_signal`;
- удаления или изменения пользовательских данных.

Это следующий блок после подтверждения сквозного поступления реального случая в очередь.

## Проверочный сценарий

1. Пользователь выбирает в правой колонке режим прошедшей активности.
2. Вводит новую формулировку, для которой нет подходящей типовой активности, например новую разновидность действия.
3. Quick capture сохраняет activity event и durable raw signal.
4. Пользователь может сразу уйти со страницы.
5. `ARCTOR_BASIC_ACTIVITY_INTAKE_ANALYSIS_V1` выполняется в фоне через существующий `after()`.
6. Если результат содержит `noSuitableTypicalActivity=true`, запись остаётся в durable signal.
7. Администратор открывает `/admin/reality-curator/signals` или нажимает «Обновить».
8. Реальный случай отображается в очереди.

## Безопасность

- миграций БД: 0;
- записей в БД со стороны нового curator API: 0;
- вызовов OpenAI со стороны curator API: 0;
- используется существующий service-role клиент только на серверной административной стороне;
- пользовательские email/name дополнительно не загружаются: в V1 возвращается только технический `user_id`.

## Точка продолжения

После подтверждения рабочего сквозного сценария реализовать состояние самого кураторского процесса: долговечный реестр задач куратора с `new / in_progress / resolved / ignored`, назначением исполнителя, причиной решения, ссылкой на changeset и историей аудита. Тогда отдельная таблица очереди станет оправданной.
