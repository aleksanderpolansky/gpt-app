ARCHITECTURE LOCK
-----------------
No separate Time Window entity was introduced.

TIME_WINDOW_ENTITY=activity_event(planned)
NEW_ENTITY=NO
NEW_TABLE=NO
DB_MIGRATION=NO

A time window remains a canonical planned activity_event.

Its container role is stored in:

metadata_json.projectPlanningV1

with:

nodeKind=time_container

Supported initial window kinds:

date_range
time_of_day

DATE RANGE
----------
A date-range container reuses canonical planned-activity scheduling:

schedule_mode_code=date_range
schedule_start_date
schedule_end_date

TIME OF DAY
-----------
A time-of-day container without a concrete calendar date remains:

schedule_mode_code=unscheduled

Its local clock bounds are stored in:

metadata_json.projectPlanningV1.timeStart
metadata_json.projectPlanningV1.timeEnd
metadata_json.projectPlanningV1.timeZone

This deliberately avoids pretending that a recurring clock window is one
specific exact calendar occurrence.

CONTAINMENT
-----------
No parent_activity_event_id column was introduced.

Existing PP1 table is reused:

activity_event_relations

with:

relation_type_code=contains
is_hard=true

Both container and child continue to belong to the same project through the
existing:

project_activity_links

PROJECT MAP
-----------
Project center receives compact actions:

+  = add task
horizontal interval = add date window
vertical interval = add time-of-day window

Time-container planned activity is rendered as a larger rectangular region.

The container has an internal + action.

A task created through that + uses the existing:

POST /api/activity/quick-capture

After canonical activity creation, the existing activity receives a hard
contains relation from the time-container activity.

Contained task is rendered inside the container instead of being duplicated as
a separate root-level Project Map card.

CALENDAR / TASK SHELF
---------------------
Planning containers are constraints/regions, not executable tasks.

Therefore time-container planned activities are excluded from:

- executable Task Shelf buckets;
- Calendar all-day planned activity rendering.

Normal child activities remain ordinary canonical activities and continue to
use existing Calendar and Task Shelf behavior.

UNCHANGED
---------
No parallel task system.
No alternate calendar system.
No alternate recurrence system.
No active-profile synchronization.
No database migration.

NOT YET IMPLEMENTED
-------------------
PP5A intentionally establishes only the canonical foundation.

Still pending:

1. boxed + for subprojects;
2. nested time containers;
3. Euler-style intersection islands;
4. hard schedule-bound validation for contained child activities;
5. recurrence materializer preservation of recurring clock bounds;
6. "available now" / green task computation;
7. additional constraint layers.
