# ARCTor — очистка системного каталога параметров + локализованный редактор

Дата: 2026-09-03
Релиз: `ARCTOR_PARAMETER_CATALOG_CLEANUP_LOCALIZED_UI_V1`
Baseline: `b52a8e91d8177e00e3d1ff6b84cd4ef5e7c18292`

## 1. Причина

Реальный пилот куратора `«шёл пешком на работу 15 минут»` дошёл до шага 6 `Проверка параметров и измерений`. При ручном просмотре каталога обнаружилось, что первоначальный seed содержит множество специализированных параметров (`step_count`, `repetition_count`, `set_count`, `items_count` и др.), хотя целевая модель должна по возможности отделять предмет наблюдения от универсального контракта значения.

Пример принятого решения: `Количество шагов` должно проектироваться как листовой ОН, а универсальный параметр `Количество` задаёт тип фиксируемого значения. Предмет подсчёта определяется ОН, а не отдельным parameter code на каждый предмет.

Пользователь решил очистить текущий активный каталог и далее добавлять необходимые параметры вручную по мере прохождения реального пилота.

## 2. Безопасная очистка

Очистка означает **retire, а не DELETE**.

- Все активные системные определения параметров, видимые в рабочем каталоге (`scope_code=system`, кроме скрытого `process_count`), переводятся в `status=retired`.
- Физические строки не удаляются: сохраняются ID, code, версия и история.
- Перед изменением runner повторно проверяет `value_object_parameter_assignments` и `activity_template_profile_parameters_v2`.
- Если хотя бы один кандидат уже используется ОН или типовой активностью, очистка блокируется до мутации.
- `process_count` исключён: production API уже намеренно скрывает его из рабочего каталога, поэтому этот релиз не меняет внутренний legacy/system contract.
- События, факты и measures не удаляются и не переписываются.

После очистки активный рабочий каталог должен быть пуст. Неактивные старые определения остаются доступны по переключателю `Показать неактивные`.

## 3. UI редактора параметров

Редактор сохраняет технические codes без изменения, но больше не заставляет куратора читать их как основной текст.

- `Измерение` в RU переименовано в `Размерность`.
- Dimension/value type/aggregation/default window показываются на языке интерфейса.
- В выпадающих списках после человеческого названия остаётся технический code: например `Количество · count`, `Число · numeric`, `Суммирование · sum`, `Одно событие · event`.
- В карточке параметра размерность показывается локализованным названием.
- По умолчанию каталог показывает только активные определения; неактивные доступны отдельным переключателем.
- Введён отдельный reusable vocabulary helper, чтобы те же подписи можно было использовать на других поверхностях ARCTor.

## 4. Что сознательно НЕ делаем

- Не создаём автоматически новый параметр `Количество`.
- Не создаём/не меняем ОН `Количество шагов`.
- Не создаём типовую активность `Ходьба`.
- Не переходим автоматически к checklist step 7.
- Не меняем существующие activity facts/measures.
- Не добавляем integer как новый `value_type_code` без отдельной проверки DB/API contract.

Следующий рабочий шаг выполняется вручную: куратор постепенно создаёт только те системные параметры, которые реально требуются при разборе модели. Первым логическим кандидатом пилота является универсальный параметр `Количество`, но его создание и canonical technical code должны быть отдельно подтверждены перед записью.

## 5. Evidence и проверки релиза

Runner обязан до любой мутации:

1. подтвердить exact `main`/origin/remote baseline;
2. подтвердить blob редактора параметров и API contract;
3. проверить чистое рабочее дерево и `git diff --check`;
4. выполнить read-only DB audit кандидатов и usages;
5. снять полный ESLint baseline и touched-file baseline;
6. после patch выполнить touched ESLint, полный ESLint no-regression, `tsc --noEmit`, Next production build и `git diff --check`;
7. создать commit;
8. только после успешного commit повторно проверить usages и выполнить controlled retire;
9. проверить, что активных видимых system parameters стало 0;
10. push и подтвердить `origin/main = remote main = local HEAD`.

Если ошибка происходит до commit — runner восстанавливает только release-owned файлы. Если ошибка происходит после commit, используется resume state; база не откатывается автоматически, чтобы не затереть возможные конкурентные изменения.

## 6. Точка продолжения

После PASS открыть `/activity-templates?locale=ru`:

- основной каталог параметров должен быть пуст;
- переключатель `Показать неактивные` должен раскрывать архивированные старые определения;
- selectors должны отображаться локализованно с technical code вторым уровнем.

Затем продолжить реальный пилот: вручную создать первый действительно нужный универсальный параметр и проверить его назначение листовому ОН до перехода к смысловым связям.

## 7. Recovery discipline

Каждый следующий значимый этап продолжает обновлять `docs/recovery/` и не считается закрытым без актуального checkpoint.
