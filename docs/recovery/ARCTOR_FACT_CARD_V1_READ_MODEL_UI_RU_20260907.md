## 1. Зафиксированная модель

Объект наблюдения не хранит числовое состояние. Он является канонической смысловой меткой/адресом. Числа и категориальные значения хранятся только в `activity_object_facts`.

Одна таблица фактов различает три роли:
- `source` — исходный/зафиксированный факт;
- `result` — результирующий факт, рассчитанный из других фактов;
- `snapshot` — факт-срез состояния на момент/границу периода, который может использоваться как следующий status quo.

Происхождение значения (`source_type`) отделено от роли факта. Поэтому измеренный вес может быть `snapshot`, а рассчитанный ночной срез — одновременно `snapshot` + `derived_calculation`.

## 3. DB contract

В `activity_object_facts` добавлены/зафиксированы:
- `fact_role_code`;
- `effective_at`;
- `valid_from`, `valid_to`;
- `snapshot_window_code`;
- `calculation_rule_code`, `calculation_rule_version`;
- `previous_snapshot_fact_id`.

`activity_event_id` допускает NULL для самостоятельных результирующих фактов и срезов.

`activity_fact_derivation_inputs_v1` хранит только происхождение расчёта: какой результирующий/срезовый факт использовал какие входные факты и в какой роли. Значения по-прежнему находятся только в таблице фактов.

## 4. Source/UI change

- `/api/activity/facts` читает новую роль/время действия/формулу/предыдущий срез.
- API читает входные факты из `activity_fact_derivation_inputs_v1`.
- Исправлена прежняя measure-centric граница: самостоятельные `result/snapshot` без `activity_event_id` больше не отбрасываются read model.
- `/activity-facts` показывает роль факта, момент состояния, период действия, вид среза, правило/версию расчёта, предыдущий срез и входные факты.
- Табличный режим получил отдельную колонку роли факта.
- Существующие 26 фактов должны отображаться как `source`.

## 6. Что этот этап НЕ делает

- не создаёт результирующие факты;
- не создаёт срезы по расписанию;
- не вводит реестр формул;
- не выполняет ночной/недельный пересчёт;
- не меняет значения существующих 26 фактов;
- не вызывает OpenAI.

Следующий этап после live acceptance — контракт создания `result/snapshot` и реестр версионируемых вычислительных правил.

## 7. Live acceptance

1. Открыть `/activity-facts?locale=ru` или нужную локаль.
2. Убедиться, что существующий факт показывает роль `Исходный факт`.
3. В таблице должна присутствовать колонка `Роль факта`.
4. В деталях должны присутствовать поля момента состояния, периода действия, среза, правила расчёта, предыдущего среза и входных фактов.
5. Для старого source-факта вычислительные поля должны быть пустыми/`не применяется`, без ошибки API.
