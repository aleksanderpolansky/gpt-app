ARCHITECTURE
------------
No separate subproject entity was introduced.

SUBPROJECT_ENTITY=project_context

A subproject is a normal project_context.

Its root is:

value_object
scope_code=actor
ontology_node_role_code=leaf
visibility=private
status=active

SUBPROJECT_ROOT=value_object(actor/private/leaf)

OBSERVATION OBJECT PARENT
-------------------------
The new subproject root leaf uses the SAME immediate parent_value_object_id
as the parent project's root leaf.

That immediate parent must be:

scope_code=global
origin_type_code=system_model
ontology_node_role_code=intermediate
status=active

SUBPROJECT_PARENT=shared_global_system_intermediate

OBSERVATION OBJECT CREATION
---------------------------
The new personal leaf is created through the existing canonical ontology RPC:

create_value_object_ontology_v1

and activated through:

set_value_object_ontology_lifecycle_v1

Semantics match the existing:

creationMode=leaf_system_parent_active_v1

contract.

No manual shortcut insert into value_objects is used.

The new leaf remains a full canonical observation object and is therefore
available through the normal Value Object page and leaf settings.

PROJECT COMPOSITION
-------------------
The relationship parent project -> subproject reuses:

project_composition_relations

with:

relation_type_code=decomposes_into

No parent_project_id column was added.

No special subprojects table was added.

The child project remains independently addressable as a normal project_context.

MAP UI
------
The project card now has the fourth compact edge action:

⊞ = Add subproject

The existing actions remain:

+ = Add task
horizontal interval = Add date window
vertical interval = Add time-of-day window

After creation the child appears on the parent Project Map as a SUBPROJECT
card.

The subproject card supports:

- open child Project Map;
- open canonical Observation Object page.

When the child is selected as the current project, it receives the same normal
project actions and can itself create further subprojects.

RETRY / IDEMPOTENCY
-------------------
The create request carries clientRequestId.

Ontology leaf creation uses an idempotency key derived from the parent project
and request id.

On retry:

- the canonical leaf can be replayed;
- an existing project_context rooted at that leaf is reused;
- an existing active decomposes_into relation is reused.

CYCLE PROTECTION
----------------
PP5B checks the current user's project-composition graph before writing a new
decomposition link.

Project decomposition cycles are rejected.
