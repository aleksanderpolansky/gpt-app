# ARCTor — Reality Curator: system template scope + checklist step 6 — lint hotfix

Дата: 2026-09-03
Релиз: `ARCTOR_REALITY_CURATOR_PARAMETER_CHECK_V1_2`
Ожидаемый baseline: `d4cd289b012a7eae6ebed976e1a294d43d2fa7ec`

## 0. Ошибка предыдущей попытки и урок

Предыдущая попытка `ARCTOR_REALITY_CURATOR_PARAMETER_CHECK_V1` остановилась безопасно до изменений с `TEMPLATE_ROUTE_CONTRACT_MISSING:signal.userId`. Причина: release-runner проверял неверные camelCase-идентификаторы, тогда как фактический production route использует `signal.user_id` и локальную переменную `actorId`. Rollback подтвердил `git diff --check: PASS` и чистое рабочее дерево.

Исправление V1.1: preflight/patch/self-test синхронизированы с фактическим production-контрактом `owner_user_id = signal.user_id` и `owner_actor_id = actorId`. Продуктовый scope и payload исходного шага не меняются.


## 0.1. Ошибка V1.1 и второй урок

Попытка `ARCTOR_REALITY_CURATOR_PARAMETER_CHECK_V1_1` дошла до touched-file ESLint и была безопасно остановлена правилом `react-hooks/set-state-in-effect`: новый `useEffect` синхронно вызывал `setParameterCheck(null)`, а затем `setParameterStateLoading(true)`/`setError(null)`. Это новая lint-регрессия; commit не создавался. Runner восстановил только release-owned файлы, `git diff --check: PASS`, worktree снова clean. Baseline остался `d4cd289b012a7eae6ebed976e1a294d43d2fa7ec`.

Исправление V1.2: состояние загрузки шага 6 теперь является производным (`checkCompleted && parameterCheck === null && error === null`), а `useEffect` не выполняет синхронных React state writes. State обновляется только из асинхронных callback результата `fetch`. При ошибке GET форма решения не открывается: показывается fail-closed блок ошибки, чтобы не создать повторную append-only запись, не зная текущего состояния шага.

## 1. Причина шага

Реальный пилот `«шёл пешком на работу 15 минут»` дошёл до ручного решения куратора: существующая типовая активность не найдена. В интерфейсе и серверной проверке сохранилась прежняя profile-scoped логика, хотя продуктовая граница уточнена: системные типовые активности являются общими для платформы и управляются администратором. Аналогично системные ОН являются общими системными определениями и именно с ними связываются системные типовые активности.

Старый уже записанный append-only результат не переписывается. Read model исправляет только устаревшую отображаемую формулировку `«в текущем профиле»` на платформенную формулировку. Техническая запись и её timestamp/eventCode/provenance остаются неизменными.

## 2. Product lock

- `activity_templates.template_scope = system` — рабочая область куратора для системных типовых активностей.
- Пользовательский профиль не является владельцем системной типовой активности.
- Системные ОН также рассматриваются как общая platform/system модель; персональные факты пользователя остаются источником сигнала, а не владельцем системного определения.
- Формулировка шага 5: `Сначала попробуйте вручную найти подходящую типовую активность, чтобы исключить вероятность ошибки модели ИИ на этапе подстановки типовой активности.`
- Рабочие ссылки куратора открываются в новой вкладке.
- Передача дела другому куратору по-прежнему отложена.

## 3. Следующий этап по утверждённому checklist v2.0

После шага 5 не перескакиваем сразу к созданию новой типовой активности. Следующий шаг общего triage — **шаг 6: «Проверить каталог параметров и измерений, связанных с предполагаемым смыслом.»**

Допустимые результаты шага 6:
- `available` — параметры уже есть;
- `missing` — не хватает параметра;
- `not_needed` — параметр не нужен;
- `needs_clarification` — требуется уточнение.

Комментарий к решению сохраняется до 1500 символов. После явного действия куратора создаётся отдельная append-only запись `related_parameter_catalog_checked` с checklist snapshot v2.0 / step 6. Эта запись не создаёт и не меняет ОН, параметры, связи или типовые активности.

## 4. Граница записи

Релиз:
- миграций БД: 0;
- DDL: 0;
- релизных мутаций БД: 0;
- OpenAI вызовов: 0.

Runtime после явного действия куратора:
- разрешён только новый append-only `INSERT` в существующий `activity_processing_logs` для события шага 6;
- нет UPDATE/DELETE/UPSERT/RPC для системной модели;
- типовые активности, ОН, параметры, связи и пользовательская activity_event не изменяются.

Событие шага 6 получает детерминированный UUID, поэтому повторный запрос не создаёт дубликат. `23505` трактуется как idempotent duplicate.

## 5. Журнал и UI

Порядок рабочего места сохраняется:
1. шапка журнала;
2. текущий следующий шаг и краткая инструкция;
3. действия/варианты решения;
4. ниже — история дела от новых событий к старым.

Технические сведения продолжают показывать стандарт: human label → дата/время → stable event code → куратор → checklist version → step.

Для старого события пилота `existing_typical_activity_checked` read model заменяет только устаревшую display-фразу `Подходящей типовой активности в текущем профиле не найдено.` на `Подходящей системной типовой активности на платформе не найдено.` Исходная append-only строка не изменяется.

## 6. Продолжение пилота

После выпуска открыть тот же сигнал `«шёл пешком на работу 15 минут»`. Текущий этап должен стать `Проверка параметров и измерений`. Куратор открывает каталог параметров в новой вкладке, проверяет существующие системные параметры и выбирает один из четырёх результатов. После сохранения в журнале появляется отдельный блок `Проверка параметров и измерений` и техническое событие `related_parameter_catalog_checked`.

Следующий программный этап после этого — checklist step 7: проверка существующих смысловых связей и их направлений.
