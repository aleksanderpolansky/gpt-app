## Управленческое решение V1

Рабочее место куратора должно вести сотрудника по одному следующему шагу и не заставлять каждый раз прокручивать всю историю дела.

1. Блок следующего действия показывается непосредственно под шапкой `Журнал обработки` и тремя карточками состояния (`Текущий этап / Ответственный / Последнее действие`).
2. Исторические записи журнала располагаются ниже блока следующего шага. При длинной истории рабочее действие остаётся наверху.
3. Любая страница, которую куратор открывает для проверки в ходе текущего процесса, не должна уводить его со страницы сигнала. В текущем шаге `/activity-templates` открывается в новой вкладке (`target=_blank`, `noopener noreferrer`). Это правило применять к следующим рабочим ссылкам куратора.
4. Перед кнопками/вариантами действия показывается короткая инструкция: что именно проверяется на этом шаге, зачем это нужно и как завершить шаг.
5. Перед финальными вариантами решения отдельно показывается короткая подсказка о допустимых исходах и необходимости зафиксировать основание решения.

## Методическая привязка

Учебник куратора требует сначала проверять существующие templates, не создавать template только из единичной фразы и не превращать goal/place/context в новый шаблон без самостоятельного смысла. Для activity↔ОН связей направление, conditions, temporal scope и evidence должны рассматриваться явно; «ходьба полезна для сердца» недостаточно для канонической причинной связи с конкретным показателем.

## Acceptance / evidence для release runner

Runner обязан до commit/push проверить:

1. exact baseline commit и clean worktree;
2. `origin/main` и remote main равны baseline;
3. blob hashes обоих изменяемых исходных файлов;
4. payload hashes и статический contract;
5. `git diff --check` до и после;
6. ESLint baseline изменяемых файлов и отсутствие регрессии;
7. полный ESLint baseline до/после без увеличения errors/warnings;
8. `tsc --noEmit`;
9. `next build`;
10. только ожидаемые changed files;
11. commit, push, fetch и совпадение local/origin/remote;
12. rollback до commit и resume после созданного commit при сбое push.

После PASS этого UI-release вернуться к реальному сигналу, визуально проверить новое расположение блока и новую вкладку `/activity-templates`, затем сохранить фактический результат проверки типовой активности.
