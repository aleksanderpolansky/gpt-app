PROBLEM
-------
Calendar date/date-range items were opening Cux6TaskDetailModal from a
synthetic locally reconstructed Cux6ShelfItem.

That synthetic object forced:

outcomeOptions=[]
selectedOutcome=null

Therefore a planned occurrence could have configured outcomes in
activity_events, while the Calendar card did not see them.

The modal then submitted outcomeLabel=null and the server correctly rejected
completion with:

Select one of the configured activity outcomes.

FIX
---
Calendar no longer constructs an artificial task-detail object from
CalendarAllDayItem.

All Calendar date/date-range planned activity entry points now load the
canonical planned activity through:

GET /api/calendar/task-shelf/{activityEventId}

The returned Cux6ShelfItem is passed to the shared Cux6TaskDetailModal.

Calendar occurrence is explicitly marked:

isRecurrenceDefinition=false

The recurrence definition remains non-executable.

A latest-request guard prevents an older slower detail request from replacing
a newer user selection.

A visible error is shown when canonical detail loading fails.

SEMANTIC LOCK
-------------
activity_events remains the canonical activity entity.

planned occurrence = activity_event role planned

completion = new activity_event role actual

fulfills_planned_activity_event_id remains the canonical plan-to-actual bridge.

No separate task entity was introduced.
