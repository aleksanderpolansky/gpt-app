# ARCTOR_ACTIVITY_TEMPLATE_IMPACT_PROFILE_AUTHORING_V1

Дата: 2026-08-21
Baseline source: `04e43556124d62e858296ab36203d59d2de6ca95`

## Решение

Типовая активность хранит набор связей с листовыми ЦО/ОН один раз. Реальное событие не размножается в десятки физических фактов: запись события содержит ссылку на точную версию профиля, а вклады в связанные ЦО/ОН разворачиваются виртуально при чтении.

Это сохраняет стоимость записи нового известного события близкой к O(1) относительно количества связанных ЦО/ОН. Таблица связей индексируется в обе стороны: `profile -> object` и `object -> profile`.

## Параметры

В V1 разрешены четыре исходных параметра события: `process_count`, `repetition_count`, `distance_m`, `duration_seconds`. `process_count=1` обязателен для каждого связанного ЦО/ОН. Для остальных параметров пользователь вручную задаёт маршрутизацию к параметру ЦО/ОН и контролируемый способ подсчёта: `copy`, `count`, `sum`, `max`, `min`, `avg`. Произвольные формулы и eval запрещены.

## Версионирование

Каждое сохранение карточки создаёт новую неизменяемую версию impact profile. Старые события могут продолжать ссылаться на старую версию. Новое событие с `activity_template_id` автоматически получает текущий `impact_profile_id` DB-trigger-ом, если профиль существует.

## Динамика ЦО/ОН

Новая карточка переиспользует существующий `value_object_analytics_profiles_v1`: baseline, target, critical boundary, desired direction, refresh period, inactivity delta, trend window.

В этом релизе виртуальные вклады доступны в БД через read-only projection views, но существующий runtime-калькулятор текущего состояния продолжает читать подтверждённые физические `activity_object_facts`. Это намеренная граница: автоматическое объединение виртуальных и физических вкладов должно быть следующим отдельным шагом с дедупликацией по event_id, чтобы не создать двойного счёта.

## Безопасность и масштабирование

- Новые таблицы RLS-enabled; browser roles не имеют прямого доступа.
- Save RPC доступен только `service_role`; HTTP API сначала разрешает Auth0 + active actor context.
- Максимум 500 ЦО/ОН на одну версию профиля.
- Исторические activity events/facts не обновляются и не backfill-ятся.
- Новая схема не включает AI-вызовы.
- Для будущей аналитики использовать `COUNT(DISTINCT event_id)` при подъёме по `part_of`, чтобы один процесс не считался многократно через несколько дочерних объектов.

## Точка продолжения

Следующим runtime-шагом: подключить `activity_event_virtual_parameter_contributions_v1` к аналитике текущего состояния с дедупликацией относительно уже материализованных фактов по event_id/provenance. После этого добавить дневной агрегат только при реальной необходимости по объёму данных.

## Precommit lint hotfix V2

Первая попытка source-release V1 была остановлена до commit штатным ESLint: `react-hooks/set-state-in-effect` обнаружил синхронный `setSearchResults([])` непосредственно внутри `useEffect` в поиске ЦО/ОН. Launcher выполнил полный rollback к baseline `04e43556124d62e858296ab36203d59d2de6ca95`, рабочее дерево осталось чистым.

В package/launcher V2 исправление узкое: очистка результатов короткого поискового запроса перенесена в обработчик пользовательского ввода, а `useEffect` при длине запроса < 2 просто завершается. В validator добавлен отдельный контракт `UI_SEARCH_EFFECT_NO_SYNC_SETSTATE`, чтобы эта ошибка не повторилась. DB-слой не менялся и повторного DB APPLY не требует.
