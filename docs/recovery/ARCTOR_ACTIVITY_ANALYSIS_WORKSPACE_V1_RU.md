# ARCTOR_ACTIVITY_ANALYSIS_WORKSPACE_V1

Дата: 2026-08-22
Source baseline: `10149d098a6fbd9f5808002fb52f29573444c199`
DB schema change: NONE

## Решение этапа

Существующая страница `/activity-ai-lab` больше не используется как отдельная форма ввода активности. Быстрый ввод остаётся только в правой колонке AI-Навигатора. После фиксации пользователь получает единственное короткое подтверждение: «Активность зафиксирована. Активность доступна для анализа в Журнале активностей.»

Журнал активностей становится точкой входа в анализ: название сохранённой активности открывает `/activity-ai-lab?activityEventId=<id>&locale=<locale>`. Страница AI Lab превращается в рабочее пространство конкретной уже сохранённой активности.

На этом этапе в рабочем пространстве реализован только блок «1. Базовый анализ»: исходная активность, её жизненный статус, явно извлечённые параметры и список только уверенно подходящих существующих типовых активностей. Кнопки применения типовой активности, «Сохранить связи», «Дополнительный анализ», создание фактов и привязка ЦО/ОН намеренно не реализуются.

## Упрощение Журнала активностей

Для записей активности в списке убраны отдельные кнопки «Открыть», «Контейнер» и «Изменить». Они создавали несколько конкурирующих путей к одной записи и показывали техническую модель контейнера пользователю.

Название активности становится ссылкой на рабочее пространство анализа. В списке остаются жизненный статус активности, компактный статус базового анализа и вторичные операции удаления/восстановления. Подробный базовый анализ переносится с карточки списка в рабочее пространство анализа.

Старый modal/detail код пока не удаляется полностью, поскольку он ещё используется историческими календарными log-записями; для обычной activity-записи основной путь теперь ведёт в AI Lab.

## Устойчивость базового анализа

Первый production-тест `ARCTOR_BASIC_ACTIVITY_INTAKE_ANALYSIS_V1` показал, что событие сохранилось правильно, но базовый анализ перешёл в `failed`. Точный production errorCode намеренно не читался из Supabase при подготовке этого патча: проектное правило требует отдельного разрешения на production diagnostic read.

Чтобы не чинить наугад одну предполагаемую ошибку, базовый intake сделан fail-soft:

- Nano-модель по-прежнему является основным анализатором;
- AI вызывается один раз, без автоматических retries, `store=false`;
- невалидный отдельный measurement или candidate больше не обрушает весь результат — такой элемент просто отбрасывается;
- сервер независимо извлекает несколько очевидных числовых параметров из буквального текста как защитный слой: повторения, расстояние, длительность и массу;
- регулярные выражения защитного слоя используют Unicode-безопасную границу после русских/украинских/польских единиц; локально отдельно проверены `20 раз`, `3,2 км`, `42 минуты`, `20 кг`, `12 razy`;
- эти безопасные параметры объединяются с валидным AI-результатом без дублей;
- если модель/бюджет/context-manifest/provider временно недоступны, событие не переводится в общий `failed`, а сохраняется завершённый `safe_server_fallback`;
- в fallback типовая активность показывается только при практически точном серверном совпадении (`candidateScore >= 0.98`), то есть система не предлагает «что-нибудь похожее»;
- при обычной успешной работе именно Nano решает semantic matching, включая опечатки и речевые вариации;
- никакие ЦО/ОН, impact profiles или факты не передаются модели и не записываются автоматически.

Fallback является защитой от инфраструктурного сбоя, а не заменой AI matching.

## Граница расходов и повторов

Существующие уже сохранённые `failed` результаты не перезапускаются автоматически при каждом открытии AI Lab, чтобы не создать скрытый повторный расход. После релиза acceptance выполняется на новой активности. Отдельный управляемый retry старого анализа можно добавить позже, если он понадобится.

## Что не меняется

- схема БД;
- таблицы ЦО/ОН;
- таблицы типовых активностей и impact profiles;
- `activity_template_id` не назначается автоматически;
- A3.1/Standard не запускается автоматически;
- `activity_object_facts` не записываются этим этапом;
- clean-start semantic reset остаётся отдельным будущим этапом;
- действия после выбора типовой активности проектируются отдельным блоком.

## Acceptance после deploy

1. Ввести новую активность через правую колонку, например «сегодня подтянулся узким хватом 20 раз».
2. Убедиться, что справа остаётся только короткое подтверждение фиксации.
3. Открыть Журнал активностей: у новой записи нет кнопок «Открыть», «Контейнер», «Изменить»; название кликабельно.
4. Перейти по названию в `/activity-ai-lab?activityEventId=...`.
5. Увидеть исходную активность, статус и блок «1. Базовый анализ».
6. Ожидаемый минимум для примера: параметр `20 повторений`; при рабочем Nano и уверенном совпадении — «Подтягивание узким хватом».
7. Если провайдер временно недоступен, вместо красного общего fail должен быть безопасный fallback с явно извлечёнными параметрами; слабые типовые активности не предлагаются.

## Точка продолжения

После acceptance этого этапа отдельно проектировать выбор найденной типовой активности и две будущие операции: применение стандартного сценария/связей и дополнительный индивидуальный анализ.
