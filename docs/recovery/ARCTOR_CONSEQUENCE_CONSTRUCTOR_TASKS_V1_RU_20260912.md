# ARCTor — Конструктор последствий: очередь заданий V1

Дата: 2026-09-12
Baseline before release: ce9669a4e805009391ed17bd44e02aed786a90d9
Release: ARCTOR_CONSEQUENCE_CONSTRUCTOR_TASKS_V1_20260912

## Зафиксированная модель
- После назначения листового ОН конкретному параметру кураторского разбора сразу создаётся активное задание в «Конструкторе последствий».
- Исходный контекст задания: сырая активность + параметр + исходный листовой ОН.
- Если типовая активность уже определена, задание сразу отображает её.
- Если типовой активности ещё нет, задание остаётся привязанным к сырой активности как к временному источнику происхождения.
- После появления типовой активности контекст автоматически переопределяется по curator journey metadata; администратор также может вручную выбрать типовую активность.
- Ручная смена типовой активности применяется ко всем заданиям одной исходной сырой активности.
- Рабочая пара исходный ОН → целевой ОН не является универсальной связью. Её будущий смысл определяется только внутри конкретной типовой активности.
- После появления типовой активности задания дедуплицируются по ключу: типовая активность + параметр + исходный листовой ОН.
- Целевой ОН обязательно будет листовым, но в V1 его выбор заблокирован до реализации отдельного конструктора связей ОН.
- V1 не создаёт value_object_relations, формулы и результирующие факты.

## Реализация
- Новый server module: src/lib/reality-curator/consequence-constructor.server.ts.
- Новый admin API: /api/admin/consequence-constructor.
- Новая UI-страница: /admin/consequence-constructor.
- В меню администратора под «Куратор модели» добавлен «Конструктор последствий · N».
- object-bootstrap создаёт задание сразу и для выбранного существующего листа, и после создания нового листа.
- GET полной страницы выполняет reconciliation старых curator mapping logs, поэтому ранее созданные назначения также могут попасть в очередь.
- Summary API для меню остаётся read-only и использует лёгкий count без reconciliation writes.
- Данные V1 хранятся append-only в activity_processing_logs; SQL schema не меняется.

## Статусы V1
- awaiting_template — есть исходная сырая активность, но типовая ещё не определена.
- awaiting_relations — типовая активность определена, но конструктор связей ОН ещё не заполнен.
- targetSelectionState=locked_pending_relations — целевой листовой ОН пока выбрать нельзя.

## Safety / invariants
- Никакая общая связь между двумя ОН автоматически не создаётся.
- Одинаковая пара ОН в разных типовых активностях рассматривается как разные будущие правила.
- Сырая активность сохраняется как provenance даже после привязки к типовой активности.
- Текущий workflow куратора не блокируется ошибкой создания secondary consequence task; reconciliation восстанавливает недостающую запись при открытии конструктора.
- Нет SQL schema change.

## Точка продолжения
Следующий блок — «Конструктор связей ОН». После него на странице «Конструктор последствий» разблокировать выбор только тех листовых целевых ОН, с которыми у исходного ОН подтверждена допустимая связь. После выбора первого целевого ОН задавать вопрос «Добавить связь с другим ОН?». Формулы и результирующие факты — следующий этап после выбора целевых ОН.
