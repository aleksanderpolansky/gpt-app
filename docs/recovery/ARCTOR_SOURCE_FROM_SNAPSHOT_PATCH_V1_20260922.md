# ARCTor: исходное значение из факта-среза — V1, 22.09.2026

База intake: 40496d390f5600c866f924757cacf22ca000bed0.

## Что изменено

В форме создания системной типовой активности для каждой выбранной связи «параметр → ОН» доступны три режима: прямое значение; прямое, а при отсутствии — срез; только срез. В расчётных режимах доступны поиск состояния, выбор и числовой множитель. Настройка выполняется до публикации активности.

Каталог состояний переиспользован из /api/activity/facts/snapshots. Он показывает типы состояний с активным системным назначением того же числового параметра. В системном профиле сохраняется смысловой адрес состояния (ОН + параметр), а не персональная запись администратора. При записи исходного факта выбирается последний подтверждённый срез пользователя и активного действующего субъекта на момент started_at активности. Будущие, чужие и неподтверждённые срезы не используются; просроченное состояние требует уточнения.

Настройки sourceValueBindingsV1 записываются в существующее metadata_json профиля. Формула использует существующий язык arctor_formula_v1 и операцию multiply. Чистый вычислитель перенесён из formula-rule-test-runner.server.ts в общий модуль без изменения реализации операций; прежний тестировщик импортирует его обратно. Новый язык или второй вычислитель не создаётся. Отдельная запись в реестре правил последствий для простого множителя не создаётся.

Модуль E03 использует существующий attach_global_observation_facts_gsr1_v1. Значения из срезов помечаются derived_calculation / deterministic_calculation / deterministic. Исходная запись сохраняет роль source по существующему контракту writer. ID использованного среза, его время, вход, единица, множитель, выражение и обоснование сохраняются в source_snapshot_json происхождения измерения. Это не добавляет графовые рёбра result/snapshot для source-фактов.

Единица среза сохраняется: 35 gram × 1 = 35 gram. Значение не переименовывается в kilogram. Writer проверяет допустимость единицы по тому же определению параметра. Канонический параметр с единицей kilogram может содержать допустимое измерение gram, как и при прямой записи. Отдельный механизм конвертации не добавлен.

Для повторного подтверждения сохранены использованные writer-строки и отпечаток входа. Обычный повтор использует прежний срез и существующую идемпотентность RPC. Изменение исходного текста, времени или профиля не считается тем же расчётом; существующий writer блокирует конфликт вместо дубликатов. Если RPC записал факты, но последующее сохранение отчёта анализа не удалось, повтор с изменившимся срезом может вернуть конфликт идемпотентности — требуется восстановление, а не повторная запись новыми ключами.

## Границы

- Новые настройки добавлены в прямую форму создания системных типовых активностей. Отдельный редактор ранее опубликованных профилей не дорабатывался.
- Существующий контролируемый шлюз подтверждения E03 сохранён. Автоматическая запись без подтверждения не включается.
- Исполнитель последствий, исторические факты и правила перерасчёта не изменяются.
- SQL-миграция не требуется: используются существующие таблицы, metadata_json и RPC из intake.
- Сохранение прямого шаблона использует существующую многошаговую процедуру: метаданные профиля записываются до завершающего маркера шаблона. Нельзя считать всю публикацию одной новой SQL-транзакцией.
- Intake содержит выборку исходников. Код вызывающей страницы и /api/activity/intake-analysis/materialize-source-facts/route.ts в выборку не вошёл. Изменён сам вызываемый модуль E03; доступность кнопки подтверждения при отсутствии явного числа должна быть проверена в браузере.

## Установка и восстановление

Сохранить ZIP в Downloads и запустить install.ps1 из репозитория gpt-app. Установщик проверяет контрольные суммы всех заменяемых файлов по intake и целостность payload до замены. Повторная установка того же payload допустима. Несовпадение базы останавливает установку.

Резервная копия изменяемых файлов: docs/recovery/*_BACKUP.zip. Лог: docs/recovery/*.log. Отчёт: docs/recovery/*.md. Отдельный *_RESULT.zip с логом и отчётом создаётся в Downloads. При ошибке проверок исходники восстанавливаются; конкурентно изменённый файл не затирается и отмечается для ручного восстановления. При неудачной сборке могут оставаться промежуточные .next-файлы — после отката нужно заново собрать прежнюю версию.

Не выполняются: npm install, миграции БД, коммит, push, публикация сайта, изменение истории фактов. Установщик проверяет локальную сборку; работающий сайт обновляется штатным процессом проекта.

## Приёмка на сайте после штатной публикации

1. Создать новую системную типовую активность «Употребление протеина». Выбрать Масса → Употребление протеиновой добавки.
2. Выбрать «Прямое значение → если отсутствует, рассчитать», состояние «Текущая порция протеиновой добавки», множитель 1. Опубликовать.
3. У своего действующего субъекта записать подтверждённый срез 35 gram до времени активности.
4. Создать «выпил протеин» без массы; убедиться, что типовая активность распознана однозначно. Выполнить существующее подтверждение записи исходных фактов. Если кнопка скрыта из-за отсутствия числа, остановиться и приложить её исходник вместе с RESULT — не включать новый автоматический путь.
5. Проверить source-факт Масса=35 gram для ОН употребления. В происхождении проверить snapshotFactId и множитель.
6. Повторить подтверждение: новых фактов нет.
7. Новая активность «выпил 20 г протеина»: масса 20 gram, прямое происхождение.
8. Отдельный шаблон в режиме «только рассчитываемое» с множителем 2: при срезе 35 gram получается 70 gram.
9. Для пользователя без нужного среза должна быть ошибка уточнения; нулевого факта нет.
10. Старый сценарий подъёма по лестнице с явными значениями и существующими последствиями должен работать как прежде.
