# ARCTOR_BASIC_ACTIVITY_INTAKE_ANALYSIS_V1

Дата: 2026-08-22
Source baseline: `4cb845401809eafbb4586e5f1045b7f2f3205e7b`

## Решение этапа

Этот этап намеренно упрощает runtime после фиксации активности. Правая колонка является быстрым входом: пользователь пишет или диктует прошедшую либо планируемую активность, событие сохраняется сразу, а пользователь получает только короткое подтверждение: «Активность зафиксирована. Активность доступна для анализа в Журнале активностей.»

Дополнительных уведомлений о завершении фонового анализа в правой колонке нет. После успешного capture интерфейс не перенаправляет пользователя автоматически в календарь или review.

## Что делает фоновая базовая модель

После сохранения события один Nano-вызов выполняет только две задачи:

1. извлекает явно сообщённые измеримые параметры — дату/время, продолжительность, повторения, подходы, расстояние, массу, количество, объём, деньги, скорость, пульс, температуру, энергию, rate и другие примитивные явно указанные значения;
2. выбирает только действительно подходящие существующие типовые активности из серверного shortlist.

В модель не передаются ЦО/ОН, impact profile, связи профиля, эффекты или факты. Модель не имеет права выбирать ЦО/ОН, диагностировать, выводить последствия либо придумывать типовую активность. `rawFragment` каждого извлечённого параметра обязан быть буквальным фрагментом исходного текста. Порог показа типовой активности — 0.90. Если уверенного совпадения нет, список остаётся пустым: слабые кандидаты не показываются.

## Что этот этап НЕ делает

- не записывает `activity_object_facts`;
- не назначает `activity_template_id` автоматически;
- не применяет impact profile;
- не запускает A3.1 Standard review автоматически;
- не проектирует и не реализует действия после будущих кнопок «Сохранить связи» и «Дополнительный анализ»;
- не удаляет старые ЦО/ОН и старые semantic-данные — clean-start reset остаётся отдельным будущим этапом.

Предыдущий `ARCTOR_RUNTIME_TEMPLATE_BRIDGE_FACT_DEDUP_V2` остаётся в истории и сохраняет unified analytics view, однако его автоматический template-first вызов из quick-capture в этом этапе сознательно отключается. Сам matcher-файл и DB RPC не удаляются, чтобы не выполнять разрушительную миграцию; новый quick-capture их не вызывает.

## Где хранится результат

Новая таблица не требуется. Результат фонового intake хранится в существующем `raw_activity_signals.normalized_preview_json.basicIntakeAnalysisV1`. Это сохраняет связь с исходным durable signal и activity event без дополнительной схемы БД.

Для Журнала добавляется read-only HTTP API, который одним пакетным запросом получает анализ максимум для 50 уже загруженных activity events. Polling, таймеры и фоновые повторные запросы отсутствуют. Если анализ ещё идёт, пользователь видит состояние «Базовый анализ выполняется…» и может позже снова открыть/обновить Журнал.

## Журнал активностей

Для activity event показывается отметка:

- «Завершенная активность» для фактической активности;
- «Планируемая активность» для будущей активности.

После завершения базового анализа карточка показывает:

- серверное время/длительность и явно извлечённые параметры;
- текст «Активность может соответствовать следующим типовым активностям:»;
- только прошедшие строгий confidence-gate существующие типовые активности;
- если список пуст: «Подходящая типовая активность не найдена.» и ссылка на полный список типовых активностей.

На этом этапе в карточке нет кнопок, которые что-либо сохраняют или запускают индивидуальный анализ. Их поведение будет отдельным проектным блоком.

## Навигация

Под «Журнал активностей» добавляется дочерний пункт «Типовые активности» (`/activity-templates`) выше «Требуют проверки». Локализация добавлена для RU/PL/EN/ES/UK/DE/CS.

## Безопасность и стоимость

- capture не ждёт AI;
- один Nano-вызов выполняется в Next `after()`;
- model store=false, retries=0;
- используется существующий AI budget preflight и usage accounting;
- provider получает максимум 24 названия/коротких названия кандидатов, но не каталог ЦО/ОН;
- сервер читает только минимальные поля activity templates;
- production Supabase не использовался для подготовки патча;
- существующие Activity Events не переписываются исторически.

## Следующий отдельный блок

После production-проверки этого intake отдельно спроектировать поведение выбора типовой активности, «Сохранить связи» и «Дополнительный анализ». Только после работоспособного Journal workflow выполнять отдельный inventory/backup + semantic clean-start reset ЦО/ОН и старых AI semantic данных.

## Неудачная попытка V1 и исправление V2

Первый V1 source-run 2026-08-22 дошёл до `ESLINT_CHANGED` после успешных package/patch validators. ESLint Next 16 выявил три уже существовавших в `src/app/activity-today/page.tsx` нарушения `react-hooks/set-state-in-effect`: синхронный `setLocale(...)` при монтировании, очистку `setMutualLinksByActivityId({})` в пустой ветке effect и `setAutoOpenHandled(true)` в auto-open effect. Это не ошибка новой бизнес-логики intake, но файл Journal стал изменяемым в этом релизе, поэтому lint обязан быть чистым. Commit/push не создавались; launcher выполнил `ROLLBACK=PASS` и вернул HEAD на исходный `4cb8454`.

V2 не отключает правило ESLint и не исключает Journal из проверки. Вместо этого:

- начальная синхронизация locale выполняет `setState` только из callback таймера/popstate;
- пустая mutual-links ветка больше не делает ненужную синхронную очистку state (при пустом списке событий старое значение всё равно не рендерится);
- флаг одноразового auto-open переведён из render-state в `useRef`, поскольку он не участвует в UI;
- перед любыми изменениями checkout patch-tool теперь программно загружает реальный ESLint из `node_modules` production-repo и запускает его на всех восьми будущих TS/TSX версиях через `lintText`. При любой ошибке или warning релиз останавливается до source mutation.
