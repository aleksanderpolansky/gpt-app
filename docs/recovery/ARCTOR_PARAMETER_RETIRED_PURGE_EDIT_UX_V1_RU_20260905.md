# ARCTOR — очистка retired-параметров + безопасное удаление + Edit UX

Дата: 2026-09-05
Релиз: `ARCTOR_PARAMETER_RETIRED_PURGE_EDIT_UX_V1_0_3`
Baseline: `53e0c8679e17ee41d9dcbe9b6618628bbaf905d3`

## 1. Причина

В реальном проходе конструктора сигнала `«подтянулся 10 раз»` куратор сформировал набор измеримых параметров и решил добавить универсальную `Продолжительность` (`duration`).

Создание новой записи было корректно заблокировано, потому что в БД уже существовала старая retired-запись с тем же technical code `duration`. Одновременно каталог содержал множество retired legacy-параметров с нулевым отображаемым использованием, что создавало шум.

Дополнительно кнопка `Изменить` выглядела неработающей: состояние редактирования переключалось, но форма находилась после длинной сетки карточек и оставалась далеко ниже текущего viewport.


## Ошибка первого release-runner и урок

Первая попытка `ARCTOR_PARAMETER_RETIRED_PURGE_EDIT_UX_V1` завершилась **до начала мутаций** на source-contract gate.

Фактический Git blob baseline-файла
`src/app/activity-templates/activity-parameter-admin-catalog.tsx`
на commit `53e0c8679e17ee41d9dcbe9b6618628bbaf905d3`:
`ee7d652bfb64dcfc60bf5e4dcbd6f9571b9f1a6d`.

В первом runner был ошибочно зафиксирован другой expected blob:
`f37d432ccdafe399667cc1d22bb7fd496cce6081`.

Следствия первой попытки:
- `DB_MUTATION_APPLIED: NO`;
- `CODE_COMMIT_CREATED: NO`;
- push не выполнялся;
- baseline, `origin/main` и remote `main` остались без изменений.

V1.0.1 меняет только release-runner source contract и фиксирует этот урок в recovery; функциональный cleanup payload не меняется.


## Ошибка второй попытки V1.0.1 и урок

Вторая попытка `ARCTOR_PARAMETER_RETIRED_PURGE_EDIT_UX_V1_0_1` также завершилась **до начала мутаций** на том же source-contract gate.

Причина: при исправлении первого runner в expected blob была случайно потеряна последняя hex-цифра `d`.
В V1.0.1 было записано 39 символов:

`ee7d652bfb64dcfc60bf5e4dcbd6f9571b9f1a6`

вместо канонического 40-символьного Git blob:

`ee7d652bfb64dcfc60bf5e4dcbd6f9571b9f1a6d`.

Следствия второй попытки:
- `DB_MUTATION_APPLIED: NO`;
- `CODE_COMMIT_CREATED: NO`;
- push не выполнялся;
- baseline, `origin/main` и remote `main` остались без изменений.

V1.0.2:
- исправляет expected blob до полного 40-символьного SHA;
- добавляет в source-contract gate явную проверку формата `^[0-9a-f]{40}$`;
- логирует одновременно actual и expected blob;
- не меняет functional cleanup payload.


## Ошибка третьей попытки V1.0.2 и урок

V1.0.2 успешно прошёл source-contract gates, dedicated validator, touched/full ESLint, TypeScript, production build, allowlist и создал локальный code commit. Затем pre-audit ошибочно классифицировал все 39 retired definitions как zero-use, потому что usage-аудит ещё не учитывал ссылки из фактических измерений/фактов.

PostgreSQL остановил единый bulk DELETE по FK:

`activity_event_measures_parameter_definition_id_fkey`

Таблица `activity_event_measures` хранит `parameter_definition_id` с `ON DELETE RESTRICT`. В P4A-контракте такой же `parameter_definition_id ... ON DELETE RESTRICT` существует и в `activity_object_facts`.

Защита сработала правильно:
- bulk DELETE был отклонён атомарно;
- `DB_MUTATION_APPLIED: NO`;
- push не выполнялся;
- временный локальный code commit был сброшен runner-ом обратно к baseline;
- worktree после rollback — clean.

Урок: usage системного параметра включает не только назначения и настройки шаблонов, но и уже сохранённые исторические измерения/факты. Такие определения нельзя физически удалять, даже если они retired.

V1.0.3 добавляет в usage/audit:
- `activity_event_measures`;
- `activity_object_facts`;
и сохраняет любой retired parameter, имеющий хотя бы одну из известных ссылок.

`duration` отдельно исключён из bulk purge и сохраняется для повторной активации: его исходный P7 seed-контракт структурно совместим с текущей потребностью (`time` / `numeric` / canonical `minute` / `sum` / `event` / non-negative; допустимы second/minute/hour).

## 2. Решение

- Retired system parameters физически удаляются только если непосредственно перед DELETE подтверждено отсутствие ссылок.
- `process_count` всегда исключён из физического удаления.
- Активный системный `count` является обязательным preflight-инвариантом и не затрагивается.
- Проверяются известные прямые ссылки:
  - `value_object_parameter_assignments`;
  - `activity_template_profile_parameters_v2`;
  - `fact_capture_precision_preferences`;
  - `activity_event_measures`;
  - `activity_object_facts`.
- Для каждой таблицы pre-audit получает exact reference count; retired definition с любой ссылкой остаётся в БД.
- Дополнительные неизвестные FK остаются последней защитой БД: FK `ON DELETE RESTRICT` должен остановить единый bulk DELETE целиком.
- Admin API считает назначения, template usage, precision preferences, сохранённые measures и object facts частью общего `usageCount`.
- `duration` намеренно не удаляется даже при zero-use: он нужен текущему конструктору и после PASS должен быть переиспользован/активирован.
- Admin API получает DELETE только для `retired + usageCount=0`; active/used/process_count удалить нельзя.
- Для retired zero-use карточки появляется кнопка `Удалить`.
- `Изменить` и `Новый параметр` автоматически прокручивают интерфейс к реально открытой форме.

## 3. Почему политика retire-only изменена

3 сентября очистка намеренно использовала `retire`, а не `DELETE`: на тот момент это была безопасная первичная очистка каталога и сохранение истории было важнее удобства.

После реального прохода конструктора выяснилось, что старые zero-use seed definitions мешают повторно создавать канонические параметры по осознанному контракту. Поэтому физическое удаление теперь допускается только для retired zero-use system definitions и только через fail-closed usage/FK gates.
