# ARCTOR_RUNTIME_TEMPLATE_BRIDGE_FACT_DEDUP_V2

Дата: 2026-08-21
Source baseline: `5f1d8d24a25a3294424293192a82680d0a947d09`

## Зачем сделан этап

После карточки типовой активности ARCTor уже умеет хранить один версионный профиль связей типовой активности с любым количеством ЦО/ОН и виртуально разворачивать параметры события в эти объекты. Не хватало runtime-моста между свободным вводом пользователя, типовой активностью, существующим A3.1 review-first фактов и расчётом состояния ЦО/ОН.

V1 этого runtime-моста не применялся. В нём была слишком грубая граница: уверенно распознанная типовая активность полностью отключала стандартный семантический review. Это неправильно для фраз вроде «подтянулся узким хватом 20 раз, после этого заболела шея». V2 заменяет эту логику до первого production APPLY.

## Зафиксированное решение

Число связанных ЦО/ОН не фиксировано. У одной типовой активности может быть несколько объектов, у другой — десятки или сотни. Runtime не содержит смыслового ограничения на конкретное число объектов; профиль хранит фактический набор связей, заданный в карточке.

Первый AI-вызов выполняет узкую работу: связывает свободный текст/диктовку с одной из уже существующих личных типовых активностей. Сервер предварительно формирует небольшой shortlist; провайдер получает максимум 24 названия-кандидата, но не получает каталог ЦО/ОН, impact profile, правила воздействия или факты. Nano возвращает индекс кандидата/`no_match`, confidence и только технический флаг `residualReviewRequired`: есть ли в исходной фразе явно сообщённое дополнительное содержание помимо самой активности и уже покрываемых сервером repetitions/distance/duration. Этот флаг не является анализом фактов и не определяет ЦО/ОН.

После совпадения сервер детерминированно записывает `activity_template_id`, существующий trigger фиксирует точный `impact_profile_id`, а повторения/расстояние/длительность сохраняются как параметры события. `process_count=1` остаётся частью виртуального профиля.

## Три runtime-режима

1. **Чистая типовая активность.** Например: «подтянулся узким хватом 20 раз». Nano распознаёт типовую активность, residual-review=false. Широкий A3.1 review не запускается. ЦО/ОН и маршрутизация параметров берутся из сохранённого профиля.

2. **Типовая активность + остаточные факты.** Например: «подтянулся узким хватом 20 раз, после этого заболела шея». Nano только распознаёт типовую активность и ставит residual-review=true. Затем существующий Standard A3.1 запускается в специальном residual-режиме: ему известны название уже распознанной типовой активности и список параметров, уже покрытых сервером. Он обязан анализировать только дополнительные явно сообщённые факты и предлагать ЦО/ОН для них; саму типовую активность, её обычные repetitions/distance/duration и её impact-profile он повторно не анализирует.

3. **Типовая активность не найдена.** Никакая template-связь не записывается. Работает прежний полный A3.1 review-first путь с человеком в контуре проверки.

Если к сообщению приложено изображение и текст совпал с типовой активностью, residual-review принудительно остаётся включённым: первый Nano не видит содержимое изображения, поэтому дополнительное изображение должен проверить существующий A3.1 pipeline. Числовые факты из изображения по-прежнему не материализуются без поддержанного provenance-контракта.

## Почему стандартный AI для фактов сохраняется

Типовой профиль описывает повторно используемую структуру воздействия класса активности. Он не заменяет наблюдаемые факты конкретного эпизода.

Пример: «пробежал 5 км за 27 минут, пульс был 158, болело левое колено». Бег/5 км/27 минут покрываются template + серверными параметрами. Пульс и боль — конкретные факты этого эпизода. Они идут в residual A3.1 review, где AI предлагает, к каким листовым ЦО/ОН их присоединить, а запись остаётся review-gated.

## Дедупликация со старой системой

Добавляется read-only `activity_object_analytics_inputs_v1`. Он объединяет:

- подтверждённые физические `activity_object_facts`;
- виртуальные вклады `activity_event_virtual_parameter_contributions_v1`.

При совпадении `(activity_event_id + value_object_id + parameterCode)` физический подтверждённый факт имеет приоритет, а соответствующий виртуальный вклад не выдаётся. Это предотвращает двойной счёт, если один и тот же event/object/parameter уже был подтверждён старой review-first логикой.

Существующий analytics-profile переключается на этот единый read-source. Baseline/target/critical/refresh/inactivity остаются прежними.

## Масштабирование

- Одно реальное событие остаётся одной строкой события, а не размножается по количеству ЦО/ОН.
- Связи ЦО/ОН хранятся один раз в версионном impact profile.
- На AI для template identity уходит только shortlist названий; список ЦО/ОН провайдеру не отправляется.
- Текущий server-side shortlist допускает до 5000 активных профилей actor и максимум 24 кандидата в одном Nano-вызове. При существенно большей библиотеке следующим оптимизационным шагом будет отдельный индекс поиска кандидатов, а не увеличение prompt.
- Исторический backfill отсутствует. V2 не переписывает старые events/facts.

## Безопасность

- Production Supabase не использовался для подготовки кода.
- Новый RPC доступен только service_role.
- Browser roles не получают прямой SELECT на unified analytics view.
- AI matcher не пишет `activity_object_facts` и не выбирает ЦО/ОН.
- Standard A3.1 остаётся единственным AI-слоем, который делает предложения для дополнительных фактов, и факты по-прежнему создаются только после существующей проверки/Save.

## Evidence и точка продолжения

После deploy проверить минимум четыре сценария:

- чистая известная активность + repetitions — только Nano + серверные правила;
- та же активность с опечаткой/диктовкой — тот же template;
- известная активность + явный дополнительный факт — Nano + residual Standard A3.1;
- близкая, но другая активность — не должна ошибочно получить template.

После нескольких дней практики оценить false-match/no-match, частоту residual-review, необходимость псевдонимов типовых активностей и дневных агрегатов. Учебник по карточке типовой активности делать после стабилизации реального использования.

## DB POSTCHECK FIX2

Production APPLY был выполнен успешно. Первый исходный POSTCHECK содержал синтаксическую ошибку только в диагностическом SQL и не изменял БД. FIX1 выполнился, но проверка №15 была слишком жёстко привязана к внутреннему alias `f`, который `pg_get_viewdef()` вправе переименовывать. FIX2 заменил её на alias-agnostic проверку самой структуры физического приоритета. Production результат FIX2: `20/20 PASS`, `allPass=true`. Повторный APPLY и rollback не выполнялись. Канонический diagnostic-файл в source package заменён на FIX2, чтобы recovery/repo не сохраняли известную хрупкую проверку.

## Source release hotfix V3 — patcher analytics anchor

Первая попытка source release после DB POSTCHECK FIX2 была остановлена до commit на `APPLY_PATCH_TARGETS`: patch-tool вернул `ANALYTICS_FACT_SOURCE_COUNT_MISMATCH:0`. Новый runtime-код не был закоммичен; launcher выполнил `git reset --hard` и `git clean`, итог `ROLLBACK=PASS`, HEAD снова `5f1d8d24a25a3294424293192a82680d0a947d09`, рабочее дерево чистое.

Причина была не в runtime-архитектуре и не в БД, а в слишком хрупком многострочном текстовом anchor patcher-а для `loadFacts()`. V3 не меняет семантику runtime. Patcher теперь ограничивает замену телом функции `loadFacts()` и меняет только `.from("activity_object_facts")` на `.from("activity_object_analytics_inputs_v1")`. Он не зависит от пробелов между `.from()` и `.select()` и fail-closed проверяет ровно один старый источник внутри `loadFacts()`. Перед любыми изменениями repo launcher запускает отдельный `PATCH_TOOL_SELF_TEST`.

## Source release hotfix V4 — recovery whitespace

Вторая попытка source release (launcher V3) успешно прошла patch-tool self-test, применение runtime-патчей, основной validator `67/67`, regression-проверки профиля `54/54`, ветки ЦО `32/32`, A3.1 `125/125`, ESLint и полный production `next build`. Ошибка появилась только после staging на `git diff --cached --check`: в recovery-файле была строка `Дата: 2026-08-21` с двумя завершающими пробелами и одна лишняя пустая строка в конце файла. Commit не создавался; launcher выполнил rollback, итог `ROLLBACK=PASS`, HEAD восстановлен на `5f1d8d24a25a3294424293192a82680d0a947d09`, рабочее дерево чистое.

V4 не меняет runtime-код, SQL, matcher, patch-tool или согласованную архитектуру. Исправлена только текстовая чистота recovery/evidence и усилен package-validator: теперь он до изменения Git проверяет все новые текстовые payload-файлы на trailing whitespace и ровно один завершающий newline, чтобы аналогичный precommit-дефект больше не дошёл до staging.
