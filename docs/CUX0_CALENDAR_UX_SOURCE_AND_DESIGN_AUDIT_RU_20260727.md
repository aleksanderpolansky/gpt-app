- `main @ 48ba74da68a17ac489eaf12b3e538fefcd0c4f13`
- PP1A и PP1B уже создали каноническую модель `activity_events` и календарную проекцию только для `exact`.

- Визуальный ориентир: `High-Fidelity Dashboard Design.zip`.

## Подтверждённая целевая концепция

Основной сценарий:

1. Пользователь открывает календарь.
2. Нажимает «Добавить».
3. Над календарём раскрывается встроенный composer.
4. Пользователь пишет или диктует активность обычными словами.
5. AI заполняет ручные поля, но не придумывает отсутствующие значения.
6. Пользователь может исправить любой результат.
7. Активность сохраняется в канонический `activity_events`.
8. Activity Container открывается только по запросу через «Подробнее».

## Текущее устройство source

### Календарь

`src/app/calendar/page.tsx` является тонкой оболочкой над
`src/app/calendar-rebuild/CalendarRebuildClient.tsx`.

`CalendarRebuildClient.tsx` — монолитный клиент примерно на 2000 строк. В нём одновременно находятся:

- загрузка `calendar_events` и `time_blocks`;
- day/week/month представления;
- четыре крупные KPI-карточки;
- фильтры;
- grid/list;
- редактирование и отмена событий;
- журнал календаря;
- модальное окно деталей.

Отдельных режимов `timeline/gantt` и модели task shelf сейчас нет.

### Добавление активности

Текущий маршрут двухшаговый:

- `/calendar/add` — отдельная страница ввода текста;
- `/calendar/activity-review` — обязательный большой Activity Container.

Это противоречит подтверждённому UX: composer должен раскрываться внутри календаря, а контейнер должен быть необязательным.

### Semantic Preview

`src/app/api/calendar/activity-review/semantic-preview/route.ts` содержит старое системное правило:

- при отсутствии даты/времени ставить завтра 08:00;
- при отсутствии длительности ставить 30 минут.

Такие же значения присутствуют в fallback-нормализации. Поэтому preview продолжает показывать искусственные значения, хотя PP1B write path их уже не сохраняет.

### Timing parser

`src/lib/activity/pp1/activityTiming.ts` до CUX1:

- находил только первое время;
- не извлекал окончание из интервала;
- не понимал названия месяцев;
- проверял общий маркер `до` как deadline раньше exact-интервала;
- не вычислял длительность по началу и окончанию;
- не переносил год корректно через границу года.

Это объясняет Production-дефекты:

- `с 18:00 до 18:45` → deadline;
- необходимость повторного ручного ввода;
- неправильный год в model preview;
- неправильное окончание после ручной корректировки.

### Выбор Value Objects

`PlannedTargetSelectorPp1`:

- загружает весь список `/api/value-objects` одним запросом;
- показывает плоский список чекбоксов;
- не имеет поиска;
- не имеет фильтра branch policy;
- не имеет фильтра уровня root/intermediate/leaf;
- не показывает полный путь объекта;
- не поддерживает recent/favorite/AI suggestions.

`/api/value-objects` GET сейчас возвращает все actor-owned объекты и не принимает поисковые параметры.

### Задачи над календарём

`/api/calendar-rebuild/events` читает только:

- `calendar_events`;
- `time_blocks`.

Он не читает planned `activity_events` с режимами:

- `unscheduled`;
- `date_only`;
- `date_range`;
- `deadline`.

Поэтому task shelf потребует отдельного read contract.

### Многодневные события

Календарная сетка группирует событие только по дате его начала (`eventDateKey`). Многодневное событие не строит полосу через несколько дней. Нужна отдельная layout-модель multiday bars.

### Персональные правила AI

В source нет канонической таблицы или API для:

- системного текста правил по локали;
- пользовательской редактируемой копии;
- reset к системному тексту;
- истории версий;
- тестирования правила без записи активности.

## Архитектурный вывод

Календарь не следует латать одной большой заменой. Нужен контролируемый rebuild поверх PP1:

1. сначала исправить timing correctness;
2. затем встроить composer и убрать обязательный контейнер;
3. затем добавить editable AI rules;
4. затем масштабируемый VO selector и task shelf;
5. затем multiday/timeline/gantt;
6. после этого завершить визуальную адаптацию и мобильный UX.
