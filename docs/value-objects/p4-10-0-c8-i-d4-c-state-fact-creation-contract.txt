Core Principle
--------------
A state hook or candidate state signal is not a state fact.

A candidate can become a state fact only after passing all gates:

1. dimension lookup gate
2. claim policy gate
3. source type gate
4. evidence gate
5. forbidden overclaim gate
6. safe wording gate
7. confidence / claim strength gate
8. privacy / sensitivity gate
9. value window / expiry gate
10. correction / rollback readiness gate

If any required gate fails, the candidate must be rejected or kept as shadow-only.

Definitions
-----------
1. category candidate
A semantic candidate produced from free text or activity analysis.
It describes meaning, role, object, participant, purpose, metric, or context.

It must not be persisted as a state fact directly.

2. state hook candidate
A signal that an activity may affect or indicate a state dimension.
Example:
- "helped child with math" may create a family_care_load_signal hook.
- "walked to work" may create a physical_activity_load hook.
- "sent 5 sales emails" may create a pipeline_building_effort hook.

It is not a state fact yet.

3. state signal candidate
A structured candidate ready for governance gates.
It references:
- user
- value object
- state dimension key
- proposed value
- source
- evidence
- confidence
- claim strength
- validity window
- privacy level
- wording

It still must not be persisted until all gates pass.

4. state fact
A controlled internal record in value_object_state_facts.
It is not an absolute medical, psychological, legal, financial, or business truth.
It is a governed planning signal, proxy signal, system estimate, or user-confirmed context flag.

Allowed State Fact Types
------------------------
D4-C allows only the following safe output types:

1. system_estimate
A conservative estimate derived from safe activity data or rule output.
Example:
- 30 minutes of German practice may increase language_practice_balance.

2. proxy_only
A proxy signal that must not be worded as direct fact.
Example:
- fatigue_signal
- stress_load_estimate
- family_care_load_signal

3. user_confirmed
A fact/signal that requires explicit user confirmation.
Example:
- financial_pressure_signal

4. rule_produced_planning_signal
A deterministic planning signal produced by an approved internal rule.
Example:
- 5 sales emails -> pipeline_building_effort.

5. ai_assisted_shadow_candidate
AI may propose a candidate, but it remains shadow-only until governed by rules or user confirmation.

6. corrected_or_rollbackable_signal
A fact that can be corrected, revoked, superseded, or recalculated after activity correction.

Forbidden State Fact Types
--------------------------
The system must reject candidates that imply:

- medical diagnosis
- hormonal measurement without direct source
- psychological diagnosis
- legal conclusion
- employer evaluation
- creditworthiness assessment
- hidden financial inference
- hidden health inference
- confirmed income without explicit source
- confirmed client acquisition without explicit source
- confirmed deal closure without explicit source
- confirmed muscle growth or fat loss without direct measurement
- child development scoring
- social ranking
- irreversible personal profile judgment

Forbidden wording examples:

- "high cortisol"
- "low dopamine"
- "depression"
- "burnout diagnosis"
- "client acquired"
- "deal closed"
- "income confirmed"
- "child improved"
- "muscle growth confirmed"
- "financially unreliable"
- "bad employee"
- "poor parent"

Safe wording examples:

- "stress load estimate increased based on indirect activity signals"
- "fatigue signal detected as proxy only"
- "pipeline building effort recorded"
- "language practice balance improved"
- "financial pressure signal recorded because the user explicitly confirmed it"
- "family care load signal increased due to caregiving-related activity"

Required Candidate Fields

Gate 1 — Dimension Lookup Gate
------------------------------
Input:
- candidate.dimensionKey

Process:
1. Look up public.state_dimensions by dimension_key.
2. Check is_active = true.
3. Read:
   - id
   - claim_policy
   - default_privacy_level
   - is_sensitive
   - domain
   - title

Accept if:
- dimension exists
- dimension is active

Reject if:
- dimension does not exist
- dimension is inactive
- dimension_key is blank
- candidate tries to create a new dimension automatically

Output:
- resolved dimension_id
- resolved claim_policy
- resolved sensitivity
- resolved default privacy

D4-C rule:
No automatic dimension creation.
No AI-created active dimension.
No uncontrolled state dimension expansion.

Gate 2 — Claim Policy Gate
--------------------------
Claim policies:

1. system_estimate
Can be created from approved deterministic rules or safe system logic.
AI-only candidates must remain shadow-only unless validated by rules.

2. proxy_only
Can be created only as proxy signal.
Must not use direct diagnostic wording.
Must not claim causality stronger than evidence allows.

3. user_confirmed
Can be persisted only if explicit user confirmation exists.
No hidden inference from behaviour.

Policy mapping:

- attention_load:
  allowed if source_type is rule or system.
  AI-only stays shadow.

- family_care_load_signal:
  proxy only.
  allowed as proxy from activity semantics.
  no claim about family quality or child outcome.

- fatigue_signal:
  proxy only.
  allowed only as indirect fatigue signal.
  no medical conclusion.

- financial_pressure_signal:
  user_confirmed only.
  allowed only with explicit user statement.
  no inference from spending, job search, or behaviour.

- stress_load_estimate:
  proxy only.
  no hormonal, psychiatric, or diagnostic wording.

- pipeline_building_effort:
  allowed as system_estimate from safe business activity.
  no confirmed client/deal/income claim.

Reject if:
- candidate claim policy is stronger than dimension policy
- user confirmation is missing for user_confirmed dimension
- proxy_only dimension is worded as direct fact
- system_estimate is created from unvalidated AI-only output

Gate 3 — Source Type Gate
-------------------------
Allowed source_type values already supported by DB:

- manual
- user_confirmed
- rule
- ai
- system
- import
- correction

D4-C source rules:

manual:
- allowed only for user-provided direct input
- must preserve evidence text
- may require user confirmation for sensitive dimensions

user_confirmed:
- allowed for user-confirmed signals
- required for financial_pressure_signal
- must include userConfirmationText or equivalent evidence

rule:
- allowed for deterministic internal rules
- must include ruleId and ruleVersion

ai:
- shadow-only by default
- cannot directly persist sensitive or high-claim facts
- can propose candidates for later review/rule validation

system:
- allowed for deterministic platform-generated planning signals
- must include internal explanation

import:
- allowed only if source/evidence includes imported source metadata
- no direct medical/financial interpretation unless import source is explicitly appropriate and future governance allows it

correction:
- allowed for corrected/revoked/superseded facts
- must reference previous fact or corrected activity

Reject if:
- source_type is unknown
- source_type is ai and candidate attempts direct persistence
- source_type lacks required evidence
- source_type is incompatible with dimension claim_policy

Gate 4 — Evidence Gate
----------------------
Every persisted state fact must have evidence_json as a JSON object.

Required evidence content by source:

activity_event evidence:
- activityEventId
- userId
- inputText or title
- durationMinutes if used
- activity status if relevant
- category or rule evidence if derived

user_confirmation evidence:
- confirmation text or confirmation action
- timestamp
- dimensionKey confirmed
- exact safe meaning confirmed

rule evidence:
- ruleId
- ruleVersion
- matched fields
- deterministic explanation
- source activity or object reference

AI evidence:
- prompt/output reference or explanation
- must be shadow-only unless future governance approves
- must include notAStateFactYet = true

correction evidence:
- previousFactId or sourceActivityEventId
- correction reason
- correction timestamp
- correctedBy actor/system

Reject if:
- evidence_json is empty for non-manual internal facts
- evidence cannot explain why the fact exists
- evidence does not match the source_type
- evidence attempts to hide sensitive inference

Gate 6 — Safe Wording Gate
--------------------------
Every accepted fact must include safe wording.

Safe wording must:

- use "signal", "estimate", "proxy", or "user-confirmed" when appropriate
- avoid diagnostic language
- avoid hidden inference
- avoid deterministic outcomes
- avoid irreversible profile judgment
- state the evidence source plainly

Required wording fields:

safeWording.shortLabel:
- short UI-safe label

safeWording.userVisibleExplanation:
- explanation that can be shown to user

safeWording.internalExplanation:
- more technical internal explanation

Examples:

"Fatigue signal"

"Indirect fatigue signal based on activity context. This is not a medical conclusion."

stress_load_estimate:
shortLabel:
"Stress load estimate"

userVisibleExplanation:
"Estimated stress load based on indirect activity/context signals. This is not a hormonal or psychological diagnosis."

financial_pressure_signal:
shortLabel:
"Financial pressure signal"

userVisibleExplanation:
"Financial pressure signal recorded from explicit user confirmation."

pipeline_building_effort:
shortLabel:
"Pipeline building effort"

userVisibleExplanation:
"Business development effort detected from outreach-related activity."

Gate 7 — Confidence and Claim Strength Gate
-------------------------------------------
confidence:
- must be numeric
- must be between 0 and 1
- default should not be 1 unless direct user confirmation or deterministic rule is strong

claimStrength:
- must be integer
- must be between 0 and 5

Recommended claimStrength scale:

0:
shadow-only candidate, not persisted as fact

1:
weak proxy signal

2:
ordinary planning signal / conservative estimate

3:
strong user-confirmed or deterministic operational fact

4:
direct measurement from trusted source

5:
reserved for future direct verified source with strict governance

D4-C rule:
For now, do not use claimStrength 4 or 5 unless future direct-source governance is added.

Recommended defaults:

- ai shadow candidate:
  confidence <= 0.70
  claimStrength = 0

- proxy_only signal:
  confidence <= 0.75
  claimStrength = 1

- system_estimate from rule:
  confidence <= 0.85
  claimStrength = 2

- user_confirmed:
  confidence <= 0.95
  claimStrength = 3

Reject if:
- confidence is outside 0..1
- claimStrength is outside 0..5
- claimStrength is too high for claim_policy
- AI-only candidate asks for claimStrength > 0

Gate 8 — Privacy / Sensitivity Gate
-----------------------------------
Default privacy:
- private

D4-C rule:
All current seeded dimensions must default to private.

Sensitive dimensions:
- family_care_load_signal
- fatigue_signal
- financial_pressure_signal
- physical_activity_load
- recovery_need
- stress_load_estimate

Sensitive facts must not be public by default.

Allowed D4-C privacy levels:
- private

Blocked for D4-C:
- shared_with_org
- public_masked
- public

Reason:
Public/shared visibility requires a separate later governance phase.

Reject if:
- candidate tries to persist sensitive dimension as public
- candidate tries to share health/finance/family proxy outside private scope
- candidate overrides default privacy without approved future governance

Gate 9 — Valid Window / Expiry Gate
-----------------------------------
Every state fact should define whether it is:

1. event-scoped
2. current/short-term
3. daily
4. weekly
5. baseline/long-lived

Recommended valid windows:

event-scoped:
- valid_from = activity started_at or created_at
- valid_to = activity ended_at or null if not meaningful

short-term proxy:
- valid_from = now or event time
- valid_to = bounded expiry
- examples: fatigue_signal, stress_load_estimate

daily planning signal:
- valid_from = start of day or event time
- valid_to = end of day or next recalculation

weekly planning signal:
- valid_from = week start
- valid_to = week end or next recalculation

baseline:
- not used in D4-C without special future governance

Reject if:
- valid_to < valid_from
- sensitive proxy is created as indefinite baseline without explicit future governance
- expiry is missing for proxy-only signals unless explicitly event-scoped

Gate 10 — Correction / Rollback Readiness Gate
----------------------------------------------
Every persisted fact must be correction-ready.

Current DB supports correction_status:
- active
- corrected
- revoked
- superseded

D4-C required metadata:

metadata.rollbackable = true
metadata.createdByContract = "state-fact-creation-contract-v1"
metadata.sourceActivityEventId if derived from activity
metadata.previousFactId if correction/supersession
metadata.recalculationGroupId if later needed

Required correction behaviours:

1. User correction:
If user says the state fact is wrong, it can be revoked or superseded.

2. Activity correction:
If source activity duration/time/status changes, dependent facts must be recalculated or revoked.

3. Activity deletion:
If source activity is deleted/revoked, dependent facts must be revoked or marked superseded.

4. Rule update:
If rule version changes, facts generated by old rule version must be traceable.

Reject if:
- candidate cannot be traced to source/evidence
- candidate cannot be corrected/revoked
- metadata does not allow future audit
