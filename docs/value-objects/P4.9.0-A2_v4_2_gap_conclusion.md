# P4.9.0-A2 — v4.2 gap conclusion after live schema inventory

Date: 2026-05-18
Status: DONE

## Target v4.2 model

According to v4.2, the target flow is:

free text / app action -> Activity Event -> global categories / semantic elements -> derived Value Objects -> Event to ValueObject exposure links -> aggregates / snapshots -> future analytics / UI

Core target rules:

- a global category is not the same as a personal or enterprise Value Object
- each used category can create a personal or enterprise Value Object
- the full meaning of an activity can also create its own Value Object
- Activity Event stores real time once
- analytics can project the same event onto multiple Value Objects
- exposure_minutes can exceed 24h in total analytical sums
- MVP uses parent/child only
- no typed relation edges now
- no tags/entity_tags now
- no full UI/UX now

## What already exists and can be reused

### Reusable as-is or nearly as-is

- activity_events as source-of-truth event table
- contextual_categories as initial global category/rubricator layer
- activity_processing_logs as audit/debug layer
- daily_aggregates and current_snapshots as general aggregate/snapshot foundation
- value_objects as base commercial/generic Value Object table
- value_object_instances as existing event-derived instance layer
- value_object_daily_aggregates and value_object_state_snapshots as VO analytical foundation

## Main gaps against v4.2

### Gap 1 — no clear category-to-ValueObject bridge

There is no confirmed minimal table like:

- value_object_category_links

Needed purpose:

- record which global category / semantic element created or defines a given Value Object
- support category combinations that produce a derived Value Object
- keep global category separate from user/enterprise Value Object

### Gap 2 — event links target value_object_instances, not direct Value Objects

Current table:

- activity_event_value_object_instance_links

Current link target:

- value_object_instance_id

v4.2 target needs a simple analytical projection:

- event_id
- value_object_id
- exposure_minutes
- source
- confidence

Decision: do not delete old table now. Add a v4.2-compatible projection/link layer or extend carefully after focused inspection.

### Gap 3 — relation_type exists in current link model

Current link table has relation_type.

v4.2 says: no typed relation edges on MVP. Only parent/child belongs to Value Objects.

Decision: do not use relation_type as the central v4.2 semantic relation model. Keep it only for legacy/compatibility if needed.

### Gap 4 — exposure_minutes is missing

Current link model has weight and confidence but not exposure_minutes.

v4.2 needs exposure_minutes because one real Activity Event can analytically count toward many Value Objects.

### Gap 5 — value_objects lacks v4.2 canonical fields

Current value_objects does not yet clearly contain:

- parent_value_object_id
- entity_protocol_characteristics_json
- needs_user_review
- ui_visibility / visibility for object cloud
- category-derived origin fields

Decision: add minimal fields/tables only after code inventory and migration design.

## Technical decision

Do not rewrite or drop existing VO/VOI tables.

Proceed with additive design:

1. document current schema
2. inspect runtime code references
3. design minimal v4.2 migration
4. add category-to-VO links
5. add or create event-to-VO exposure link layer
6. add parent/child support to value_objects
7. keep free-text processor as first input path
