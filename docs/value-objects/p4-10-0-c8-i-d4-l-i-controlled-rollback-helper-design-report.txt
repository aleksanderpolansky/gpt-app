Purpose:
Design the future controlled rollback helper contract for value_object_state_facts without implementing runtime rollback yet.

Core principle:
Rollback is not a delete.
Rollback is not an update-by-state_fact_id-alone operation.
Rollback is a controlled state transition that must:
1. prove the authenticated user context;
2. prove ownership/permission through actor/value_object relationships;
3. prove the target state fact belongs to the same value_object and user context;
4. apply only an allowed correction_status/valid_to style change in a future implementation;
5. create an audit event in value_object_state_fact_audit_events;
6. remain idempotent.

Hard prohibitions:
- Do not delete value_object_state_facts.
- Do not update a state fact by state_fact_id alone.
- Do not rollback another user's state fact.
- Do not rollback through public/client-side direct table access.
- Do not create a generic update endpoint.
- Do not expose a read/write audit API to public clients.
- Do not treat a public/catalog Value Object as write permission.
- Do not allow AI-only rollback.
- Do not allow placeholder UUIDs.
- Do not bypass the actor/value_object ownership resolver.
- Do not treat rollback as correction; correction is a separate lifecycle.

Required validation gates:
1. Request shape gate:
   - stateFactId must be valid UUID.
   - valueObjectId must be valid UUID.
   - requestTraceId must be non-empty.
   - idempotencyKey must be non-empty.
   - reason must be non-empty.
   - sourceRoute/helperVersion/contractVersion/d4GateVersion must be non-empty.

2. Auth gate:
   - Resolve authenticated app user.
   - Resolve actor/person context if required by existing auth resolver.
   - Reject if authenticated context is missing.
   - Reject placeholder UUIDs.

3. Target Value Object ownership gate:
   - Load value_object by valueObjectId.
   - Verify write permission through owner_actor_id / allowed actor relation.
   - Public/catalog visibility is not write permission.
   - Reject if requester is not allowed to modify facts for that Value Object.

4. State fact target gate:
   - Load value_object_state_facts by stateFactId and valueObjectId together.
   - Do not load by stateFactId alone for authorization decision.
   - Verify the state fact belongs to the same valueObjectId.
   - Verify the state fact is not already rolled_back/superseded/invalid in a future status field.
   - Verify source and confidence are not used as permissions.

5. Allowed update scope gate:
   Future runtime implementation may update only tightly scoped rollback fields, for example:
   - correction_status
   - valid_to
   - metadata_json rollback subobject
   - updated_at if such column exists
   No other value_json/source/evidence/dimension/value_object fields may be changed by rollback.

6. Audit event gate:
   - Insert one value_object_state_fact_audit_events row.
   - action_type should be "rolled_back" for successful rollback.
   - action_type should be "rejected_rollback" for rejected rollback attempts if policy later decides to log rejected attempts.
   - audit event must include:
     - user_id
     - actor_id when available
     - value_object_id
     - state_fact_id
     - dimension_key
     - reason
     - request_trace_id
     - idempotency_key
     - source_route
     - helper_version
     - contract_version
     - d4_gate_version
     - previous_valid_to
     - new_valid_to
     - evidence_json
     - metadata_json
   - The audit event must be inserted in the same transaction as the future state fact update.

7. Idempotency gate:
   - The unique audit index is:
     user_id + state_fact_id + action_type + idempotency_key
   - Repeated rollback request with the same idempotency key must not create duplicate audit events.
   - Repeated rollback request must return "already_rolled_back" or an idempotent success response, not perform another update.

Required future transaction behavior:
- Future rollback runtime must be transactional.
- State fact update and audit event insert must succeed together or fail together.
- No partial rollback is allowed.

Relationship to correction:
- Rollback invalidates or closes a state fact.
- Correction supersedes a state fact and creates/references a corrected fact.
- Correction needs a separate helper design after rollback helper design/proof.
- Do not mix rollback and correction into one generic mutation endpoint.

Relationship to Next Best Action:
- Next Best Action must ignore rolled-back/invalid state facts.
- Until rollback runtime exists, NBA must use only valid, non-superseded facts and conservative signals.
- Audit history is not itself a recommendation signal unless later explicitly modelled.
