# P4.10.0-C4 — minimal free-text v1 design decision

Date: 2026-05-19
Scope: Free-text processor v1
Status: DESIGN DECISION — no code change yet

## Context

P4.10.0-C1/C2/C3 runtime inventory is closed.

Latest confirmed commit before this decision:

- 99cfcaa Inventory free-text value object runtime

## Main decision

Free-text v1 must be implemented above the bridge layer.

Do not start by rewriting valueObjectBridge.ts.

Reason:

- valueObjectBridge.ts already writes the important v4.2 projections;
- it already handles activity_event_value_object_links;
- it already handles value_object_usage_aggregates;
- it already handles value_object_category_links;
- it already handles value_object_instances and state/daily/snapshot projections;
- the missing part is not projection writing, but classification/mapping for unknown input_text.

## Current known-template runtime path

Existing route flow:

1. record / complete / confirm route creates or updates activity_events.
2. Route calls ensureActivityEventRubricatorClassificationForKnownTemplate.
3. Known-template lifecycle creates or reuses entity_classifications.
4. Route calls processActivityValueObjectBridge.
5. activityValueObjectLifecycle calls rubricatorValueObjectMapper.
6. activityValueObjectLifecycle then calls valueObjectBridge.
7. valueObjectBridge writes legacy and v4.2 projections.

## Free-text v1 target path

Target runtime flow:

1. User submits simple free text.
2. activity_event is created with input_text and without a known template.
3. Existing known-template classifier either skips or returns no mapping.
4. Free-text v1 fallback classifier/mapper analyzes input_text.
5. Fallback mapper returns a small controlled mapping compatible with the existing bridge contract.
6. Existing valueObjectBridge writes the same projections as for known templates.

## Insertion point

The preferred insertion point is activityValueObjectLifecycle.ts.

Reason:

- routes already call processActivityValueObjectBridge;
- this wrapper already connects mapping and bridge;
- adding fallback here avoids duplicating code in record, complete, and confirm routes;
- known-template path can remain unchanged;
- bridge can remain unchanged unless exact type inspection later proves a small adapter is needed.

## Preferred implementation shape

Add a new helper module later:

- lib/activity/freeTextValueObjectMapper.ts

Potential exported function:

- resolveValueObjectMappingsFromFreeTextForActivityEvent

This helper should return a mapping result compatible with the existing bridge path.

activityValueObjectLifecycle.ts should do:

1. Try existing resolveValueObjectMappingsFromRubricatorForActivityEvent.
2. If mappings exist, use them unchanged.
3. If no mappings exist and activity_event.input_text exists, try free-text fallback.
4. If fallback returns mappings, pass them to existing processValueObjectBridgeForActivityEvent.
5. If fallback also returns no mappings, keep current skip behavior.

## Free-text v1 scope

Free-text v1 is deliberately small.

It should support only a limited deterministic test case first:

- walked to work for 15 minutes
- walking to work 15 minutes
- went to work on foot for 15 minutes

Expected semantic output:

- one Value Object for walking / walking practice;
- optionally one Value Object for commuting to work, if categories and mapping contract allow it without schema changes;
- event exposure_minutes should come from event duration;
- created/updated Value Objects should be marked as needing review if generated from free text.

## What must be inspected before coding

Before writing implementation code, inspect exact TypeScript contracts for:

- ProcessActivityValueObjectBridgeResult
- RubricatorValueObjectMappingResult
- ProcessValueObjectBridgeInput
- mapping object type consumed by processValueObjectBridgeForActivityEvent
- required fields for category link creation
- whether category_id/contextual category must exist before bridge can link categories

## No new schema now

No DB migration is planned for C4/C5 unless exact implementation proves a missing required field.

Known live schema is already sufficient for the foundation:

- value_objects
- value_object_category_links
- activity_event_value_object_links
- value_object_usage_aggregates
- value_object_daily_aggregates
- value_object_cloud_profiles_v1
- value_object_hierarchy_profiles_v1

## Explicit non-goals

- Do not introduce AI classifier in v1.
- Do not introduce OpenAI calls in v1.
- Do not introduce typed Value Object relation edges.
- Do not introduce tags/entity_tags.
- Do not redesign valueObjectBridge.
- Do not redesign record / complete / confirm routes.
- Do not build final UI.
- Do not process external calendar/wearable/NFC data now.

## Risk controls

- known-template flow must remain unchanged;
- record / complete / confirm routes must remain route-stable;
- fallback must be deterministic and easy to test;
- fallback must fail safely and return skipped when input_text is not recognized;
- generated Value Objects should be marked for review where possible;
- no destructive DB changes;
- no broad automatic category explosion.
