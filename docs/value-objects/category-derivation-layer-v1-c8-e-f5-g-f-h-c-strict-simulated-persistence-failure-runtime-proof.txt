1. Purpose

This proof documents strict-mode runtime behavior for the Category Derivation complete-route adapter when a persistence-layer failure is safely simulated before real DB run creation.

The tested scenario is:

- endpoint:
  /api/activity/debug/category-derivation-complete-route-adapter-failure-test

- scenario:
  simulated_persistence_failure

- mode:
  shadow_persist

- failActivityComplete:
  true

The purpose is to prove that the same simulated persistence failure which is non-blocking when failActivityComplete=false becomes a controlled blocking adapter result when failActivityComplete=true, while still avoiding production writes, OpenAI calls, schema changes, RLS changes and /api/activity/complete changes.

4. Why the strict proof needed route changes

The original debug route had guards that were intentionally written for the first non-blocking failure-behavior proof only.

Two guards had to be relaxed only for:

- scenario=simulated_persistence_failure
- expectFailActivityComplete=true
- CATEGORY_DERIVATION_ROUTE_RUNNER_FAILS_ACTIVITY_COMPLETE=true

The relaxed guards are debug-route-only and do not affect /api/activity/complete.

7. What this proof demonstrates

This proof demonstrates that in shadow_persist mode with failActivityComplete=true:

- the adapter is enabled;
- routeRunner executes;
- derivation candidates are produced;
- the simulated persistence failure occurs before real run creation;
- the failure is normalized as simulated_persistence_failure;
- the adapter becomes blocking:
  adapterResult.ok=false;
- no category_derivation_runs row is created;
- no activity_category_derivations rows are created;
- no production_persist is enabled;
- OpenAI is not called;
- schema, migrations, RLS and permissions are not modified;
- /api/activity/complete remains unchanged.

8. Anti-regression notes

Do not remove the strict proof guard exceptions without understanding why they exist.

The exceptions are allowed only for:

- scenario=simulated_persistence_failure
- expectFailActivityComplete=true
- CATEGORY_DERIVATION_ROUTE_RUNNER_FAILS_ACTIVITY_COMPLETE=true

Do not generalize this to other scenarios without a separate proof.

Do not simulate persistence failure by damaging the real DB.

Do not use DROP, ALTER TABLE, broken RLS, broken permissions or schema corruption for this proof type.

The stable strict-mode signal is:

- adapterResult.ok=false
- adapterResult.reason=simulated_persistence_failure
- routeRunner.executed=true
- routeRunner.persisted=false
- persistenceDerivationRowsCreated=0
