Purpose of this design:
Define how controlled state facts may be corrected, expired, or rolled back in the future without creating a dangerous update/delete path now.

Core decision:
Do NOT implement runtime rollback/correction in this step.
First, define strict rules and gates. Runtime route/helper implementation may be a later step only after this design is accepted.

Terminology:
1. Rollback:
   The user/system cancels the effect of a previously created state fact.
   The original row must not be deleted.
   The row may later be marked as rolled_back/expired through a controlled update path.
2. Correction:
   The original fact was incomplete or wrong.
   The old row should be marked corrected/superseded/expired.
   A new corrected fact may be created through the same controlled persistence contract.
3. Expiry:
   A fact naturally stops being valid after valid_to.
   Expiry does not necessarily mean the fact was wrong.
4. Audit:
   Every correction/rollback must be explainable after the fact.
   No silent update is allowed.

Hard rollback/correction rules:
1. No delete.
2. No generic update endpoint.
3. No client-side direct update to value_object_state_facts.
4. No update by state_fact_id alone.
5. No service-role-backed rollback route without authenticated actor resolution.
6. No rollback of another user's state fact.
7. No rollback if the target Value Object does not belong to the authenticated actor or allowed organization context.
8. No rollback if metadata_json.rollbackable is not true, unless an admin-only emergency path is separately designed.
9. No rollback if correction_status is already rolled_back/corrected/superseded/expired.
10. No rollback without reason.
11. No correction without linking old fact and new fact.
12. No raw evidence deletion.
13. No proof artifact manual deletion.
14. No AI-only rollback.
15. No hidden production debug rollback.

Minimum future rollback request envelope:
- mode: controlled_rollback
- confirmControlledRollback: true
- stateFactId
- reason
- requestedAt
- clientTraceId
- expectedCurrentCorrectionStatus: active
- expectedRollbackable: true

Minimum future correction request envelope:
- mode: controlled_correction
- confirmControlledCorrection: true
- stateFactIdToCorrect
- reason
- correctedCandidate
- requestedAt
- clientTraceId
- expectedCurrentCorrectionStatus: active
- expectedRollbackable: true

Required future rollback gates:
1. Request envelope validation.
2. Authenticated actor resolution.
3. Target state fact lookup.
4. State fact ownership check by user_id and/or actor/Value Object ownership.
5. Target Value Object access check.
6. Dimension lookup.
7. Current correction_status check.
8. rollbackable metadata check.
9. Reason/evidence validation.
10. Idempotency key check for rollback request.
11. Controlled update only:
    - correction_status set to rolled_back or expired;
    - valid_to set to rollback timestamp;
    - metadata_json updated with rollback metadata.
12. Audit/event recording before or inside the same transaction if an audit table exists.
13. Response must disclose writesAttempted=true only if the controlled update was attempted.
14. Response must never expose unrelated private state facts.

Required future correction gates:
1. All rollback gates for the old fact.
2. Corrected candidate must pass D4-C/D4-F validation.
3. Corrected candidate must use the same or explicitly compatible dimension.
4. Corrected candidate must link to old fact through metadata_json.corrects_state_fact_id.
5. Old fact must link to new fact through metadata_json.corrected_by_state_fact_id if possible.
6. New fact creation must use existing controlled persistence helper pattern, not a separate bypass.
7. No correction may weaken privacy.
8. No correction may raise claim_strength beyond allowed policy.
9. Evidence must explain why the correction is being made.
10. Correction must be idempotent.

Recommended future database behavior:
- Prefer transactional controlled update for rollback/correction.
- Avoid delete.
- Avoid upsert.
- Avoid generic partial update payloads.
- Only allow a whitelisted update set:
  - correction_status
  - valid_to
  - metadata_json rollback/correction sub-object
  - updated_at
- If audit table is introduced later, record:
  - actor_id/user_id
  - state_fact_id
  - action_type: rollback/correction/expiry
  - previous correction_status
  - new correction_status
  - reason
  - request_trace_id
  - timestamp
  - route/helper versions
