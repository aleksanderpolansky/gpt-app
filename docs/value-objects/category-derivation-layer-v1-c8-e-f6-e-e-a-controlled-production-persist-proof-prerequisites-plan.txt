5. Main prerequisite questions

Before any controlled production_persist proof, we must answer:

- What cleanup or rollback policy is required before any production_persist proof?
- What metadata marker must identify proof/test activity events?
- Should the first production_persist proof be debug-only, real complete-route, or staged through a proof marker?
- Should failActivityComplete remain false for the first production_persist proof?
- What exact DB rows are allowed to be created in the controlled proof?
- What exact DB verification must prove no duplicates?
- What rollback or cleanup command is allowed after the proof?
- What must remain forbidden?

6. Cleanup / rollback prerequisite

Exact marker: cleanup / rollback policy

A controlled production_persist proof must not proceed until there is an explicit cleanup/rollback plan.

Minimum cleanup/rollback requirements:

- proof/test activity events must be distinguishable by metadata marker;
- category_derivation_runs created by the proof must be distinguishable by activity_event_id and version tuple;
- activity_category_derivations created by the proof must be distinguishable by derivation_run_id and activity_event_id;
- cleanup must not affect normal user data;
- cleanup must be optional after proof, not automatically destructive;
- cleanup commands must be reviewed separately before execution;
- SQL must not be run in PowerShell;
- any SQL cleanup must be run only in the approved SQL environment after a separate instruction step.

7. Proof/test metadata marker prerequisite

Exact marker: proof/test metadata marker

All proof/test rows must include enough metadata to identify the proof scenario.

Required marker concept:

- proof: P4.10.0-C8-E-F6-E-E-controlled-production-persist-proof
- purpose: controlled_production_persist_proof
- doNotUseAsCanonicalBusinessEvent: true
- cleanupEligible: true
- productionPersistProof: true
- createdBy: debug_setup_route or controlled_proof_route

The exact marker may be adjusted in a later implementation/proof plan.

8. Allowed proof scope

A first controlled production_persist proof may create only the rows required to prove the Category Derivation persistence path.

Allowed rows in a controlled proof may include:

- one started or completed activity_event created specifically for proof;
- one category_derivation_run for that proof activity_event and version tuple;
- expected activity_category_derivations rows for that derivation_run;
- related processing/debug rows only if already part of the existing controlled route behavior.

The proof must verify:

- exactly one routeRunner-specific completed run for the proof event;
- no duplicate completed runs;
- expected number of activity_category_derivations;
- second call does not duplicate rows if idempotency is part of the proof;
- production_persist mode was intentionally enabled only for the controlled proof context;
- OpenAI was not called;
- UI was not created;
- schema/RLS/permissions were not changed.

9. Recommended first production_persist proof shape

Recommended safest shape:

Option C / controlled proof-marker route.

The first production_persist proof should not be broad production_persist on /api/activity/complete for all normal events.

Recommended proof shape:

- use a debug/proof route or controlled proof setup route;
- create or use a proof/test activity_event with explicit metadata markers;
- enable production_persist only in a controlled dev-server environment;
- keep failActivityComplete=false;
- call the adapter through completeRouteIntegration, not directly through routeRunner;
- verify idempotency behavior;
- verify exact DB row counts;
- do not touch UI;
- do not call OpenAI;
- do not change schema, migrations, RLS or permissions.

10. failActivityComplete prerequisite

Initial production_persist proof should keep:

- CATEGORY_DERIVATION_ROUTE_RUNNER_FAILS_ACTIVITY_COMPLETE=false

Reason:

The first production_persist proof should verify durable persistence behavior without risking activity completion failure for normal route behavior.

Strict blocking mode may be considered only after non-blocking production_persist proof is proven safe.

11. production_persist mode prerequisite

A future proof may use:

- CATEGORY_DERIVATION_ROUTE_RUNNER_MODE=production_persist

But only after:

- cleanup/rollback policy is written;
- metadata marker strategy is written;
- proof route target is selected;
- exact expected DB rows are defined;
- idempotency verification is included;
- safety checks are defined;
- F6-E-E-B inspection confirms the existing routes/config support the controlled proof.
