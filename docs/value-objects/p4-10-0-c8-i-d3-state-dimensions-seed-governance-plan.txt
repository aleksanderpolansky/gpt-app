============================================================
1. Purpose of D3
============================================================

D3 prepares the first controlled seed set for public.state_dimensions.

The goal is not to create "medical facts", "hormonal conclusions", "psychological diagnoses", or "confirmed business results".

The goal is to define safe state dimensions that can later support:

- Next Best Action ranking
- weakest direction detection
- safe proxy-based state reasoning
- user-confirmed state facts
- similarity/relevance scoring
- recommendation feedback loops

D3 is a governance step before seed SQL.

No SQL should be executed in this step.

============================================================
2. Locked architectural rules
============================================================

The unified Value Object model remains unchanged.

Do not create mandatory Value Object subtypes such as:

- biological_value_object
- context_value_object
- state_value_object
- baseline_value_object
- commercial_value_object
- personal_value_object

State must be represented through state layers and state dimensions, not by changing the ontology of Value Objects.

Category candidates are not state facts.

Activity category derivation may produce signals, but state facts require one of the following:

- direct measurement
- user confirmation
- safe proxy estimate
- system calculation based on explicit non-sensitive data
- correction/audit trail

Similarity and relevance remain separate:

- similarity = semantic/category overlap
- relevance = state/context/rule/obligation/current-user-fit

============================================================
3. Safety principles
============================================================

The system must avoid unsafe claims.

Forbidden direct claims include, but are not limited to:

- "high cortisol"
- "low dopamine"
- "depression"
- "anxiety disorder"
- "testosterone increased"
- "hormonal imbalance"
- "medical condition"
- "child development improved"
- "client acquired"
- "deal closed"
- "income received"
- "muscle growth confirmed"
- "fat loss confirmed"
- "disease risk changed"

Allowed safer formulations:

- "stress load estimate"
- "fatigue signal"
- "recovery need"
- "attention load"
- "physical activity load"
- "learning progress signal"
- "pipeline building effort"
- "financial pressure signal"
- "family care load signal"
- "work responsibility load"
- "social interaction load"
- "language practice balance"

The system may say:

- "This activity may indicate increased recovery need."
- "This is a proxy signal, not a medical conclusion."
- "The system should ask the user to confirm this state."
- "The activity may contribute to pipeline-building effort."
- "The activity may reflect family care load."

The system must not say:

- "Your cortisol is high."
- "You are depressed."
- "Your testosterone improved."
- "You earned money from this activity."
- "You gained muscle."
- "Your child improved because of this activity."

============================================================
4. Claim policy meanings
============================================================

The state_dimensions.claim_policy field uses the following allowed values:

1. direct_measurement

Use only when the state dimension can be based on a direct source:
- wearable measurement
- manually entered numeric value
- imported measurement
- explicit structured source

Examples:
- sleep_duration_minutes
- heart_rate_average
- steps_count

2. proxy_only

Use when the system may only infer a weak/soft signal from activity context.

Examples:
- fatigue_signal
- stress_load_estimate
- family_care_load_signal

3. user_confirmed

Use when the system should ask the user before treating the signal as a fact.

Examples:
- subjective_energy_level
- perceived_stress_level
- mood_signal

4. system_estimate

Use when the system calculates a non-sensitive estimate from explicit activity data.

Examples:
- language_practice_balance
- physical_activity_load
- work_responsibility_load

5. blocked

Use for dimensions that should not be inferred or stored without future legal/medical/privacy design.

Examples:
- hormone_level_estimate
- mental_health_diagnosis
- disease_risk_estimate

============================================================
5. Privacy level meanings
============================================================

The state_dimensions.default_privacy_level field uses:

1. private

Default for almost all personal state dimensions.

2. shared_with_org

Only for future enterprise/workflow contexts where the user explicitly shares limited data.

Not used in D3 seed unless absolutely necessary.

3. public_masked

Only for future aggregated or anonymized public reporting.

Not used in D3 seed.

4. public

Not used for sensitive or personal state dimensions.

D3 default:

- private

7. Dimensions intentionally not included in first seed
============================================================

The following should not be included in D3 seed:

- cortisol_level
- dopamine_level
- testosterone_level
- depression_risk
- anxiety_disorder
- child_development_score
- muscle_growth_confirmed
- income_confirmed
- client_acquired
- deal_closed
- burnout_diagnosis

Reason:

These require medical, psychological, financial, legal, or outcome confirmation logic that is outside the safe MVP state-dimensions seed.

They may be represented later only as:

- user-confirmed context
- imported verified measurement
- professional/medical integration
- explicit non-sensitive proxy
- aggregated non-identifying analytics

============================================================
8. D3 seed SQL preparation rules
============================================================

When D3 seed SQL is prepared later:

1. It must use insert ... on conflict (dimension_key) do update or do nothing.
2. It must not modify existing non-D3 tables.
3. It must not create new structural tables.
4. It must not create new Value Object types.
5. It must not create state facts for users.
6. It must only seed the state_dimensions dictionary.
7. It must keep default_privacy_level mostly private.
8. It must mark sensitive dimensions clearly.
9. It must include forbidden_claims.
10. It must include safer_proxy_wording.
11. It must be reviewed as a draft outside supabase/migrations first.
12. Only after review should a final executable seed migration be placed in supabase/migrations.
