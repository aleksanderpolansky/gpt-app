## Interpretation

The safest P4.9.1 integration direction is to connect v4.2 as an additive runtime projection, not as a replacement for the existing VOI pipeline.

Existing runtime behavior should continue to create:

- value_objects
- value_object_instances
- activity_event_value_object_instance_links
- value_object_state_deltas
- value_object_daily_aggregates
- value_object_state_snapshots

The new v4.2 runtime layer should additionally populate:

- value_object_category_links
- activity_event_value_object_links
- value_object_usage_aggregates

## Proposed integration point

Preferred first integration point:

1. after an Activity Event is created / confirmed;
2. after the existing VOI pipeline has created or found a value_object_id;
3. create direct activity_event_value_object_links rows from event_id to value_object_id;
4. set exposure_minutes from activity_events.duration_minutes by default;
5. upsert value_object_usage_aggregates by user_id + value_object_id;
6. create value_object_category_links only when category/context data is known and reliable;
7. do not remove or alter existing relation_type-based VOI links.

## Why this direction is safer

- It preserves the already-working VOI pipeline.
- It avoids rewriting known-template processing.
- It creates the v4.2 analytical projection gradually.
- It allows testing with one known-template activity before generalizing.
- It keeps Activity Event as the source of truth for real time.
- It avoids making relation_type the central v4.2 semantic model.
