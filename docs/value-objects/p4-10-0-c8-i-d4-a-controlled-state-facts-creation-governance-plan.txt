Terminology:
Use "state fact" carefully.

A state fact in this project means:
A structured state-layer record created under controlled governance, linked to a value object, activity, source, or context, and used for planning and recommendation logic.

It does not mean:
An objective medical, psychological, financial, legal, or business truth.

Preferred user-facing wording:
- signal
- estimate
- planning signal
- proxy signal
- possible load
- recent activity load
- user-confirmed priority
- may be useful
- likely relevant for planning

Avoid user-facing wording:
- diagnosis
- disorder
- disease
- hormone level
- confirmed result
- guaranteed progress
- client acquired
- deal closed
- income earned
- child improved
- muscle growth confirmed

Controlled creation pipeline:
The future controlled state-facts creation mechanism should follow this sequence:

1. Input event exists
   Example sources:
   - activity event
   - manual activity record
   - user correction
   - user confirmation
   - rule output
   - AI-assisted derivation draft
   - wearable/imported data later
   - calendar/time-block context later

2. Candidate state signal is proposed
   The system proposes a candidate, not a final unsafe conclusion.

3. Candidate references an existing state_dimension
   The candidate must reference public.state_dimensions.dimension_key.

4. Claim policy gate is checked
   The candidate must comply with the state dimension claim_policy:
   - system_estimate
   - proxy_only
   - user_confirmed
   - direct_measurement
   - blocked

5. Source type gate is checked
   The candidate source must be included in allowed_source_types for that dimension.

6. Forbidden claims are checked
   The candidate wording and internal claim must not match forbidden_claims.

7. Safer wording is selected
   The system must use safer_proxy_wording for summaries or recommendation explanations.

8. Sensitivity and privacy are applied
   default_privacy_level and is_sensitive must influence visibility and API behavior.

9. Evidence is attached
   A state fact should be traceable to activity/context/source evidence.

10. Confidence is bounded
   The system should store confidence as a planning confidence, not as truth certainty.

11. Expiry/window logic is considered
   Many state facts should be time-windowed and not permanent.

12. User correction must be possible
   User must be able to correct, reject, or override state signals later.

Claim policy interpretation:

1. system_estimate
Allowed:
- general planning estimates
- workload estimates
- recent activity distribution
- practice balance
- physical load estimate
- pipeline effort estimate

Not allowed:
- confirmed result
- diagnosis
- hidden sensitive conclusion

2. proxy_only
Allowed:
- weak proxy wording
- possible tiredness
- stress-load signal
- care responsibility signal

Not allowed:
- direct medical/psychological/hormonal conclusion
- diagnostic label
- child outcome claim

3. user_confirmed
Allowed:
- signal only if user explicitly entered or confirmed it
- example: financial_pressure_signal

Not allowed:
- hidden inference from behavior
- creditworthiness
- bankruptcy risk
- income confirmation without user input

4. direct_measurement
Allowed only when:
- there is a real direct measurement source
- the system has explicit source metadata
- the measurement type is not over-interpreted

For current D3 seed:
No first-seed dimension uses direct_measurement.

5. blocked
Used when:
- dimension exists only as a forbidden/blocked concept
- no fact should be created
- future governance needs to explicitly prevent a dangerous category

For current D3 seed:
No first-seed dimension uses blocked.

Important per-dimension notes:

attention_load:
Can be estimated from deep work, language learning, planning, debugging, long uninterrupted sessions.
Must not imply ADHD, cognitive impairment, or mental-health diagnosis.

fatigue_signal:
Can be a weak proxy from duration, sleep-related context, workload, low-efficiency patterns, or user input.
Must not imply diagnosed fatigue, chronic fatigue, medical exhaustion, or burnout diagnosis.

recovery_need:
Can suggest lower load, stretching, food, hydration, sleep, walking, or passive learning.
Must not imply medical recovery requirement, injury diagnosis, or illness diagnosis.

stress_load_estimate:
Can be a proxy for emotional load after conflict, interruption, workload, or user-confirmed stress.
Must not imply cortisol level, anxiety disorder, panic disorder, psychiatric condition, or mental illness.

learning_progress_signal:
Can reflect practice momentum, repetitions, tests, corrections, and review frequency.
Must not imply official certificate level or guaranteed exam readiness.

language_practice_balance:
Can detect under-practiced languages or over-concentration.
Must not imply official fluency or certificate achievement.

physical_activity_load:
Can reflect duration, intensity, movement type, and training load.
Must not imply muscle growth, fat loss, testosterone change, injury diagnosis, or medical improvement.

family_care_load_signal:
Can describe family/care responsibility load such as helping a child learn.
Must not imply child development improvement, parenting quality score, family diagnosis, or child psychological state.

work_responsibility_load:
Can estimate work obligation load.
Must not imply employer evaluation, legal conclusion, disciplinary risk, or job performance score.

pipeline_building_effort:
Can reflect preparation effort for sales, business development, job search, partnerships, outreach.
Must not imply client acquired, deal closed, revenue earned, guaranteed lead, or confirmed sales result.

financial_pressure_signal:
Can exist only from explicit user confirmation or manual input.
Must not infer financial distress, bankruptcy risk, creditworthiness, income, or debt without user input.

social_interaction_load:
Can estimate people-facing communication load.
Must not imply social anxiety, personality disorder, relationship diagnosis, or psychological condition.

Runtime creation modes:

1. Shadow candidate mode
The system proposes candidate state signals but does not persist them.
Useful for testing AI/rule logic safely.

2. Draft persist mode
The system persists draft state facts with low authority and clear status.
These facts may require review, user confirmation, or automatic expiry.

3. Confirmed persist mode
The system persists confirmed facts only when:
- user confirmed,
- rule is safe,
- source is allowed,
- claim policy passed,
- privacy is applied.

4. Correction mode
The user or system can invalidate, correct, or supersede a state fact.

5. Rollback mode
Used when activity correction or deletion changes state facts.
