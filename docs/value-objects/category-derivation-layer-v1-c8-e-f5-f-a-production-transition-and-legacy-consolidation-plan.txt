CENTRAL QUESTION BEFORE production_persist

Before production_persist, we must decide what becomes the authoritative Category Derivation path for /api/activity/complete.

There are three possible strategies.

OPTION A - Keep legacy and routeRunner running side-by-side

Description:
- legacy Category Derivation remains active;
- routeRunner persists category_derivation_runs and activity_category_derivations;
- Value Object Bridge continues to use legacy additional category links;
- routeRunner persistence is used as audit/proof/analytics layer.

Pros:
- lowest risk;
- no immediate change to Value Object Bridge;
- preserves existing complete-route behavior;
- routeRunner persistence can be accumulated safely.

Cons:
- duplicated derivation logic;
- two derivation sources may diverge;
- harder to reason about source of truth;
- long-term technical debt.

Recommended use:
- short transitional period only.

OPTION B - routeRunner becomes authoritative for persistence, legacy remains only as bridge fallback

Description:
- routeRunner persists canonical category_derivation_runs and activity_category_derivations;
- legacy Category Derivation remains temporarily only to feed current Value Object Bridge if bridge still depends on old data shape;
- response metadata distinguishes routeRunner canonical result from legacy fallback.

Pros:
- routeRunner persistence becomes the source of truth;
- lower risk than removing legacy immediately;
- allows later Value Object Bridge migration.

Cons:
- still has duplicate runtime work;
- requires clear naming and logging;
- requires later bridge refactor.

Recommended use:
- best next step before production_persist.

OPTION C - routeRunner fully replaces legacy Category Derivation in complete route

Description:
- legacy internal function is removed or bypassed;
- routeRunner is the only Category Derivation path;
- Value Object Bridge consumes routeRunner output or persisted derivations.

Pros:
- clean architecture;
- single source of truth;
- lower long-term complexity.

Cons:
- highest immediate risk;
- requires Value Object Bridge input adaptation;
- requires more regression tests;
- should not be done in one step without controlled bridge migration.

Recommended use:
- later target state, not immediate next step.

RECOMMENDED STRATEGY

Recommended path:
B first, C later.

Meaning:
1. Keep production default disabled for now.
2. Use shadow_persist for local tests only.
3. Add an explicit plan to make routeRunner the canonical persistence path.
4. Keep legacy complete-route Category Derivation as temporary bridge fallback.
5. Do not remove legacy logic until Value Object Bridge can consume routeRunner result or persisted derivations directly.
6. Do not enable production_persist until idempotency and bridge semantics are verified.

WHY NOT production_persist IMMEDIATELY

production_persist currently technically works in local routeRunner tests, but enabling it too early would create architectural ambiguity:

- Are activity_category_derivations canonical?
- Are value_object_category_links still created from legacy additionalCategoryLinks?
- Which derivation_run_id should downstream analytics trust?
- Should Value Object Bridge use routeRunner-derived candidates directly?
- Should legacy Category Derivation still persist its own run?
- What happens if routeRunner persistence succeeds but Value Object Bridge fails?
- What happens if Value Object Bridge succeeds but routeRunner persistence fails?
- Should category derivation failure block activity completion in production?
- How do we test idempotency when complete route returns already_completed on repeated POST?

These questions must be answered before production_persist is enabled.
