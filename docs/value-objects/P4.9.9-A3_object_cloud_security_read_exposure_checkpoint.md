## Completed work

### A1 — static security/read exposure inspection

Created:

- docs/value-objects/P4.9.9-A1_object_cloud_security_read_exposure_inspection.md

The inspection confirmed:

- API uses auth0.getSession();
- API returns 401 when no Auth0 session exists;
- API looks up app_users by auth0_sub;
- API filters value_object_cloud_profiles_v1 by user_id = current app user id;
- API validates valueObjectId as UUID;
- UI uses GET fetch only;
- UI calls the debug API, not the database directly.

### A2 — runtime security boundary test

Created:

- docs/value-objects/P4.9.9-A2_object_cloud_security_boundary_runtime_test_result.md

Runtime verification confirmed:

- authenticated request returns 200;
- unauthenticated request with credentials omitted returns 401;
- returned user ids match authenticated filters.userId;
- business-german category filter returns only current user data;
- knee-exercises category filter returns only current user data;
- invalid valueObjectId returns 400;
- unknown category returns 200 with zero profiles;
- all runtime checks passed.

## Final decision

The object-cloud read stack is acceptable as a debug/admin tool.

It should not yet be exposed as a normal production feature or linked from public navigation.

## Reason

The endpoint uses the shared Supabase client. If that client uses SUPABASE_SERVICE_ROLE_KEY, RLS is bypassed at database level.

The current safety boundary is therefore application-level filtering by authenticated app user id.

This is acceptable for hidden/debug usage during development, but should be hardened before production exposure.

## Required rule going forward

Do not add the following route to public navigation yet:

- /value-objects/debug/cloud-profile

Do not convert the endpoint into a normal user-facing API yet:

- /api/value-objects/debug/cloud-profile

## Production hardening candidates

Before non-debug exposure, choose one of these paths:

1. Add explicit admin/dev-only guard to the debug API and page.

2. Create a user-scoped RLS-respecting Supabase read client and expose a non-debug API later.

3. Keep current route hidden and use it only for developer verification of the object-cloud read model.
