4. Cleanup policy principle

Cleanup is allowed only for rows that are explicitly marked as proof/test rows.

Cleanup must never rely only on time, title, input text, or guessed content.

Cleanup must be based on exact metadata markers and exact links between rows.

5. Required proof markers

The proof event must include these metadata markers:

- proof: P4.10.0-C8-E-F6-E-controlled-production-persist-proof
- purpose: controlled_production_persist_proof
- doNotUseAsCanonicalBusinessEvent: true
- cleanupEligible: true
- productionPersistProof: true
- createdBy: controlled_proof_route
- productionRouteUnderTest: false
- categoryDerivationRouteUnderTest: true
- completeRouteModified: false
- openAiExpected: false

6. Rows that may be cleaned

Cleanup may target only rows connected to proof events with all required markers.

Eligible cleanup scope:

- activity_events created by the controlled proof route
- category_derivation_runs linked to those proof activity_events
- activity_category_derivations linked to those proof derivation_run_id values
- optional processing/debug rows only if they are explicitly linked to the proof event or proof derivation_run_id and separately reviewed

7. Rows that must never be cleaned

Cleanup must never delete:

- normal user activity_events
- rows without cleanupEligible: true
- rows without productionPersistProof: true
- rows without purpose: controlled_production_persist_proof
- rows created by /api/activity/complete normal business flow
- rows not linked to the proof event
- rows not linked to the proof derivation_run_id
- organization, actor, user, category, rubricator, value object, offer, certificate, purchase, wallet, or booking data
- migrations
- schema objects
- RLS policies
- permissions
- application source code

8. Cleanup order

If cleanup is later approved, the safe logical order is:

1. Identify proof activity_events by exact metadata markers.
2. Identify category_derivation_runs where activity_event_id is one of those proof event ids.
3. Identify activity_category_derivations where derivation_run_id is one of those proof run ids.
4. Review counts before deletion.
5. Delete activity_category_derivations linked to proof derivation runs.
6. Delete category_derivation_runs linked to proof events.
7. Optionally delete proof activity_events only after linked proof derivations and runs are removed.
8. Re-check counts after deletion.

9. Rollback policy

Rollback for a controlled proof means returning the database to the state before the proof rows were created.

Rollback may include deleting the proof rows defined in this policy.

Rollback must not revert source code automatically.

Rollback must not modify schema, migrations, RLS, permissions, or normal business data.

If runtime proof reveals a route bug, source-code rollback must be handled separately through Git.

10. SQL execution policy

No SQL may be executed in PowerShell.

No cleanup SQL may be executed in this step.

No cleanup SQL may be executed automatically by ChatGPT.

If cleanup SQL is later created, it must be reviewed separately and executed only in an approved database tool, such as Supabase SQL Editor, after explicit approval.

11. Required pre-cleanup evidence

Before any cleanup command is executed later, collect:

- proof activity_event id
- proof derivation_run_id
- count of matching proof activity_events
- count of matching proof category_derivation_runs
- count of matching proof activity_category_derivations
- confirmation that all matching activity_events have required proof markers
- confirmation that no normal activity_events are included
- confirmation that no unrelated derivation runs are included
- confirmation that no unrelated derivation rows are included
