PURPOSE

DESIGN DECISION

Do not add routeRunner as an additional second Category Derivation flow inside /api/activity/complete.

Instead, the final production integration should replace or wrap the existing older complete-route Category Derivation block with a feature-flagged adapter.

Reason:
Existing /api/activity/complete already derives, resolves, and persists categories. Running routeRunner in addition would likely duplicate work.

TARGET INTEGRATION MODEL

Use an adapter layer:

lib/activity/categoryDerivation/completeRouteIntegration.ts

This adapter should sit between /api/activity/complete and routeRunner.ts.

The complete route should eventually call only one integration function, for example:

runCategoryDerivationForCompleteRoute({
  supabase,
  activityEvent,
  actorId,
  mode,
  includeResponseDebug,
  failActivityComplete,
})

The adapter should:
1. Preserve the current CategoryDerivationCompleteRouteResult response shape or provide a compatible shape.
2. Use routeRunner internally when feature flag mode allows.
3. Skip safely when disabled.
4. Avoid duplicate category derivation rows.
5. Convert routeRunner result into the same fields currently used by complete route response metadata.

RECOMMENDED MODES

CATEGORY_DERIVATION_ROUTE_RUNNER_MODE

Allowed values:

1. disabled
No routeRunner execution.
No writes.
Complete route returns disabled/skipped metadata only.

2. legacy_existing
Keep current /api/activity/complete logic using old derive/resolve/persistDerivations flow.
This mode may be useful temporarily during transition.

3. shadow_no_persist
Call routeRunner with:
- persist: false
- resolve: true or false depending on cost/safety choice

Purpose:
Verify derivation output without writing category_derivation_runs or activity_category_derivations.

4. shadow_persist
Call routeRunner with:
- persist: true
- resolve: true

Purpose:
Write rows, but treat failure as non-fatal.

5. production_persist
Call routeRunner with:
- persist: true
- resolve: true

Purpose:
Normal production behavior once proven.

Recommended default:
disabled

Recommended first local test mode:
shadow_no_persist

Recommended second local test mode:
shadow_persist

Recommended production default:
disabled until verified.

IDEMPOTENCY POLICY

Before any production persist mode, the adapter must check whether a completed category_derivation_run already exists for the same activity_event_id and same policy/schema/rule version.

Recommended idempotency rule:

Skip creating a new persistent run if there is already a completed run where:
- activity_event_id matches
- processor_version = category_derivation_v1
- rule_version = rules_v1
- schema_version matches the configured integration schema version
- policy_version matches the configured integration policy version
- status in completed / completed_with_warnings

If a run exists:
- return skipped_existing_completed_run
- include existing derivationRunId
- do not insert new activity_category_derivations

Future revision logic:
Only later add rerun/revision behavior if:
- rule_version changes;
- policy_version changes;
- schema_version changes;
- user correction requires re-derivation.

ERROR POLICY

Default production behavior:
Category Derivation errors must not fail /api/activity/complete.

If routeRunner fails:
- capture error in categoryDerivationResult
- set ok: false for category derivation only
- keep activity completion successful unless fail flag is true

If CATEGORY_DERIVATION_ROUTE_RUNNER_FAILS_ACTIVITY_COMPLETE=true:
- routeRunner failure may return a route error
- this should be used only for controlled local tests, not default production

RESPONSE SHAPE POLICY

The complete route currently returns categoryDerivationResult-like metadata near the final response.

The new integration should preserve a compact response shape:

categoryDerivation: {
  enabled: boolean,
  mode: string,
  ok: boolean,
  skipped: boolean,
  reason: string | null,
  derivationRunId: string | null,
  candidateCount: number,
  resolvedCandidateCount: number,
  persistenceDerivationRowsCreated: number,
  warnings: string[],
  errors: string[]
}

Optional debug extension only if INCLUDE_RESPONSE_DEBUG=true:

categoryDerivationDebug: {
  routeRunnerResult,
  policy,
  idempotency,
  versions
}

PLACEMENT IN /api/activity/complete

Based on F3-C-A, routeRunner integration should happen where existing categoryDerivationResult is currently produced, before Value Object Bridge response metadata is assembled.

Important:
Do not move Value Object Bridge / impact / aggregate / snapshot logic in this integration block.

Production route order should remain conceptually:

1. Validate ACTIVITY_RECORDING_ENABLED.
2. Parse request.
3. Resolve authenticated user/person actor context.
4. Create or complete activity_event.
5. Run existing core processing.
6. Run Category Derivation integration adapter.
7. Run or preserve Value Object Bridge / known-template / impact processing as currently designed.
8. Return response with compact category derivation metadata.

Important:
The exact code placement must be confirmed immediately before patching, using the current route.ts line structure.

RELATION TO EXISTING OLD COMPLETE-ROUTE CATEGORY DERIVATION BLOCK

Because /api/activity/complete already has old category derivation logic, the patch must choose one of two paths:

Option A - minimal safe transition:
Keep old functions in place but gate old execution behind legacy_existing mode.
Add new adapter but do not remove old code immediately.

Option B - clean replacement:
Remove old inline derive/resolve/persist block and replace it with completeRouteIntegration.ts.
Riskier, but cleaner.

Recommended:
Option A first.

Reason:
It reduces risk and allows comparison between legacy_existing and routeRunner modes.

F3-C-B DECISION

Proceed with Option A:
Feature-flagged adapter with legacy_existing available temporarily.

Do not remove old complete-route category derivation logic yet.
Do not run new routeRunner unconditionally.
Do not write duplicate rows.
