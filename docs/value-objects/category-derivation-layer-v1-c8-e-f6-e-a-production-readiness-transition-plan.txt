4. Production-readiness question

The next question is not:

"Can we enable production_persist immediately?"

The correct next question is:

"What exact safety conditions, inspection results, rollback strategy and observability gates must exist before production_persist can be enabled?"

5. Core decision for F6-E-A

Decision:

Do not enable production_persist in F6-E-A.

Do not modify source code in F6-E-A.

Create a staged production-readiness plan first.

6. Main production_persist risks

Before production_persist can be enabled, these risks must be understood:

- duplicate derivation runs for the same activity event;
- duplicate activity_category_derivations rows;
- incomplete or partially persisted routeRunner state;
- unresolved candidates being persisted incorrectly;
- valueObjectBridge creating duplicate or conflicting value objects;
- rawSignal / processingLogs mismatch;
- routeRunner failure causing activity completion failure unexpectedly;
- strict mode accidentally blocking /api/activity/complete for normal users;
- performance cost from persistence on each completion;
- unclear rollback if production persistence creates wrong rows;
- inability to distinguish proof/test activity events from real business data;
- insufficient audit trail for production persistence.

7. Required safety gates before production_persist

Before any production_persist transition is approved, we need a separate inspection and decision step covering:

- idempotency behavior;
- duplicate run prevention;
- completed / completed_with_warnings lookup behavior;
- routeRunner retry behavior;
- rollback / cleanup strategy;
- auditability;
- production feature flag behavior;
- non-blocking vs strict behavior;
- whether failActivityComplete should remain false during first production transition;
- whether production_persist should first run only through a debug or controlled proof route;
- whether proof/test events need a dedicated marker or cleanup policy.

9. Strong recommendation

The first production-readiness move should probably not be direct production_persist on /api/activity/complete for all events.

Safer options to evaluate in F6-E-C:

Option A:
Keep /api/activity/complete in shadow_persist and add no code.

Option B:
Create a controlled production_persist proof using a debug setup event and a narrow proof path.

Option C:
Use production_persist only when a proof/test metadata marker is present.

Option D:
Keep failActivityComplete=false during initial production_persist so that completion remains non-blocking.

Option E:
Require idempotency proof and cleanup/rollback notes before production_persist.
