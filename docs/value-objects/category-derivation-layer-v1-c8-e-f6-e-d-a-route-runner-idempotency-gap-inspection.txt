5. Interpretation

The runLookup helper exists and contains completed-run lookup logic, but current routeRunner does not appear to call or import it.

This means the production-readiness blocker from F6-E-B is real enough to require a focused idempotency design before production_persist.

The current idempotency debug route uses the adapter, but if neither adapter nor routeRunner calls runLookup, that route may not prove actual duplicate-run prevention in the current runtime path.

6. Design questions for next step

F6-E-D-B should decide:

- whether completed-run lookup belongs inside routeRunner, adapter, or persistence layer;
- whether routeRunner should check existing completed runs before createCategoryDerivationRun;
- what exact response should be returned when an existing completed run is found;
- whether existing-run detection should be active in shadow_persist, production_persist, or both;
- how to prove duplicate-run prevention without enabling broad production_persist;
- what cleanup policy applies to proof/test rows.

7. Preliminary safe design direction

The safest likely design is:

- perform completed-run lookup inside routeRunner before createCategoryDerivationRun;
- return a stable existing-run result when a completed/completed_with_warnings run already exists for the same activityEventId and version tuple;
- keep adapter non-blocking with failActivityComplete=false;
- prove behavior through a controlled idempotency runtime proof before any production_persist transition.

This is only a design hypothesis. F6-E-D-B must approve or reject it before implementation.

8. Safety gates preserved

- no production_persist
- no OpenAI call
- no schema or migration change
- no RLS or permission change
- no UI work
- no SQL in PowerShell
- no runtime/source code changes
- no broad refactor
