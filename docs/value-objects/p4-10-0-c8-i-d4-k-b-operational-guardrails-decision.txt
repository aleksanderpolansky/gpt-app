Decision:
Do NOT create a permanent read-only API endpoint for state facts yet.

Reason:
A read-only state-fact endpoint would be a new data exposure surface for private user state facts. Even if it is read-only, it still creates privacy, ownership, and production-safety risks. The D4-K-A local/server-side verification is enough for the current proof stage.

Operational guardrails for future state fact read models:
1. No public state-fact read endpoint.
2. No endpoint that reads arbitrary state facts only by id without owner verification.
3. No endpoint that exposes another user's value_object_state_facts.
4. No direct client access to value_object_state_facts.
5. No service-role-backed read endpoint without strict authenticated actor resolution.
6. No list-all-state-facts endpoint.
7. No production debug endpoint that returns raw private state facts.
8. No metadata leakage beyond what is needed for the immediate UI/read-model purpose.
9. Read models must be purpose-specific, not generic table mirrors.
10. State facts remain private by default unless an explicit future publication/privacy model is designed.

Allowed future read-model directions:
1. Owner-scoped read model:
   - authenticated user only;
   - actor ownership checked;
   - value_object_id must belong to the authenticated actor or allowed organization context;
   - returns only minimal fields needed for UI/analytics.
2. Internal diagnostic verification:
   - local script or admin-only process;
   - never public;
   - never generic all-user listing.
3. Aggregated state snapshot read model:
   - reads from future snapshots/aggregates instead of exposing raw state facts;
   - safer for dashboards and Next Best Action.
4. Purpose-specific read path for a single Value Object:
   - only after ownership and privacy checks are stable;
   - no raw evidence dump by default.
