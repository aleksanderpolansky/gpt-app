# P4.9.12-A1 — controlled parent/child Value Object hierarchy strategy

Date: 2026-05-18
Status: DRAFT / READY FOR REVIEW

## Purpose

Define how parent/child Value Object hierarchy should be introduced after P4.9.11 confirmed that the schema is ready but no hierarchy data exists yet.

## Current confirmed state

P4.9.11 confirmed:

- value_objects.parent_value_object_id exists;
- value_objects_count: 5;
- cloud_profile_rows_count: 2;
- value_objects_with_parent_count: 0;
- distinct_parent_value_objects_count: 0;
- cloud_profiles_with_parent_count: 0;
- cloud_profiles_with_children_count: 0;
- cloud_profiles_without_parent_count: 2.

Current cloud objects are root-level:

1. business-german
2. knee-exercises

## Core rule

The parent/child relation is only structural:

- who is parent;
- who is child.

No other relationship type should be stored in parent_value_object_id.

Other meanings such as cause, influence, supports, blocks, improves, worsens, trains, belongs-to-context, goal-of, result-of, or combines-with should be discovered or represented later at the analytics layer, not inside parent_value_object_id.

## Why this matters

Parent/child must stay simple because the same Value Object can later be analyzed in many different ways through:

- categories;
- activity history;
- exposure duration;
- context;
- state deltas;
- daily aggregates;
- snapshots;
- entity/protocol characteristics.

If parent_value_object_id starts carrying multiple semantic meanings, the model becomes ambiguous and hard to query.

## One parent rule

For the current MVP, one Value Object can have at most one direct parent through:

- value_objects.parent_value_object_id

This avoids multi-parent graph complexity in the base schema.

Combinations and overlapping meanings should be analyzed through category combinations and read models, not through multiple parent pointers.

## Root object rule

A Value Object with:

- parent_value_object_id = null

is a root-level object.

Root does not mean “most important”. It only means that no structural parent is currently assigned.

## Child object rule

A Value Object with:

- parent_value_object_id = another value_objects.id

is a child of that parent.

Child does not mean “less valuable”. It only means that, in the chosen structural view, the object is placed under another object.

## Scale/view rule

The difference between root and child depends on the chosen scale of analysis.

Example:

- body can be parent of leg;
- leg can be parent of knee;
- knee can be parent of knee exercises;
- knee exercises can be parent of a specific protocol.

But the platform should not force this full hierarchy immediately.

The user should be able to start with practical objects and refine hierarchy later.

## No ontology explosion rule

Do not create a new Value Object for every small parameter automatically.

Use:

- entity_protocol_characteristics_json
- category_origin_json
- metadata_json
- categories

for parameters that describe the entity, method, protocol, or execution form.

Create a separate child Value Object only when it becomes useful for:

- repeated tracking;
- separate analytics;
- separate UI display;
- separate goals;
- separate state;
- separate aggregation;
- separate review or merging.

## Category relationship rule

Categories are not parent/child hierarchy.

Categories describe semantic components of a Value Object.

Example:

- walking to work for 15 minutes can connect to walking and commute categories;
- analytics can later ask how much time was walking, commute, health, work preparation, etc.;
- this does not require parent_value_object_id to have multiple parents.

## Activity meaning rule

An activity event remains a source/action record.

The meaningful interpreted object created or affected by activity is a Value Object.

When a user says something like:

- walked to work for 15 minutes

the system may connect the event to Value Objects such as:

- walking;
- commuting to work;
- daily movement;
- health practice;

but parent/child hierarchy should not be used to encode all these meanings.

The object-cloud and category system handle the wider semantic analysis.

## Draft/review rule

A draft or review-needed Value Object is not a different ontological type.

It is the same Value Object with UI/review state:

- needs_user_review = true/false;
- ui_visibility;
- metadata_json;
- category_origin_json.

Review is about interface and clarification, not about a separate object class.

## Safe introduction strategy

Parent/child hierarchy should be introduced in this order:

1. Document hierarchy rules.

2. Create a read-only hierarchy view that can show root/child fields even when no child data exists.

3. Create one controlled test relation only after the view is ready.

4. Verify that the object-cloud read layer can show parent/child structure.

5. Only then consider API/UI exposure.

## First controlled test relation candidate

Do not create this relation yet without a separate step.

Potential future test relation options:

### Option A — Business German hierarchy

- parent: German language / language learning / business communication;
- child: Business German;
- child or protocol: German marketing handwriting practice.

### Option B — Knee exercises hierarchy

- parent: knee / lower-limb health / physical practice;
- child: Knee exercises;
- child or protocol: knee training health practice.

## Important caution

The two current cloud objects are already root-level in the current data:

- Business German;
- Knee exercises.

Do not retroactively assign hierarchy automatically without a controlled migration/test.

## Recommended next implementation step

P4.9.12-A2 should create a read-only SQL view or SQL audit that presents:

- value_object_id;
- parent_value_object_id;
- root/child status;
- children_count;
- category slug/name;
- usage count;
- total exposure minutes;
- latest activity template;
- needs_user_review;
- ui_visibility.

This should still work even when no parent/child links exist yet.

## Non-goals for this block

Do not yet:

- write parent_value_object_id values;
- add hierarchy UI editing;
- add public navigation;
- add graph traversal;
- support multiple parents;
- infer hierarchy automatically with AI;
- merge Value Objects automatically.

## Decision

P4.9.12 starts with rules and read-only modeling.

Controlled writes come later, after the read model is stable.
