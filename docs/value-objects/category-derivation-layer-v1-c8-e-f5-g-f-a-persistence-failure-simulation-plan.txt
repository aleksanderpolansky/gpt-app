3. Why persistence failure simulation is needed

The previous failure tests prove validation and mode-safety behavior before persistence starts.

They do not yet prove what happens if:

- the adapter is enabled;
- mode is shadow_persist;
- event and actor are valid;
- routeRunner is allowed to execute;
- derivation candidates are produced;
- persistence layer starts or is about to start;
- a controlled simulated persistence failure occurs.

This is important before any later complete-route non-blocking failure proof, because the failure must be contained, observable, and non-destructive.

4. Safety principles

This block must not simulate failure by damaging the real database.

Forbidden methods:

- no DROP;
- no ALTER TABLE just to break persistence;
- no RLS/permission corruption;
- no removal of columns or indexes;
- no production_persist;
- no OpenAI call;
- no full UI/UX;
- no commercial core changes;
- no changes to /api/activity/complete until debug-only proof is green;
- no SQL in PowerShell.

Allowed methods:

- debug-only route;
- injected test flag;
- explicit simulation switch in debug-only path;
- controlled throw before actual DB write or at a safe mock boundary;
- safety response proving no DB rows were created;
- TypeScript-only code changes with narrow scope;
- proof document after runtime PASS.

5. Preferred simulation design

Preferred approach:

Create or extend a debug-only route for Category Derivation adapter failure behavior.

The route should accept:

{
  "scenario": "simulated_persistence_failure",
  "mode": "shadow_persist",
  "expectFailActivityComplete": false
}

The route should prepare a valid synthetic activity event and valid actorId, then trigger a controlled simulated persistence failure inside a debug-only path.

Important:

The simulation must not depend on real DB schema failure.
The simulation must not require changing Supabase permissions.
The simulation must not write partial rows unless the proof explicitly verifies rollback/no partial state.
The safest first proof is to throw before persistence writes after derivation/resolution preparation, or to inject a failing persistence adapter in a debug-only wrapper.

6. Expected non-blocking result

For failActivityComplete=false, expected behavior:

- HTTP status: 200 or controlled proof status;
- json.ok: true for the debug proof if expected failure is handled;
- adapterResult.ok: true;
- adapterResult.skipped: false or true depending on implementation boundary;
- adapterResult.reason: simulated_persistence_failure or persistence_failed;
- adapterResult.derivationRunId: null unless a run is intentionally created before failure;
- persistenceDerivationRowsCreated: 0;
- routeRunner.executed: true if the simulation occurs inside routeRunner path;
- routeRunner.persisted: false;
- routeRunner.resolved: true/false depending on injection point;
- safety.categoryDerivationRunCreated: false unless deliberately testing partial run;
- safety.activityCategoryDerivationsCreated: false;
- safety.productionPersistEnabled: false;
- safety.openAiCalled: false;
- safety.completeRouteModified: false;
- safety.schemaOrPermissionsModified: false.

The first safe variant should prefer zero created rows.

7. Expected blocking result later, not now

Strict/blocking mode must not be tested first.

Later, after non-blocking proof is green, test:

{
  "scenario": "simulated_persistence_failure",
  "mode": "shadow_persist",
  "expectFailActivityComplete": true
}

Expected later behavior:

- adapterResult.ok=false;
- failure is surfaced clearly;
- still no schema/RLS/permission damage;
- no production_persist;
- no OpenAI call.

This later blocking proof should be a separate step.

10. Runtime proof acceptance criteria

The runtime proof can be accepted only if:

- response is valid JSON;
- expected scenario is simulated_persistence_failure;
- mode is shadow_persist;
- failActivityComplete is false;
- failure is simulated by debug-only code, not real DB damage;
- route reports controlled failure reason;
- no production persist;
- OpenAI not called;
- schema/permissions not modified;
- /api/activity/complete unchanged;
- no unexpected DB rows;
- TypeScript PASS;
- implementation committed only after runtime PASS;
- proof document committed after implementation commit.

11. Anti-regression notes

Do not repeat the earlier mistake where the test harness required a specific error text even when adapterResult.reason already contains the normalized failure reason.

For simulated persistence failures, define one stable primary signal:

- adapterResult.reason
or
- adapterResult.errorCode
or
- expectedChecks.normalizedFailureReason

Do not rely only on raw exception message text.
