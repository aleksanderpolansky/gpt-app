# P4.9.0-A6 — exact minimal additive migration plan

Date: 2026-05-18
Status: READY FOR LIVE MIGRATION

## Purpose

Prepare the minimal additive v4.2 foundation migration for Category-Derived Value Objects.

## Design decision

The migration must be additive and compatibility-preserving.

It must not:

- delete existing VO / VOI tables
- delete activity_event_value_object_instance_links
- make relation_type the central semantic model
- introduce full UI/UX
- introduce tags/entity_tags
- introduce external API/calendar/wearables/NFC

## Migration part 1 — extend value_objects

Add minimal v4.2 canonical fields:

- parent_value_object_id
- entity_protocol_characteristics_json
- needs_user_review
- ui_visibility
- category_origin_json
- metadata_json

Purpose:

- support parent/child hierarchy
- store entity/protocol characteristics
- allow draft/review UI flag without disabling analytics
- support future object cloud visibility
- store category-derived origin metadata

## Migration part 2 — create value_object_category_links

Create bridge between derived Value Objects and global category/rubricator material.

Purpose:

- keep global category separate from personal/enterprise Value Object
- record which category/semantic element created or defines a Value Object
- support category combinations

## Migration part 3 — create activity_event_value_object_links

Create direct event-to-ValueObject exposure projection.

Purpose:

- Activity Event stores real time once
- one Activity Event can project analytical exposure to multiple Value Objects
- exposure_minutes can be summed for object cloud and analytics
- no relation_type in this v4.2 projection table

## Migration part 4 — create value_object_usage_aggregates

Create minimal lifetime/current aggregate for future object cloud.

Purpose:

- usage_count
- exposure_minutes
- first_used_at
- last_used_at
- last_event_id

## Important compatibility note

Existing value_object_daily_aggregates and value_object_state_snapshots remain untouched.

The new usage aggregate is a simple object-cloud/read-optimization layer, not a replacement for existing aggregate tables.

After migration, run post-check before commit.
