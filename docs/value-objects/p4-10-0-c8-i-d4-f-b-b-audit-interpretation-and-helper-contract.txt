2. Main architectural conclusion

The project is ready for a controlled persistence plan, but not ready for blind implementation.

Reason:
A real persistence route must combine four things safely:
1. authenticated user resolution;
2. value object access/ownership resolution;
3. state dimension and claim policy validation;
4. guarded insert into value_object_state_facts.

The current D4-E-B route intentionally avoids all of that and remains shadow-only.

3. Proposed helper contract for future implementation

The future implementation should be organized as a small controlled helper layer rather than a large route body.

Proposed future helper names:

3.1 resolveAuthenticatedStateFactActor

Purpose:
Resolve the current authenticated app user and related actor context.

Input:
- Next.js request/session context

Output:
- appUserId
- auth0Sub or equivalent identity key
- email if available
- actorId if already supported by the project
- organization/space role context if needed later

Must reject:
- no session
- no app user
- placeholder UUID
- ambiguous user identity

3.2 resolveStateFactTargetValueObject

Purpose:
Resolve and authorize the target value_object_id.

Input:
- appUserId / actor context
- valueObjectId

Output:
- valueObject row
- ownership/access decision
- organization_id if relevant
- owner_actor_id if relevant
- access mode: personal_owner / organization_actor / denied

Must reject:
- missing value_object_id
- non-existing value_object_id
- user has no permission
- public/catalog visibility alone without write permission

3.3 resolveStateFactDimension

Purpose:
Resolve dimension_key to an active state_dimensions row.

Input:
- dimensionKey

Output:
- dimension_id
- dimension_key
- claim_policy
- is_sensitive
- default_privacy_level
- is_active

Must reject:
- unknown dimension
- inactive dimension
- missing claim_policy
- unsafe or unsupported policy

3.4 validateStateFactCandidateAgainstContract

Purpose:
Re-run D4-C / D4-F-A validation before persistence.

Input:
- candidate or insertDraft
- authenticated user context
- value object context
- dimension context

Output:
- accepted controlled insert payload
- or rejection decision

Must reject:
- AI-only direct persistence
- forbidden overclaims
- missing evidence_json
- unsafe wording
- invalid confidence
- invalid claim_strength
- invalid privacy_level
- missing user confirmation for user_confirmed dimensions
- proxy-only claims without safe proxy wording
- no rollback/correction metadata
- no validity handling when required

3.5 buildValueObjectStateFactInsertPayload

Purpose:
Build a payload matching value_object_state_facts constraints.

Output fields should include:
- user_id
- value_object_id
- dimension_id when available
- dimension_key
- value_json
- source_type
- source_id when available
- confidence
- evidence_json
- claim_strength
- privacy_level
- valid_from
- valid_to
- correction_status = active
- metadata_json

Must include metadata:
- contract version
- processor/helper version
- source route name
- idempotency key or deduplication basis
- rollbackable = true
- created_from_candidate = true
- not_created_by_ai_directly = true

3.6 checkStateFactIdempotency

Purpose:
Prevent uncontrolled duplicate facts.

Possible future strategies:
- source_type + source_id + dimension_key + value_object_id
- activity_event_id + dimension_key + value_object_id
- metadata_json.idempotency_key
- supersede/correction instead of repeated blind insert

D4-F-B-B does not choose the final strategy yet.

3.7 persistStateFactControlled

Purpose:
Perform the actual insert only after all gates pass.

Must:
- be server-only
- use existing Supabase convention
- never run from debug route
- verify before/after counts in tests
- return persisted row id
- return audit metadata

Must not:
- accept AI-only direct persistence
- accept placeholder user IDs
- bypass RLS/security assumptions
- weaken state facts policies
- create public state facts

5. Required future test cases

Before any persistence route is committed, the following tests must exist:

5.1 Auth rejection
- no session -> reject
- missing app user -> reject
- placeholder UUID -> reject

5.2 Value object access rejection
- missing valueObjectId -> reject
- non-existing valueObjectId -> reject
- valueObjectId not owned/accessible by current actor -> reject

5.3 Dimension rejection
- unknown dimension -> reject
- inactive dimension -> reject

5.4 AI-only block
- sourceType = ai -> reject or shadow_only
- no insert

5.5 User-confirmed policy
- financial_pressure_signal without user confirmation -> reject
- financial_pressure_signal with explicit user confirmation -> accept only if all other gates pass

5.6 Proxy-only policy
- stress_load_estimate with safe proxy wording -> possible accept only with low claim strength and validity handling
- high cortisol wording -> reject

5.7 System-estimate policy
- language practice duration -> possible accept
- physical activity load duration -> possible accept
- pipeline building effort count -> possible accept
- no skill improvement / medical / income/deal claims

5.8 Write-count proof
- accepted case increases value_object_state_facts count by exactly 1
- rejected/shadow_only cases increase count by 0

5.9 Rollback readiness proof
- inserted row has correction_status = active
- metadata_json contains helper/contract/idempotency info
- evidence_json is traceable
