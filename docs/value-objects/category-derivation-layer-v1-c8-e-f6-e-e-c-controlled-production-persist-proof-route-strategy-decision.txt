4. Core strategy decision

Decision:

Create a separate controlled production_persist debug proof route.

Do not reuse the existing idempotency debug route as-is.

Do not patch /api/activity/complete for the first production_persist proof.

Do not enable production_persist globally.

5. New controlled route target

Approved target route for later implementation planning:

- /api/activity/debug/category-derivation-controlled-production-persist-proof

This route name is intentionally explicit.

It must be treated as:

- debug-only;
- authenticated;
- proof/test-only;
- non-canonical business flow;
- cleanup-aware;
- production_persist-proof marked;
- adapter-based, not direct routeRunner-based.

6. Why not use real /api/activity/complete first

The real complete route is not selected as the first production_persist proof target.

Reasons:

- it is closer to normal business behavior;
- it can mix proof rows with normal activity completion semantics;
- proof/test metadata and cleanup strategy must be proven before touching real complete-route production_persist behavior;
- first proof should isolate Category Derivation persistence from unrelated complete-route side effects;
- this keeps risk low and makes verification easier.

7. Why not reuse existing idempotency debug route as-is

The existing idempotency debug route is not selected as-is.

Reasons:

- it was built for shadow_persist adapter-level idempotency proof;
- it explicitly blocks production_persist;
- it does not currently contain all controlled production_persist proof markers;
- changing its meaning could weaken the historical proof semantics already documented;
- a separate route keeps previous idempotency proof stable and avoids mixing proof purposes.

8. Why create a separate controlled proof route

A separate controlled proof route is the safest strategy.

Benefits:

- explicit route purpose;
- clear marker strategy;
- avoids changing existing proof route semantics;
- keeps real /api/activity/complete untouched;
- allows strict checks against accidental normal-user usage;
- can require proof/test metadata before persistence;
- can verify idempotency through adapter-level runLookup;
- can include DB verification;
- can include safety reporting;
- can remain non-blocking with failActivityComplete=false.

9. Route behavior requirements

The later controlled route must:

- accept only a proof/test activity_event id;
- require explicit marker metadata;
- reject missing proof/test markers;
- reject non-debug/non-local unsafe use if such guard exists in current project patterns;
- call runCategoryDerivationForCompleteRoute through completeRouteIntegration;
- not call routeRunner directly;
- support callTwice=true for idempotency verification;
- use completeRouteIntegration adapter-level runLookup;
- return firstCall and secondCall proof data;
- return derivationRunId;
- return persistenceDerivationRowsCreated;
- return DB verification;
- return safety object;
- confirm OpenAI was not called;
- confirm UI was not created;
- confirm schema/RLS/permissions were not changed;
- confirm /api/activity/complete was not modified;
- confirm proof route is debug-only and non-canonical.

10. Metadata marker requirements

The controlled proof must require or create proof metadata with these exact concepts:

- proof: P4.10.0-C8-E-F6-E-controlled-production-persist-proof
- purpose: controlled_production_persist_proof
- doNotUseAsCanonicalBusinessEvent: true
- cleanupEligible: true
- productionPersistProof: true
- createdBy: controlled_proof_route or debug_setup_route
- productionRouteUnderTest: false
- categoryDerivationRouteUnderTest: true

11. Setup route decision

Decision:

Do not rely on the current create-free-text-start-event route as sufficient as-is for production_persist proof.

Later implementation may choose one of two safe options:

Option 1:

- extend or create a dedicated setup route that creates a started proof event with all required markers.

Option 2:

- make the controlled proof route create its own proof event internally and immediately run the controlled proof.

Preferred direction:

- create one self-contained controlled proof route if feasible;
- otherwise create a dedicated setup route with explicit proof markers.

12. Cleanup / rollback decision

Before runtime production_persist proof, write a separate cleanup/rollback plan.
