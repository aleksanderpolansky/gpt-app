DECISION QUESTION

Should routeRunner now be integrated into the production /api/activity/complete route?

SHORT DECISION
Not yet.

Reason:
The routeRunner deterministic runtime path is now proven in isolation, but production integration should be controlled by a feature flag and preceded by one more integration design step.

WHY NOT PATCH /api/activity/complete IMMEDIATELY

1. /api/activity/complete is the canonical production route.
It already participates in activity processing, Value Object Bridge, aggregates, snapshots, and previous proof events.

2. Category Derivation now writes to new tables.
Production integration must avoid duplicate derivation runs, accidental repeated inserts, or unexpected side effects on existing processing flows.

3. Runtime proof used a debug-created activity_event.
Production route may have different timing, user context, metadata, activity template, processing status, and existing bridge flow.

4. We need an explicit feature flag.
The correct integration should allow:
- disabled mode
- debug-only mode
- production-shadow mode
- production-write mode

5. We need idempotency / duplication policy.
Before production integration, define whether repeated processing of the same activity_event should:
- skip if a completed category_derivation_run already exists;
- create a new run every time;
- only rerun if rule_version / schema_version / policy_version changed;
- create a correction/revision later.

6. We must not call OpenAI yet.
AI-assisted derivation should come after deterministic routeRunner is safely integrated or after shadow mode exists.

INTEGRATION DESIGN REQUIREMENTS

The production route integration must:

1. Be feature-flag controlled.
No unconditional write path.

2. Be non-breaking.
If category derivation fails, /api/activity/complete must still complete its existing work unless the failure is explicitly configured as fatal.

3. Return debug metadata only when safe.
Avoid bloating normal production response.

4. Preserve existing Value Object Bridge behavior.
Do not change activity_event_value_object_links or aggregate/snapshot logic in this block.

5. Avoid duplicate processing.
A repeated request should not create uncontrolled duplicate derivation rows.

6. Keep AI disabled.
No OpenAI calls in this integration block.

7. Keep canonical production proof event untouched.
Do not rerun old canonical proof event.

8. Keep semantic snapshot/correction/moderation deferred.
Do not create:
- activity_semantic_interpretations
- activity_category_corrections
- category_moderation_items
