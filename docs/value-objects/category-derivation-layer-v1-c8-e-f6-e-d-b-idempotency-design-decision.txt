4. Corrected interpretation

The gap is not simply "there is no idempotency anywhere".

The corrected interpretation is:

- runLookup exists;
- completeRouteIntegration.ts references and uses runLookup;
- current idempotency debug route uses the adapter;
- routeRunner itself does not import or call runLookup;
- routeRunner itself is therefore not internally idempotency-protected;
- adapter-level idempotency may protect /api/activity/complete integration;
- but routeRunner-level production readiness remains ambiguous if routeRunner can be called directly or by future callers.

5. Architectural decision

Decision:

Do not immediately move runLookup into routeRunner.

Do not immediately enable production_persist.

Do not immediately modify /api/activity/complete.

First prove the current adapter-level idempotency behavior at current HEAD.

Reason:

The current system appears to have idempotency protection at the completeRouteIntegration adapter layer. Before changing architecture, we should prove whether the existing adapter-level guard already prevents duplicate completed runs for the real complete-route integration path.

7. Why this proof comes before implementation

Implementation should wait because:

- adapter already references runLookup;
- idempotency route already uses adapter;
- we need evidence of current behavior before changing routeRunner;
- routeRunner-level idempotency may still be desirable later, but it should be justified by proof, not assumed;
- changing both adapter and routeRunner could create duplicated lookup logic or ambiguous ownership.

8. Idempotency ownership decision for now

Temporary ownership decision:

- For /api/activity/complete integration, idempotency ownership remains in completeRouteIntegration adapter until proven insufficient.
- routeRunner remains the lower-level derive/resolve/persist executor.
- routeRunner-level idempotency is not approved yet.
- production_persist is not approved yet.

9. Conditions that would require routeRunner-level idempotency

RouteRunner-level idempotency should be reconsidered if the next proof shows:

- adapter does not actually prevent duplicate derivation runs;
- second call creates a new derivationRunId;
- second call creates additional activity_category_derivations rows;
- direct routeRunner calls are intended to be supported as production path;
- future code paths can bypass completeRouteIntegration;
- production_persist needs protection independent of caller.
