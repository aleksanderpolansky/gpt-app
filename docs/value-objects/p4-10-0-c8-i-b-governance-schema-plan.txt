## 5. Governance principles

### 5.1 Additive only

All future migrations must be additive.

Allowed:

- CREATE TABLE;
- CREATE INDEX;
- ALTER TABLE ADD COLUMN;
- CREATE VIEW if safe;
- CREATE FUNCTION if required and reviewed;
- CREATE POLICY if RLS is clear;
- COMMENT ON for documentation.

Not allowed without separate explicit decision:

- DROP TABLE;
- DROP COLUMN;
- destructive rename;
- changing existing semantics;
- weakening RLS;
- replacing existing source-of-truth logic.

### 5.2 Activity Event remains source of truth

Activity Event remains the source of truth for recorded actions.

State deltas and snapshots are derived layers.

They must be recalculable or auditable.

### 5.3 AI output remains candidate, not truth

AI/category derivation output may produce:

- category candidates;
- semantic hooks;
- metric candidates;
- inferred state candidates;
- risk flags.

It must not write state facts directly.

### 5.4 Value Object remains unified

Do not add mandatory VO subtype.

Do not classify VO by `value_object_kind` as primary architecture.

Role is derived from:

- category bundle;
- actor;
- hierarchy;
- source activity;
- state dimensions;
- relevance/similarity edges;
- current analytical context.

### 5.5 Privacy by default

State and baseline data must be private by default.

Sensitive domains:

- health;
- family;
- child-related data;
- finance;
- work;
- baseline/social origin;
- emotional/stress proxy;
- medical documents or lab data.

### 5.6 Explainability

Every future state fact, delta or snapshot must be explainable through:

- source;
- evidence;
- confidence;
- window;
- derivation method;
- claim strength;
- correction status.

## 6. Existing structure groups to inspect

C8-I-C SQL audit must inspect the following groups.

### 6.1 Activity layer

Inspect whether existing activity tables support:

- activity id;
- user / actor ownership;
- title / text;
- timestamps;
- duration;
- status;
- source;
- correction/audit logic;
- links to participants;
- links to external objects;
- metadata JSON if available.

Questions:

- Is activity event source-of-truth clear?
- Are corrected activities auditable?
- Is duration reliable?
- Can one activity link to multiple Value Objects?
- Is there a clean place to attach future state deltas?

### 6.2 Category derivation layer

Inspect whether existing derivation structures support:

- derivation run id;
- source activity id;
- category candidates;
- semantic layer;
- confidence;
- evidence;
- forbidden overclaims;
- risk flags;
- normalized activity;
- detected language;
- rule vs AI source;
- correction status.

Questions:

- Are category candidates stored or only returned at runtime?
- Is confidence preserved?
- Is evidence preserved?
- Are forbidden overclaims preserved?
- Is there a stable derivation_run_id for audit?
- Can state hooks later reference derivation runs?

### 6.3 Contextual categories / taxonomy layer

Inspect whether category structures support:

- category id;
- slug/key;
- title;
- semantic layer;
- category type;
- parent category if any;
- global vs user-created status;
- approval / governance status;
- source;
- created_by;
- active/inactive state.

Questions:

- Can new categories be suggested without becoming active ontology automatically?
- Is governance status available?
- Can user-created categories become globally available later?
- Can category links preserve semantic layer?

### 6.4 Value Objects

Inspect whether `value_objects` support:

- id;
- owner / actor / organization / user context;
- title;
- description;
- parent/child relation;
- visibility/privacy;
- source activity or creation context;
- category signature through links;
- status;
- created_at / updated_at.

Questions:

- Is parent/child hierarchy represented clearly?
- Can personal and enterprise VOs coexist without subtype?
- Can state tables reference VO id safely?
- Are public/commercial VOs separated by visibility/context rather than subtype?
- Is there any existing field that risks becoming a hidden subtype?

### 6.5 Value Object category links

Inspect whether there are links between VO and categories.

Required future properties:

- value_object_id;
- category_id or category_key;
- semantic layer;
- confidence;
- source;
- evidence;
- created_at;
- is_primary / is_required if available.

Questions:

- Can similarity scoring use category links?
- Can category weights be derived?
- Can category links distinguish action/domain/purpose/role/responsibility?
- Can family/care/business layers be represented?

### 6.6 Value Object exposure / activity-to-VO links

Inspect whether activities link to Value Objects.

Questions:

- Is there an activity-to-VO link table?
- Can one activity expose multiple VOs?
- Can one activity create/update multiple VOs?
- Is duration stored once at activity level?
- Can analytical time attribution exceed 24h conceptually without duplicating source time?
- Can future deltas reference both activity and VO?

### 6.7 Actor / organization / participant model

Inspect whether schema supports:

- user actor;
- organization actor;
- activity participants;
- participant roles;
- buyer/seller/provider/receiver/self/teacher/student/family roles;
- future actor relationships.

Questions:

- Can actor be user or organization?
- Can household/family/external person be represented later?
- Are participant roles flexible enough?
- Are actor relationships separate from VO hierarchy?

### 6.8 Commercial core

Inspect whether commercial tables remain compatible:

- organizations;
- offers;
- purchase_confirmations;
- certificates;
- bookings;
- point transactions if present;
- organization-derived currency logic.

Questions:

- Does purchase confirmation remain external-purchase confirmation, not cart/order items?
- Are points burned when spent?
- Is seller not receiving spent points?
- Is currency derived from organization country?
- Can purchase confirmation amount later produce direct measurement / transactional confirmed fact?
- Are business claims blocked without confirmation?

### 6.9 Calendar / time / availability layer

Inspect whether existing structures support:

- calendar events;
- time blocks;
- availability rules;
- work shifts;
- no-multitasking blocks;
- family obligations;
- commute/travel;
- current/today/last_7d windows.

Questions:

- Can available time be calculated?
- Can work/no-multitasking constraints be represented?
- Can current state frame use calendar/time data?
- Can deadlines and obligations be audited?

### 6.10 Correction / feedback layer

Inspect whether existing correction structures support:

- user correction;
- activity correction;
- category correction;
- VO correction;
- recommendation feedback later;
- audit trail;
- before/after value.

Questions:

- Can user override inferred state?
- Can rejected recommendations update future relevance?
- Can state facts/deltas/snapshots be corrected or invalidated?
- Is there an audit trail pattern already used?

### 6.11 Privacy / RLS / ownership

Inspect whether future state tables can follow current RLS patterns.

Questions:

- How is user ownership enforced?
- How is organization ownership enforced?
- Are public directory fields separated from private fields?
- Can sensitive state data remain private?
- Will child/family/health/finance/work states need stricter policies?
- Are service role/admin paths separated from user paths?
