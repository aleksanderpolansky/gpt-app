2. Existing source conventions to reuse

2.1 Auth0/session convention

Source files:
- lib/auth0.ts
- lib/activity/activityUserContext.ts
- src/app/api/me/route.ts
- src/app/api/sync-user/route.ts

Observed reusable convention:
- Auth0 session is obtained through auth0.getSession().
- App user is resolved through app_users.auth0_sub = session.user.sub.
- sync-user is the authoritative reference for mapping Auth0 identity to app_users, persons, actors, and personal/marketplace spaces.
- activityUserContext is a candidate for reuse or extraction because it already resolves session, app_user, person, and person actor.

Future decision:
- Do not accept client-provided user_id for state fact persistence.
- Future helper must resolve user identity server-side.
- Future helper must reject missing session, missing app user, placeholder UUID, and ambiguous identity.

2.2 Supabase convention

Source files:
- lib/supabase.ts
- src/app/api/sync-user/route.ts
- src/app/api/value-objects/route.ts
- src/app/api/activity/debug/category-derivation-controlled-production-persist-proof/route.ts

Observed reusable convention:
- Shared Supabase service client is exported from lib/supabase.ts.
- Routes import and use that shared supabase object.
- Existing routes use .from(), .select(), .insert(), .update(), .eq(), .single(), .maybeSingle() patterns.

Future decision:
- Do not invent a new Supabase client style.
- Do not create direct client-side writes to value_object_state_facts.
- Future write helper must be server-only.

2.3 Value Object access convention

Source files:
- src/app/api/value-objects/route.ts
- src/app/api/value-objects/debug/cloud-profile/route.ts

Observed reusable convention:
- value_objects are a central table and are already used by existing routes.
- owner_actor_id / organization_id / user-related fields may inform access checks.
- Current information is enough to require a dedicated resolver, but not enough to assume write permission from value_object_id alone.

Future decision:
- Future helper must load value_object server-side.
- Future helper must decide access mode explicitly:
  - personal_owner
  - organization_actor
  - denied
- Public/catalog visibility must not imply state-fact write permission.

2.4 Debug persist-proof convention

Source file:
- src/app/api/activity/debug/category-derivation-controlled-production-persist-proof/route.ts

Observed reusable convention:
- It may show useful style for proof discipline and before/after count checks.

Future decision:
- It is reference-only.
- It must not be copied as a state facts route.
- It must not weaken D4-C / D4-F-A gates.
- It must not define state facts domain assumptions.

2.5 D4-E-B shadow route convention

Source file:
- src/app/api/activity/debug/state-signal-candidate-shadow-test/route.ts

Observed reusable convention:
- It evaluates state signal candidates in shadow/no-write mode.
- It exposes no-write markers such as noWriteGuarantee, wouldPersist, writesAttempted.
- It can be used as a candidate shape/reference.

Future decision:
- D4-E-B remains shadow-only.
- The future write route must be separate.
- Future persistence must not trust insertDraft blindly.
- Future persistence must re-run validation server-side.

7. Future test matrix

7.1 No-write tests before implementation

Before any route/helper implementation:
- confirm D4-E-B still has no Supabase import;
- confirm D4-E-B still has no .from("value_object_state_facts");
- confirm no controlled-persist route exists yet;
- confirm no new state fact is created.

7.2 Auth tests

Required future tests:
- no session -> reject 401;
- session exists but no app_user -> reject;
- placeholder UUID -> reject;
- client sends user_id -> ignored/rejected, never persisted.

7.3 Value Object access tests

Required future tests:
- missing valueObjectId -> reject;
- non-existing valueObjectId -> reject;
- valueObjectId belongs to another user/actor -> reject;
- public value object without write permission -> reject;
- own personal value object -> eligible for next gates;
- organization value object with valid actor role -> eligible for next gates.

7.4 Dimension tests

Required future tests:
- unknown dimension -> reject;
- inactive dimension -> reject;
- active system_estimate dimension -> eligible for next gates;
- user_confirmed dimension without confirmation -> reject;
- proxy_only dimension with unsafe wording -> reject.

7.5 Contract validation tests

Required future tests:
- AI-only sourceType -> reject or shadow_only, no insert;
- high cortisol / medical overclaim -> reject;
- deal closed / income overclaim without business evidence -> reject;
- safe language practice duration -> eligible;
- safe walking duration -> eligible;
- safe sales email count -> eligible;
- financial pressure only with explicit confirmation -> eligible.

7.6 Persistence proof tests

Required future tests:
- accepted case increases value_object_state_facts count by exactly 1;
- rejected case increases count by 0;
- shadow_only case increases count by 0;
- duplicate case increases count by 0;
- inserted row has correction_status = active;
- inserted row has metadata_json.rollbackable = true;
- inserted row has metadata_json.idempotency_key;
- inserted row has evidence_json as object.

7.7 Regression tests

Required future tests:
- D4-E-B route remains no-write;
- D4-E-B response still reports noWriteGuarantee true;
- D4-E-B response still reports wouldPersist false;
- D4-E-B response still reports writesAttempted false;
- D4-E-B route still does not import Supabase.
