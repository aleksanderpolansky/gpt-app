Decision:
Use a dedicated state fact audit/correction table for future controlled rollback/correction.
Do not reuse generic activity_events, impact_events, recommendation_feedback, or calendar_events as the primary audit model for state fact rollback.

Chosen model:
Dedicated table name for the future migration:
value_object_state_fact_audit_events

Reason:
1. State facts are private, user-state-related records.
2. Rollback/correction modifies the validity of a fact, not a normal user activity.
3. Existing activity/event tables have different semantics.
4. A generic event table could blur domain boundaries and make future privacy/security review harder.
5. A dedicated audit table allows strict constraints, RLS policy design, and narrow helper behavior.
6. A dedicated table prevents rollback logic from becoming a generic update/event mechanism.

Do NOT implement runtime rollback yet:
- No rollback route in D4-L-C.
- No correction route in D4-L-C.
- No SQL migration in D4-L-C.
- No update helper in D4-L-C.
- No database write in D4-L-C.

Future table purpose:
value_object_state_fact_audit_events should record controlled lifecycle events for rows in value_object_state_facts.

Future event types:
- created
- rollback_requested
- rolled_back
- correction_requested
- corrected
- superseded
- expired
- rejected_rollback
- rejected_correction

- value_object_id uuid not null

Recommended future constraints:
- id primary key.
- foreign key state_fact_id -> value_object_state_facts(id).
- foreign key value_object_id -> value_objects(id).
- unique(user_id, state_fact_id, action_type, idempotency_key).
- action_type limited to a known enum/check constraint.
- request_trace_id required.
- reason required and non-empty.
- metadata_json required.
- evidence_json required.

RLS and access direction:
- RLS must be enabled.
- Direct public/client access should be denied initially.
- Writes should go only through controlled server-side helpers.
- Read access should not be exposed through generic endpoints.
- Future owner-scoped read model may expose summarized audit status, not raw evidence by default.

Future rollback transaction shape:
1. Resolve authenticated actor.
2. Resolve target state fact.
3. Confirm owner/user/value-object permission.
4. Confirm correction_status is active.
5. Confirm rollbackable metadata.
6. Validate reason and request trace.
7. Insert audit event: rollback_requested.
8. Update value_object_state_facts through a narrow whitelist:
   - correction_status
   - valid_to
   - metadata_json rollback sub-object
   - updated_at
9. Insert audit event: rolled_back.
10. Return a narrow response.
11. If transaction fails, do not partially update the fact.

Future correction transaction shape:
1. Resolve authenticated actor.
2. Resolve state fact to correct.
3. Validate corrected candidate through D4-C/D4-F gates.
4. Insert audit event: correction_requested.
5. Mark old fact as corrected/superseded through narrow whitelist.
6. Create new corrected fact through controlled persistence logic or shared internal function.
7. Insert audit event: corrected.
8. Link old and new facts by metadata_json.
9. Return a narrow response.
10. If transaction fails, do not leave half-corrected state.

Proof artifact policy:
- Keep the D4-J-B-B proof fact active for now.
- Do not manually delete it.
- Do not manually update it.
- If rollback is tested later, it must go through a controlled route/helper and dedicated audit table.
