# ARCTor AI-A3.1 — review-first semantic fact pipeline v1

## Зафиксированная логика

### 1. Фиксация активности

После ввода свободного текста активность сразу сохраняется через существующий PP1-контракт активности.

На этом шаге:
- исходный текст сохранён;
- серверные правила времени применены;
- activity_event создан;
- запись помечена как требующая проверки;
- факты не создаются;
- OpenAI не вызывается.

Глубокий смысловой разбор начинается только после открытия записи из списка «Требуют проверки».

### 2. Первый экран разбора

Сначала показываются измерения, которые можно получить из сообщения:
- duration;
- distance;
- count;
- mass;
- money;
- другие явно указанные величины;
- process_count=1 добавляется сервером всегда.

Измерения на этом этапе являются содержимым review draft, а не журналом фактов.

### 3. Задача ИИ

Один широкий вызов модели получает список доступных пользователю leaf-ОН: активные GLOBAL system leaves и его собственные actor-owned leaves. Модель должна выбрать:
- ровно один основной leaf;
- не менее семи дополнительных leafs.

Таким образом интерфейс получает минимум восемь разных перспектив.

Модель обязана анализировать активность через разные интеллектуальные вопросы:
- непосредственное действие;
- более общий процесс;
- состояние;
- сущность;
- отношение;
- роль;
- знание;
- поведенческий паттерн;
- контекст;
- потраченный ресурс;
- созданный ресурс;
- материальный / информационный / рабочий / учебный / физический /
  эмоциональный / социальный / отношенческий / репутационный /
  экономический результат;
- новое и выполненное обязательство;
- новая возможность;
- новое ограничение;
- альтернативное использование потраченного времени;
- краткосрочное, среднесрочное и долгосрочное следствие;
- неочевидная возможность будущего использования активности.

Это не означает, что гипотеза автоматически становится событием. Для неслучившейся,
но полезной возможности модель обязана использовать relationMode=future_use.

Пример: «гулял с собакой» может породить не только «Ходьба», но и
«Обязательные рутины», «Забота о домашнем животном», «Физическая активность»,
«Возможности новых знакомств», «Практики восстановления/медитации» — если
соответствующие leafs реально существуют в онтологии.

### 4. Человеческая проверка

Каждое предложение можно:
- подтвердить;
- отклонить;
- заменить другим leaf;
- добавить дополнительный leaf вручную.

Дополнительные связи ограничены уровнем leaf.

Если пользователь заменяет именно основной предложенный leaf, исходная
формулировка активности может быть сохранена как actor-scoped recognition example
для выбранного leaf. Она не меняет Global recognition profile и не означает
согласие на обучение модели.

### 5. Сохранение фактов

Только после «Сохранить разбор и создать факты» запускается транзакционный writer.

Для каждого выбранного leaf:
- process_count=1 создаётся всегда;
- если известна duration — duration создаётся всегда;
- каждый другой выявленный показатель тоже создаётся;
- каждый (parameterCode x leaf) — отдельная запись факта;
- нет проверки «подходит ли параметр этому leaf»;
- карточка leaf не является whitelist фактических параметров.

Пример:

Активность имеет duration=30 min и process_count=1.
Пользователь оставил три leafs.

Тогда система создаёт минимум шесть отдельных фактов:
- duration 30 min + leaf A;
- process_count 1 + leaf A;
- duration 30 min + leaf B;
- process_count 1 + leaf B;
- duration 30 min + leaf C;
- process_count 1 + leaf C.

Многократный учёт одного и того же физического времени по разным смысловым
проекциям в этой версии разрешён сознательно.

### 6. Коэффициенты

На leaf можно настроить коэффициент для конкретного parameterCode.

Правило хранит:
- target leaf;
- target parameterCode;
- source leaf другого ОН;
- source parameterCode;
- условие;
- multiplier;
- priority.

При сохранении числового факта:
- нет правила -> x1;
- контекстный факт не найден -> x1;
- условие не сработало -> x1;
- правило сработало -> x multiplier;
- несколько правил сработали -> перемножаются.

Writer использует последнее подтверждённое значение source parameter,
помеченное source leaf. Текущая активность исключена из поиска контекста.

На карточке leaf хранятся плановые настройки и коэффициенты. Реальные
наблюдаемые значения живут в журнале фактов.

### 7. Один факт, одно итоговое значение

Сущностей raw fact / calculated fact в пользовательской модели нет.
Writer создаёт только окончательный факт после коэффициентов.

Для технического аудита в metadata остаются:
- parameterCode;
- coefficientProduct;
- appliedRuleIds;
- нейтральные причины CONTEXT_MISSING / CONDITION_NOT_MATCHED.

Исходное числовое значение отдельным вторым фактом автоматически не дублируется.

## Производительность

Первичный capture не вызывает модель вообще.

Review запускает один широкий provider call, а не старую последовательность
«routing model -> DB candidates -> selection model».

Для semantic review используется Standard tier. Nano fallback намеренно запрещён:
если Standard недоступен, разбор останавливается с явной ошибкой вместо тихого
ухудшения качества. Reasoning effort = low.
