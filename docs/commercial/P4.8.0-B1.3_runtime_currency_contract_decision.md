# P4.8.0-B1.3 — Runtime Currency Contract Decision

Status: CORRECTED DECISION / DOCUMENTATION ONLY

Runtime code changed: NO

## 1. Corrected interpretation

The currency question is not an unresolved business issue.

Business currency logic was already solved:

- Each organization has exactly one country.
- International corporations register country branches as separate organizations.
- Organization currency is strictly derived from the organization's country.
- Organization currency must not be arbitrary manual user input.
- Purchase confirmations must use the organization-derived currency.
- Points thresholds must use the organization-derived currency.
- Certificate money/points calculations must use the organization-derived currency.

## 2. Current technical state

Live DB currently has both:

- purchase_confirmations.purchase_currency text NOT NULL default PLN
- purchase_confirmations.currency text nullable default PLN

Runtime currently reads purchase_currency.

Correct technical interpretation for now:

- purchase_currency remains the active runtime/API field.
- currency is currently an additive generic field introduced by A7.2.
- Do not switch runtime code to currency without a separate planned patch.
- Do not remove either field in B1.
- Future technical alignment should either synchronize both columns or choose one canonical DB field.

## 3. Runtime decision

Immediate runtime patch required: NO.

Reason:

- API selects purchase_currency, and purchase_currency exists.
- Existing rows have purchase_currency = PLN.
- New rows are protected by DB defaults.
- No cart/order/item forbidden fields exist.

## 4. Risk

Potential future drift:

- If runtime writes purchase_currency with a non-PLN value but does not also write currency, then purchase_currency and currency may diverge.
- If future code reads currency while old code writes purchase_currency, UI/API may show inconsistent values.

## 5. Recommended later technical options

Not for B1, but for a later targeted block:

1. Minimal runtime sync patch:
   - derive purchase currency from organization country/currency;
   - write both purchase_currency and currency from the same normalized value;
   - expose one canonical response field.

2. DB-level sync strategy:
   - add trigger/check logic to keep currency and purchase_currency synchronized.

3. Cleanup migration later:
   - after runtime is unified and verified, decide whether one of the two columns should be deprecated.

## 6. B1.3 conclusion

- B1 found no immediate runtime-breaking issue.
- B1 found a duplicate currency column situation that must be tracked.
- Business source of truth is organization-derived currency.
- Active runtime DB field for now: purchase_currency.
- Newly added generic field: currency.
- Next step: B1.4 business logic correction, then B2 documentation commit.
