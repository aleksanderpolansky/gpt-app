## 5. What is already aligned

- Value Object has a dedicated API route and page layer.
- Value Object creation appears to support organization_id + owner_actor_id.
- Offer route uses value_object_id and validates relation to organization/owner actor.
- Certificate route layer exists separately from Value Object route layer.
- Purchase confirmation route is separate from offers/certificates and remains suitable for external purchase confirmation.
- Points routes exist as wallet/transactions layer.
- Booking and directory routes exist and can be mapped later without rewriting commercial core.

## 6. What is not a gap

- No purchase_confirmation_items is not a missing feature at this stage. It is the target decision.
- No required purchase_confirmations.offer_id/value_object_id is not a gap. Purchase confirmation is organization-level and amount-based.
- Offer not being equal to Value Object is not a gap. It is the target boundary.
- Certificate not being created directly from Value Object is not a gap. Certificate should be created from Offer.
- No full status refactor is not a gap. Status architecture is deferred.
- No polished UX for VO/commercial directory is not a gap. Backend/data first.

## 7. Potential additive gaps / decisions before A5

| Candidate | Why it matters | A4 recommendation |
|---|---|---|
| offers.value_object_id FK/index/consistency | Route uses value_object_id, and live DB already indicated column exists; relationship must be structurally safe. | Verify exact FK/index/nullability in live SQL before migration. If missing, prepare additive FK/index only. |
| value_objects.commercial_usage | Helps separate VO type from commercial scenario: catalog_info / certificate_base / both / none. | Candidate additive field for A6, but decide in A5 after confirming current UI/API assumptions. |
| Directory VO exposure | Directory may currently expose org/offers; target later may require VO as value entry point. | Document as later UX/API design, not current migration blocker. |
| Purchase confirmation public projection | Must remain masked/safe and organization-level. | Verify current public purchase history masking before any public-history changes. |
| Certificate RPC contract | Ensure request/redeem flows preserve ledger and offer-based contract. | Inspect RPC signatures before modifying certificates/points. |

## 8. Security-sensitive areas

- Organization creation/location changes: ownership and suggested geo-area rules.
- Offer creation: organization_id + owner_actor_id/provider_actor_id + value_object_id validation.
- Certificate request/redeem/cancel/expire: offer_id, wallet, points reservation/spend/release.
- Purchase confirmation: buyer/seller trust flow and points_awarded.
- Points wallet/transactions: ledger integrity; no direct balance edits.
- Public purchase history: masking and safe public projection.

## 10. A4 conclusion

A4 draft conclusion:

- Commercial core should not be rewritten.
- Current route layer already contains the main commercial relationship paths.
- The likely first A6 implementation candidate is not a new business flow, but a small additive structural hardening step after A5: verify/add FK/index for offers.value_object_id if missing, and decide whether to add value_objects.commercial_usage.
- Purchase confirmation remains organization-level external purchase confirmation; no purchase_confirmation_items.
- Certificate remains offer-based; no direct certificate-from-VO route.
- Next step: P4.8.0-A5 decision document, after reviewing this A4 file.
