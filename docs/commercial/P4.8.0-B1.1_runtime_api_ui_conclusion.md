## 4. B1.1 conclusions

### 4.1 value_objects.commercial_usage

- Immediate runtime change required: NO.
- Reason: DB default 'none' safely covers current create flow.
- Existing Value Objects API/UI currently does not need commercial_usage to keep working.
- commercial_usage should be surfaced later only when we add commercial filtering, directory/catalog logic, or explicit VO scenario management.

### 4.2 purchase_confirmations.currency

- Immediate runtime change required for creation: NO.
- Reason: DB default 'PLN' safely covers current insert flow if the API omits currency.
- Immediate UI/API display improvement: OPTIONAL, not mandatory.
- Later public/history display should probably include currency for clarity, but this is not a blocker because existing 8 rows are now PLN and future omitted values default to PLN.

### 4.3 Forbidden regressions

- Do not add purchase_confirmation_items.
- Do not add purchase_confirmations.offer_id.
- Do not add purchase_confirmations.value_object_id.
- Do not turn purchase confirmation into cart/order/item flow.
- Do not bypass certificate/points RPC.

## 5. B1.1 decision

Decision: NO immediate runtime patch is required after A7.

Recommended next step:

- P4.8.0-B2 — create checkpoint documentation and commit B1/B1.1 docs only.

Optional later patch:

- Add currency to purchase confirmation API response/public history display.
- Add commercial_usage to Value Object admin/listing UI only when commercial filtering becomes part of the active scope.
