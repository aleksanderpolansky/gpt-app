## 2. Main findings

### 2.1 Country-to-currency mapping duplication

Duplicated hardcoded country-to-currency logic is confirmed.

Known locations:

- src/app/api/organizations/route.ts
- src/app/api/organizations/[id]/location/route.ts

Both contain organization country normalization and default currency mapping logic.

Current implementation is usable, but it should not remain duplicated long-term.

### 2.2 Existing organization currency source

Current MVP source-of-truth remains:

organization.country_code determines organization.default_currency.

organization.default_currency is the stored organization currency.

organizations.currency does not exist and is not needed now.

### 2.3 Purchase confirmation currency

Current active runtime field:

purchase_confirmations.purchase_currency.

Additional field added earlier:

purchase_confirmations.currency.

Current live DB check showed that both fields match for existing rows, but they can drift in the future if not synchronized.

### 2.4 Offer and certificate currency

offers.currency, offers.certificate_currency and offers.reference_currency already exist and are used.

Current observed pattern:

- offers.currency = PLN
- offers.reference_currency = EUR
- certificate_currency may be PLN or null

Future logic should keep offer/certificate currency aligned with organization.default_currency unless a separate approved exception is introduced.

### 2.5 Minimum purchase threshold logic

C3 inventory shows that src/app/api/directory/organizations/route.ts contains MINIMUM_PURCHASE_THRESHOLDS.

This means the 10 EUR equivalent threshold logic is already partially represented in runtime code, but it is route-local and hardcoded.

Long-term, this should move to a platform-level rule model such as commercial_currency_rules.

## 3. Decision

C3.1 does not require runtime changes.

The correct direction is:

1. Keep current runtime working.
2. Do not immediately refactor currency logic.
3. Plan a later targeted technical block for shared currency logic.
4. Keep documentation of the current duplication.
5. Avoid accidental changes to purchase confirmations, points, certificates or offers before a dedicated implementation step.

## 4. Recommended future technical block

A later implementation block should:

- create one shared country-to-currency helper;
- replace duplicated getDefaultCurrencyByCountryCode implementations;
- keep organization.default_currency as stored organization currency;
- derive purchase_confirmations.purchase_currency from organization.default_currency;
- decide whether purchase_confirmations.currency should be synchronized, deprecated, or made canonical;
- move route-local MINIMUM_PURCHASE_THRESHOLDS toward a platform-level commercial_currency_rules model;
- avoid arbitrary manual currency input for organizations.

## 5. Forbidden changes remain forbidden

- Do not add purchase_confirmation_items.
- Do not add purchase_confirmations.offer_id.
- Do not add purchase_confirmations.value_object_id.
- Do not turn purchase confirmation into cart/order/item flow.
- Do not let organization currency become arbitrary manual user input.
- Do not transfer burned points to seller.
- Do not bypass certificate/points RPC.
