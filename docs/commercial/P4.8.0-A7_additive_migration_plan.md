# P4.8.0-A7 — Additive Migration Plan Draft

Status: PLAN / DRAFT ONLY  
Runtime code changed: NO  
Migration applied: NO

## 1. Purpose

Prepare a minimal additive migration plan after A6 live structural verification.

A6 confirmed:

- offers.value_object_id exists, has FK, has index, has no orphan rows.
- offer_items exists, has FK/index foundation, has no orphan rows.
- purchase_confirmations correctly has no offer_id, value_object_id, purchase_items, purchase_confirmation_items, cart_id, order_id.
- value_objects.commercial_usage is absent.
- purchase_confirmations.currency is absent.
- required certificate/points RPC functions exist.

## 2. Migration principle

A7 must be small, additive and non-destructive.

Allowed:

- add nullable/default-safe metadata columns;
- add CHECK constraints that do not break existing rows;
- add comments documenting semantics;
- add verification SQL.

Forbidden:

- no runtime code changes;
- no purchase_confirmation_items;
- no purchase_confirmations.offer_id;
- no purchase_confirmations.value_object_id;
- no cart/order/item-flow;
- no certificate-from-Value-Object route;
- no points balance mutation;
- no booking refactor;
- no directory UX changes.

## 3. Proposed additive changes

### 3.1 value_objects.commercial_usage

Add nullable text field:

- `none`
- `catalog_info`
- `certificate_base`
- `both`

Recommended default: `none`.

Reason:

This separates the *type/nature of the Value Object* from its *commercial scenario*.  
Example: the same VO can be informational/catalog-only, certificate base, both, or non-commercial.

### 3.2 purchase_confirmations.currency

Add text field with default `PLN`.

Recommended approach:

- add `currency text default 'PLN'`;
- keep it nullable or safely defaulted at this stage;
- add CHECK constraint for ISO-like three-letter uppercase currency codes;
- do not add offer/value object/cart/order/item fields.

Reason:

`purchase_amount` without currency can become ambiguous. Existing live DB has 8 purchase_confirmations rows, so the migration must be safe for existing records.

## 4. Why this is safe

- It does not change existing relationships.
- It does not change existing runtime code.
- It does not change certificate/points RPC logic.
- It does not force a new business process.
- It only adds semantic metadata fields that support the already approved model.
