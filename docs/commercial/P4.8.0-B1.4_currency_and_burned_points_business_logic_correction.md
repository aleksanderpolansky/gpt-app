# P4.8.0-B1.4 — Currency and Burned Points Business Logic Correction

Status: BUSINESS LOGIC CORRECTION / DOCUMENTATION ONLY

Runtime code changed: NO

## 1. Why this correction exists

B1.3 detected two technical currency fields in purchase_confirmations: purchase_currency and currency.

This must not be interpreted as an open business question. The business rule for currency was already defined earlier.

## 2. Canonical organization currency logic

The platform currency logic is:

1. A user adds an organization.
2. The organization has exactly one country.
3. International corporations must register branches as separate organizations.
4. Organization currency is strictly determined by the organization's country.
5. The organization cannot freely choose an arbitrary currency.
6. Purchase confirmations use the organization-derived currency.
7. Points thresholds use the organization-derived currency.
8. Certificate money/points calculations use the organization-derived currency and configured point exchange logic.

Correct relation:

organization -> country -> currency

The organization should not be treated as manually multi-currency in the MVP.

## 3. Minimum purchase threshold for awarding points

Rule:

- To award 10 points, the platform must confirm an external purchase worth at least 10 EUR equivalent in the organization's currency.

Recommended storage:

Do not store this threshold directly on every organization.

Store it as a platform-level country/currency rule, for example in a future table:

commercial_currency_rules

Possible fields:

- id
- country_code
- currency_code
- base_threshold_eur
- min_purchase_amount_in_currency
- exchange_rate_to_eur
- points_awarded_for_threshold
- valid_from
- valid_until
- source
- created_at
- updated_at

MVP rule example:

- base_threshold_eur = 10
- points_awarded_for_threshold = 10
- min_purchase_amount_in_org_currency = 10 EUR converted into organization currency

## 4. Certificate and points conversion logic

Certificate logic:

- Certificate is created from Offer.
- Offer price is expressed in the organization-derived currency.
- Seller may allow part of certificate price to be covered by points.
- The money part is paid to the seller.
- The points part is deducted from the buyer's points balance.
- Deducted points are burned and are not transferred to the seller.
- Seller does not receive points.
- Points work as discount/reduction rights, not as transferable currency.

Example:

- Offer / certificate price: 100 PLN
- Seller allows 50 PLN to be covered by points
- Buyer pays 50 PLN in money
- Remaining 50 PLN is converted into points using configured EUR-based point value
- If 1 point has calculation value of 1 EUR and 1 EUR = 4.30 PLN
- 50 PLN / 4.30 = 11.63 points
- Recommended rounding: ceil(11.63) = 12 points
- Buyer spends 12 points
- Seller receives 50 PLN
- The 12 points are burned

Recommended rounding rule:

points_to_spend = ceil(amount_covered_by_points_in_org_currency / exchange_rate_to_org_currency)

Reason:

- Rounding up prevents the buyer from receiving a discount greater than the calculated value of the burned points.
- The UI should show the exact calculation before confirmation.

## 5. Technical interpretation of purchase_currency and currency

Live DB currently has:

- purchase_confirmations.purchase_currency text NOT NULL default PLN
- purchase_confirmations.currency text nullable default PLN

Runtime currently reads purchase_currency.

Correct interpretation for now:

- purchase_currency remains the active runtime/API field.
- currency was added by A7.2 as an additive generic field.
- Do not change runtime immediately only because currency exists.
- Do not remove either field inside B1.
- Future technical alignment should either synchronize them or choose one canonical DB field.

## 6. Recommended technical direction after B1

Recommended later patch:

1. Keep purchase_currency as the active field for purchase_confirmations for now.
2. Make creation logic derive purchase_currency from organization country/currency, not from arbitrary user input.
3. If currency column remains, synchronize it with purchase_currency.
4. Later decide whether currency should be deprecated or whether purchase_currency should be replaced by currency.

No immediate runtime patch is required only to prevent breakage, because purchase_currency exists and current API reads it.

But a later business-alignment patch should ensure that purchase_currency and currency cannot diverge.

## 7. Forbidden changes remain forbidden

- Do not add purchase_confirmation_items.
- Do not add purchase_confirmations.offer_id.
- Do not add purchase_confirmations.value_object_id.
- Do not turn purchase confirmation into cart/order/item flow.
- Do not let organization currency become arbitrary manual user input.
- Do not transfer burned points to the seller.
- Do not bypass certificate/points RPC.

## 8. Corrected B1 decision

- Business currency logic is already solved.
- One organization has one country.
- Organization currency is derived strictly from country.
- Purchase confirmation currency should be derived from organization currency.
- Minimum purchase threshold for points should be a platform-level country/currency rule based on 10 EUR equivalent.
- Existing runtime is not broken because purchase_currency exists.
- Points spent on certificates are burned and are not transferred to the seller.
- Seller receives only the money part of the certificate payment.
- B1 should not make runtime changes.
- Next step remains B2 documentation commit, then a later targeted technical alignment block can handle currency synchronization if needed.
