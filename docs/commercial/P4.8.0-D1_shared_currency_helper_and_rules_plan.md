# P4.8.0-D1 — Shared Currency Helper and Rules Technical Plan

Status: TECHNICAL PLAN / DOCUMENTATION ONLY

Runtime code changed: NO

## 1. Why this block exists

Previous blocks confirmed:

- organization.country_code determines organization.default_currency.
- organization.default_currency is the stored organization currency.
- country-to-currency mapping is currently duplicated.
- getDefaultCurrencyByCountryCode exists in more than one route file.
- purchase_confirmations has two currency fields: purchase_currency and currency.
- current runtime is not broken.
- commercial_currency_rules table does not exist yet.
- MINIMUM_PURCHASE_THRESHOLDS exists as route-local hardcoded logic.
- points spent on certificates are burned, not transferred to seller.

D1 does not implement changes. D1 defines the safe technical direction.

## 2. Current business rules to preserve

- One organization has exactly one country.
- International corporations register branches as separate organizations.
- Organization currency is derived strictly from organization country.
- Organization currency must not be arbitrary manual user input.
- Purchase confirmation currency must be derived from organization.default_currency.
- Minimum purchase threshold for awarding 10 points is 10 EUR equivalent in organization currency.
- Certificate price is expressed in organization currency.
- Points spent on certificate reduce buyer's payable money amount.
- Points spent on certificate are burned.
- Seller receives only the money part of certificate payment.

### 3.2 Purchase confirmation currency

Current observed pattern:

Current partial implementation:

Future direction:

## 4. Proposed shared helper

Recommended future file:

- src/lib/commercial/currency.ts

Recommended helper responsibilities:

- normalizeCountryCode(value)
- normalizeCurrencyCode(value)
- getDefaultCurrencyByCountryCode(countryCode)
- getOrganizationCurrency(organization)
- assertOrganizationCurrencyIsDerivedFromCountry(organization)

This helper should not access Supabase directly at first.

Reason:

- Keep it pure and testable.
- Routes can call it without introducing DB coupling.
- Later, commercial_currency_rules can be added separately.

## 5. Proposed country-to-currency mapping

Initial supported mapping should reflect existing runtime behavior:

- PL -> PLN
- ES -> EUR
- DE -> EUR
- UA -> UAH
- US -> USD
- GB -> GBP
- CZ -> CZK

Default behavior:

- Unknown country should not silently create arbitrary currency.
- For MVP, unknown country can return null.
- Routes should reject organization currency derivation when country is required but unsupported.

## 6. Proposed commercial_currency_rules model

Recommended future table name:

- commercial_currency_rules

Purpose:

- store platform-level threshold and exchange logic;
- avoid route-local hardcoded MINIMUM_PURCHASE_THRESHOLDS;
- support the rule: 10 EUR equivalent purchase confirms eligibility for 10 points.

Possible fields:

- currency_code

- exchange_rate_to_eur
- points_awarded_for_threshold
- point_value_eur

MVP example:

## 7. Proposed purchase currency synchronization strategy

Recommended later implementation sequence:

1. Keep purchase_currency as active runtime field for now.
2. Make purchase confirmation creation derive purchase_currency from organization.default_currency.
3. Write both purchase_currency and currency from the same normalized value.
4. Read one canonical response field in API output.
5. Add verification SQL to detect drift.
6. Later decide whether to deprecate currency or purchase_currency.

Do not remove either field now.

## 8. Proposed points/certificate calculation rule

When buyer spends points on certificate:

- seller receives only money part;
- buyer's points are deducted;
- deducted points are burned;
- points are not transferred to seller.

Recommended calculation:

- amount_covered_by_points_in_org_currency / exchange_rate_to_org_currency = raw_points_to_spend
- points_to_spend = ceil(raw_points_to_spend)

Reason:

- Rounding up prevents buyer from receiving a discount larger than calculated burned points value.

Example:

- certificate price: 100 PLN
- buyer covers 50 PLN with points
- 1 point = 1 EUR calculation value
- 1 EUR = 4.30 PLN
- raw points = 50 / 4.30 = 11.63
- points_to_spend = 12
- buyer pays 50 PLN
- seller receives 50 PLN
- 12 points are burned
