## 3. Final decisions

### 3.1 Value Object

- Value Object is the unified value entity for both personal and enterprise scenarios.
- Personal Value Object and enterprise Value Object must not become separate incompatible tables.
- The difference is context/access/owner, not a different core entity.
- Personal VO is private to the user.
- Public/commercial VO is available only through organization/enterprise context.
- Personal VO must not be converted directly into enterprise/public VO.
- If a similar enterprise VO is needed later, it must be created separately.

### 3.2 Organization / actor

- Actor may be a user/person or an organization.
- Organization acts as commercial actor/provider/owner of enterprise Value Objects.
- Existing route layer already creates/links organization, person and actor references.
- Ownership/security remains sensitive and must not be refactored casually.

### 3.3 Offer

- Offer is not a Value Object.
- Offer is a commercial certificate package / certificate terms wrapper around Value Object.
- Current target logic has one offer type.
- Offer may already have internal offer_items/package composition around Value Objects.
- Existing offer_items do not turn Offer into a cart/order and do not make Offer equal to Value Object.
- Correct wording: Offer is a commercial package over one or more Value Objects, used as the base for certificates.

### 3.4 Certificate

- Certificate is created from Offer.
- Certificate must not be created directly from Value Object.
- Existing certificate routes use request/redeem RPC logic.
- Certificate/points changes are security-sensitive because of reserved/spent/released points.

### 3.5 Purchase confirmation

- Purchase confirmation is not a platform-side purchase.
- Purchase happens outside the platform: offline or on the seller's own online channel.
- User submits a request to confirm that an external purchase happened.
- Seller confirms or rejects.
- If confirmed, points may be awarded.
- Purchase confirmation remains organization-level and amount-based.
- Required conceptual fields: organization_id, buyer_user_id, purchase_amount, currency, status, points_awarded, audit timestamps.
- No purchase_confirmation_items.
- No cart/order/item-flow.
- No required offer_id.
- No required value_object_id.
- The platform does not need to know exactly what was bought to award points.

### 3.6 Points

- Points are internal reward/discount rights, not money/token.
- Points must stay ledger-style.
- Wallet balances must not be changed manually without transaction trail.
- Points routes and transactions exist; any future change requires security/ledger verification.

### 3.7 Bookings

- Booking relation layer exists and references offer/certificate/provider/receiver concepts.
- Booking should not be refactored inside P4.8.0-A5.
- Booking integration with Value Object can be mapped later.

### 3.8 Directory

- Directory organization/profile/offers/filter routes exist.
- Directory currently can continue to expose organizations/offers.
- Later, directory may become a Value Object entry point.
- This is not an immediate migration blocker.
- UX/UI remains later.

## 4. Confirmed non-gaps

- No purchase_confirmation_items is not a missing feature. It is the correct target model.
- No required purchase_confirmations.offer_id is not a gap.
- No required purchase_confirmations.value_object_id is not a gap.
- Offer not being equal to Value Object is not a gap.
- Certificate not being created directly from Value Object is not a gap.
- No status/publication/moderation refactor is not a gap.
- No polished UX for the commercial Value Object layer is not a gap.

## 5. Confirmed current alignment

- value-objects route exists.
- value-objects route creates value_objects with owner_actor_id and organization_id.
- offers route uses value_object_id.
- offers route validates value_object relation to organization/owner actor.
- offers route may create offer_items as internal package composition.
- certificate request route uses offer_id and RPC.
- certificate redeem route uses certificate_id and RPC.
- purchase confirmation route uses organization_id and purchase_amount.
- purchase confirmation route does not use offer_id, value_object_id or item list.
- points wallet/transactions routes exist.
- booking and directory route layers exist.

## 6. Decisions for A6

### 6.1 First allowed implementation direction

A6 must be additive and structural only. It must not introduce a new business flow.

Likely A6 candidates:

1. Verify exact live DB relationship for offers.value_object_id:
   - column existence,
   - nullability,
   - FK,
   - index,
   - existing rows consistency.

2. If missing, prepare additive migration only:
   - nullable FK/index hardening for offers.value_object_id,
   - no destructive rewrite,
   - no mandatory backfill unless current data proves safe.

3. Decide whether to add value_objects.commercial_usage:
   - none,
   - catalog_info,
   - certificate_base,
   - both.

4. Verify offer_items table status:
   - route uses offer_items,
   - local migration search did not clearly show create table offer_items,
   - live schema must be checked before any migration.

### 6.2 What A6 must not do

- Do not create purchase_confirmation_items.
- Do not add required offer_id to purchase_confirmations.
- Do not add required value_object_id to purchase_confirmations.
- Do not turn purchase confirmation into cart/order.
- Do not create certificate directly from Value Object.
- Do not merge Offer and Value Object.
- Do not refactor booking flow.
- Do not refactor full status/publication/moderation domains.
- Do not change UX/UI.

## 7. Security-sensitive areas

- Organization creation and location changes.
- Offer creation with organization_id, owner_actor_id/provider_actor_id and value_object_id.
- offer_items package creation.
- Certificate request/redeem/cancel/expire flows.
- Points wallet and transactions.
- Purchase confirmation confirm/reject and points_awarded.
- Public purchase history and masking.

## 8. A5 final recommendation

The commercial core must not be rewritten. Current routes already support the main relationship structure needed for Commercial Value Object integration. The next safe step is not a new user-facing feature, but a live-schema verification and small additive migration plan if needed.

Recommended next step:

P4.8.0-A6 — live structural verification and additive migration plan.

A6 should first verify:

- offers.value_object_id FK/index/nullability/consistency,
- offer_items table existence/FK/index relationship,
- purchase_confirmations absence of item/cart/order structure,
- value_objects current columns and whether commercial_usage is absent/present.

Only after that, prepare a migration if there is a proven structural gap.
