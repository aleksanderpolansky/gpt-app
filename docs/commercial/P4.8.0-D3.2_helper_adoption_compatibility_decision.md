# P4.8.0-D3.2 — Helper Adoption Compatibility Decision

Status: DECISION / DOCUMENTATION ONLY

Runtime code changed: NO

## 1. Why this decision is needed

D3 confirmed that the first safe adoption candidates are:

- src/app/api/organizations/route.ts
- src/app/api/organizations/[id]/location/route.ts

Both contain local duplicated functions:

- normalizeCountryCode
- getDefaultCurrencyByCountryCode

However, direct replacement with the shared helper is not fully behavior-preserving yet.

## 2. Important compatibility finding

Current local organization route behavior:

- getDefaultCurrencyByCountryCode returns PLN as fallback for unknown/unsupported country code.

Current shared helper behavior:

- getDefaultCurrencyByCountryCode returns null for unknown/unsupported country code.

Therefore:

- Direct replacement would change runtime behavior.
- D3.2 must not blindly replace local functions.
- A compatibility decision is required before route adoption.

## 3. Business rule tension

Business target rule:

- organization currency must be derived strictly from organization country;
- organization currency must not be arbitrary manual input;
- unknown country should not silently create arbitrary currency.

Existing runtime behavior:

- unknown country currently falls back to PLN.

Interpretation:

- The current fallback is legacy/convenience behavior.
- The target architecture should eventually reject unsupported country/currency derivation rather than silently use PLN.
- But changing this behavior must be a deliberate runtime change, not a hidden side effect of helper adoption.

## 4. Safe technical options

### Option A — behavior-preserving adoption first

Modify shared helper to support explicit fallback behavior:

- getDefaultCurrencyByCountryCode(countryCode, { fallbackCurrency: "PLN" })

Then organization routes can adopt the helper while preserving current behavior.

Pros:

- safer adoption;
- smaller behavior risk;
- route refactor can be separated from business behavior change.

Cons:

- keeps legacy fallback alive temporarily.

### Option B — target behavior adoption

Replace local route logic with shared helper as-is and allow null for unsupported country.

Pros:

- aligns with target rule;
- avoids silent arbitrary PLN fallback.

Cons:

- runtime behavior changes;
- must verify all create/update flows handle null correctly;
- may require validation/error handling in organization routes.

## 5. D3.2 decision

Recommended decision:

Use Option A first.

Reason:

- D3/D3.1 promised behavior-preserving route adoption.
- Changing fallback behavior should be a separate later business-alignment patch.
- First adoption should only remove duplication.

## 6. Recommended next implementation block

Next block should be:

P4.8.0-D3.3 — add explicit fallback support to shared helper.

Scope:

- update src/lib/commercial/currency.ts only;
- add optional fallback argument;
- keep default helper behavior as null for unknown countries;
- allow organization routes to request legacy PLN fallback explicitly;
- run TypeScript check;
- document the change.

After that:

P4.8.0-D3.4 — adopt shared helper in organization routes only.

Scope:

- import normalizeCountryCode and getDefaultCurrencyByCountryCode from "@/lib/commercial/currency";
- remove duplicated local functions from organization routes;
- call getDefaultCurrencyByCountryCode(countryCode, { fallbackCurrency: "PLN" }) if behavior preservation is required;
- do not touch directory/offers/purchase-confirmation routes;
- run TypeScript check.

## 7. Later business-alignment block

After route adoption is stable, a later block may remove legacy fallback and reject unsupported country codes.

That later block should be explicit and tested.

Possible later name:

P4.8.0-D6 — remove legacy PLN fallback and enforce supported country currency derivation.

## 8. Forbidden changes remain forbidden

- Do not add purchase_confirmation_items.
- Do not add purchase_confirmations.offer_id.
- Do not add purchase_confirmations.value_object_id.
- Do not turn purchase confirmation into cart/order/item flow.
- Do not let organization currency become arbitrary manual user input.
- Do not transfer burned points to seller.
- Do not bypass certificate/points RPC.
